## What the product owner wants

An admin starts a venue's map from a **plan file the mall already has**, then edits it like anything drawn by hand. Under L108 the admin sets the buildings and levels, supplies one plan per level, and Gabay produces an **unpublished draft** that the admin reviews, corrects and publishes later (PRD §6.22).

**Scope as ruled (L183, Q1 (a)): DXF, IMDF and vector-PDF import, plus level alignment.** Scans, rasters and photos are not P1-03's: they go to OA-4's tracing and OA-5's AI conversion. The rules-based scan generator and E-14 are dropped. The entry stays P1.

The import reads the file by rules, with no AI and no OCR. Everything is processed **in the admin's browser**: the plan is sent nowhere, and the original is kept only if the admin chooses (DC21).

**What the generator makes** (L108, PRD §6.22)
- Walls, rooms (the largest connected region as the concourse), doors (wall gaps of 0.7 to 1.5 m).
- Stairs, escalators and lifts, where the file names them.
- Room names from the file's own text.

**What it never makes** (L108)
- Escalator direction, lift details, walk-through marks, step-free widths beyond what was measured, store details and beacons. The editor and the beacon planner set these.

**Levels** (L108): the levels of a building are lined up by clicking the same two fixed features on each.

**The review flag.** L108's "every generated element starts `NeedsReview` and publish refuses until each is confirmed" is **amended by L170 (Q2, Q3)**. Each generated element carries the document's `review` flag, shown as a check in the editor. It does not block publish.

## Settled context

- **Rulings that bind it:**
  - L108: inputs, the browser, P1, the original kept only if chosen (DC21), names on scans typed or picked by hand, no assisted tools now (P3-04), two-point floor alignment.
  - L109: Gabay's own DXF reader (not `dxf-parser`) and `pdfjs-dist`. (`@techstark/opencv-js` was also named there; it is dropped for P1-03 by L183.)
  - L170: the venue map document (one per venue, buildings and levels inside), autosave, warnings-only publish, AI conversion allowed. Q3 makes the review flag non-blocking.
  - L171: E-13 widened; E-27 and E-28 signed.
- **The output is the document.** Import writes into the venue map document's **draft**, saved through OA-2's route with `baseVersion` (409 on a stale save, one editor per venue, Q7). It does not publish; publish still validates (PRD §6.22). `DraftConfidence` and `NeedsReview` columns are gone (OA-1's recorded differences); the flag is `review`.
- **Not stores.** The import creates geometry and room names. It does not create `Occupant` rows (L108: store details are not generated; the editor's Stores panel and the map file's import do that, OA-3 Q11 (b)).
- **Test inputs.** Only throwaway or invented plans. The penthouse drawings never go into git (L48, L123).
- **Roles** (`plan/FF-SK-dashboards.md`, "Plan import and drafts"):
  - MALL_ADMIN: yes.
  - VENUE_EDITOR: confirm or fix only.
  - VIEWER: read-only.
  - SUPERADMIN: all, acting in a tenant.
- **Constraints:** the seven rules. Rule 7 applies through E-26 (forms from the layout schema); limits are named constants or settings (L108 names `import.maxImageMegapixels` and `import.doorGapMinM` and `import.doorGapMaxM`, 0.7 and 1.5). Draft-only data, no new shopper data, and no new table is expected.
- **Scale:** no target is stated for import size. PRD §7 gives venues up to about 100,000 m² and a graph of about 20,000 nodes. The document is capped at `MAX_MAP_BYTES` (4 MiB) and `MAX_POLY_POINTS` (64), so a large CAD file may exceed them. The spec asks rather than invents.
- **Approval:** the intent is approved (L183). Its spec follows after R13 (L175) and goes to the owner as usual (L156).

## Settled by the owner (P1–P3 sitting, 2026-10-14, L183)

Each question below was **ruled 2026-10-14 by the product owner: (a)**. The ruled option leads; the others are kept as the ones not taken.

**Q1 Is P1-03 narrowed to DXF, IMDF and vector PDF, merged into OA-5, or kept as L108 wrote it? Ruled 2026-10-14 by the product owner: (a).**
- (a) **Ruled: narrow it.** P1-03 is "exact import": DXF, IMDF and vector PDF, read directly in the browser, with level alignment. Scans, rasters and photos belong to OA-4's tracing and OA-5's AI conversion. It stays P1, and the rules-based scan generator and E-14 are dropped (Q2 handles the case of a mall that refuses AI). This keeps the one thing that only rules do well (L108's own analysis: "rules beat AI on CAD, IMDF and vector PDF") and avoids two separate scan pipelines.
- (b) Not taken: **merge** it into OA-5 as one "plan conversion" entry. DXF, IMDF and vector PDF would go through the same proposal flow, and the exact readers would not be built. Simpler, but every plan would then depend on the AI's gate and on the plan leaving the browser, including files that were exact to begin with.
- (c) Not taken: **keep** L108's scope: DXF, IMDF, vector PDF **and** scans by rules (E-14), beside OA-5's AI scan path. Most complete, and the most to build (L): two ways to convert a scan.

**Q2 If AI is off or refused for a mall, is there still a way to convert a scanned plan? Ruled 2026-10-14 by the product owner: (a).**
OA-5's AI conversion is off by default (`ai.planConversion`), and the owner's DPO record gates its first call. L108 chose "no AI" on purpose, so that confidential drawings never leave the browser (DPA).
- (a) **Ruled:** no automatic path for scans without AI. Those malls trace the plan by hand in OA-4's backdrop mode. P1-03 stays narrow (Q1 (a)).
- (b) Not taken: keep the rules-based scan generator (E-14) as the no-AI path.

**Q3 How does Gabay know which CAD layers mean walls, doors, stairs and lifts? Ruled 2026-10-14 by the product owner: (a).**
L108 says the generator reads "wall layers and polylines, door blocks, text for names, stair and lift blocks", but each mall's CAD names its layers differently.
- (a) **Ruled:** a **mapping step** the admin confirms before the import. Common layer names are pre-selected, and the admin can change them. The step is saved with the import so it can be repeated for the next level.
- (b) Not taken: a fixed layer-name convention that the mall's drafter must follow.

**Q4 Does importing an IMDF file set the venue's georeference? Ruled 2026-10-14 by the product owner: (a).**
IMDF carries real-world (WGS84) coordinates. The document's `site.georeference` is `null` unless it is set (OA-1), and real venues rely on it for BLE and detection by location (the seed note, FF-2 G1).
- (a) **Ruled:** yes, **when the file carries it**, shown to the admin to confirm (origin and bearing) before it is written.
- (b) Not taken: the admin sets the georeference by hand, and the import places the plan in the venue frame only.

**Q5 What does an import do to a level that already has drawing in it? Ruled 2026-10-14 by the product owner: (a).**
L108 generates an unpublished draft per building and level. PRD §6.22 says "for a floor". Neither says what happens to existing work.
- (a) **Ruled:** the import **replaces that level's drawing after the admin confirms**, as one undo step, and the stores' relational rows are untouched (their keys are checked as on any save, OA-3 AC-9). An empty level needs no confirmation.
- (b) Not taken: the import **adds** its elements to what is already there (merge).
- (c) Not taken: an import is allowed **only into an empty level**. The admin must clear the level first ("Clear the draft" is the only delete, L170 Q12).
