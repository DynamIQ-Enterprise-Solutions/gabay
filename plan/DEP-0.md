### 0.1 Already source-checked on 2026-10-16 (the coder re-pastes the lines)

- **The emulator reads the body before the function.** firebase-tools 15.32.1 `lib/emulator/functionsEmulatorRuntime.js` 541-560 builds an Express 4 app with `trust proxy` on. It runs body-parser json, text, urlencoded and raw (`*/*`) with a 32 MB limit, and `rawBodySaver` (379-381) sets `req.rawBody`. No error middleware comes before `app.all('/*')`, so a JSON parse failure is answered by Express's final handler and the function never runs. That is F2's HTML page.
- **F1.** The raw parser has already consumed the multipart body. multer 2.4.0 documents this case in its README ("streamHandler": "Google Cloud Functions and Firebase Functions … expose the already-read body as `req.rawBody`"); see `lib/make-middleware.js` 57-61, 123, 435. busboy 1.6.0 is multer's own dependency.
- **F2a.** body-parser 2.3.0 `lib/read.js` 40 skips an already-read request, so the API's `express.json({ limit: MAX_JSON_BODY })` never runs on the Functions path. The platform's 32 MB applies, not 5 MB.
- **F3, the address.**
  - The runtime listens on a named pipe (`functionsEmulator.js` 1124-1132; `functionsEmulatorShared.js` 200-208), so a request has no remote address.
  - `functionsRuntimeWorker.js` 109-113 forwards the client's headers and adds no `X-Forwarded-For`, so `req.ip` is undefined.
  - express-rate-limit 8.7.1 then logs `ERR_ERL_UNDEFINED_IP_ADDRESS` once and gives every caller one key.
- **F3, the header.** `functionsEmulator.js` 139 builds the hub with a plain `express()` and never disables `x-powered-by`. helmet 8.3.0 (`index.cjs` 328-333) removes it inside our app, so the header is the emulator hub's.
- **F4.** `middleware/auditTrail.js` `snapshotOf` stores `redactSecrets(req.body)` whenever `req.body` is defined. On the Functions path that is an upload's Buffer, a form or text body, or `{}`; in-process it is undefined.
- **The suite cannot see a pool-of-one stall.** `functions/test/savepointDb.js` runs every API test over one connection.

**Plan criteria for the findings (P-rows).** Each is proven in-process through the platform-shaped host, and on the real emulator by the probe.
- **P-1:** a backdrop upload on the Functions path answers exactly as it does in-process: 201, 413 or 400.
- **P-2:** a JSON body over `MAX_JSON_BODY` gets 413 `{ "error": "Request body too large" }` on both paths.

## 3. Rulings and design choices (the spec's DC-1 to DC-25 apply; each below has an alternative)

- **R1: JSON the platform cannot parse gets the platform's own answer.** On the emulator the function never runs (§0.1). The API cannot shape that answer, and DEP-0 does not patch or wrap the framework.
  - The requirement becomes: on staging (`NODE_ENV=production`) that answer carries no stack and no path. A template line proves it at DEP-1.
  - Locally, the emulator's HTML page is a known difference, recorded in INSTALL.
  - **If row F-b shows Cloud's framework calls the function with `rawBody` on a parse failure,** `platformBody` refuses with `{ "error": "Malformed JSON body" }` and the host test covers it.
  - *Alternative:* pin `@google-cloud/functions-framework` and serve through it ourselves. That means a new library, an E-entry and an owner signature, and it still does not change what Cloud runs. Better if F-b shows the managed framework leaks a stack even under production.
- **R2: `staging:admin` refuses when `GOOGLE_APPLICATION_CREDENTIALS` is set.** AC-56 says the tool reads no key file, and the Google auth library reads one from that variable. *Alternative:* unset it silently, but then the owner would not learn which credential was used.
- **R3 (DC-32): under the emulator, a request with no socket address and no forwarded header is the loopback.** firebase.json binds the emulator to 127.0.0.1. *Alternative:* leave it NULL. True to the socket, but then the limiter puts every local caller under one key.
- **R4: where the tools live.** `db:deploy` in `db/tools`, `staging:seed` in `db/seeds`, `staging:admin` in `tools/` with an injected library, and the allow-list in `db/tools/lib/localDatabases.js`.
- **R5 (DC-30): AC-15 is proven by `dep0.poolOfOne.test.js` over a real pool of one.** *Alternative:* the spec's second full suite run at `PG_POOL_MAX=1`. It cannot see a self-wait, because every suite runs over one savepoint connection.
- **R6: AC-42's tests run in `api:test`.** *Alternative:* `tools:test` with its own scratch database, which duplicates the harness.
- **DC-26:** `platformBody` detects the pre-read by `req.rawBody`, with no mode flag. *Alternative:* `createApp({ host: 'functions' })`, which is one more thing to forget.
- **DC-27:** multer's documented `streamHandler` (2.4.0). *Alternative:* parse with busboy directly, which needs a pin, an E-entry, and copies of multer's limits.
- **DC-28:** a platform-shaped host built from the emulator's source. *Alternative:* `@google-cloud/functions-framework` as a pinned devDependency, which needs a new-library signature. Better if F-b shows Cloud's parser differs in ways the host cannot copy.
- **DC-29:** F1's emulator check signs in through the Auth emulator inside `functions-health`. *Alternative:* the manual case DEP0.1 alone, which catches no regression.
- **DC-31:** the `staging:admin` CLI loads `firebase-admin` from `functions/` through `createRequire`. *Alternative:* add it to `db/tools`, which makes a second pin.
