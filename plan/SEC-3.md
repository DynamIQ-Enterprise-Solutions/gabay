## 0. Doc checks pasted into the PR before any code (spec §7 RECALLED table, step 0)

**The SEC-1 contract as built** (read on `sec-1` at 69f56d4, 2026-10-15; re-read at the merge, and any later difference stops the slice):
- `GET /api/me` returns `{ user: {userId, email, displayName}, isSuperAdmin, platformRoles, tenants: [{tenantId, code, name, isActive, roles, permissions: {<key>: {create, read, update, delete}}}] }`. For a SUPERADMIN only, it also returns `actAsTenants: [{tenantId, code, name, isActive}]`, every tenant, ordered by `Code`.
  - **Difference from the spec:** the spec's `{id, code, name, active}` (AC-45, AC-47) is built as `tenantId` and `isActive`, the same keys as `tenants[]`. The Dart parser and the fixtures use the built names. This changes no behaviour; it is listed for sign-off (L174).
- Error bodies are `{ error: "<message>" }` (`utils/errors.js`). The five refusals of `middleware/tenantContext.js` (`MSG`) are:
  - 400 `Choose a tenant: this works inside one tenant` (M-NO-TENANT)
  - 403 `This account has no access to that tenant` (M-NOT-HELD)
  - 403 `This tenant is not active` (M-INACTIVE-TENANT; SUPERADMIN proceeds)
  - 403 `You do not have permission to do this` (M-FORBIDDEN)
  - 503 `Permission check unavailable` (M-UNAVAILABLE)

  The `M-*` codes are only labels in the server's comments; they are not in the body. The client therefore decides by status (DC-4) and shows the body's text only through `formatApiError`.
- `middleware/auth.js` answers:
  - 401 for a missing token, an expired session, an invalid session or an inactive account;
  - 403 `This account has no access`;
  - 503 when Firebase or the database is unreachable.
- `auth/routeKeys.js` `ROUTE_KEYS`: `lookups`, `venues`, `venue-maps`, `venue-versions`, seeded by `db/migrations/0002_permission_rows_and_userrole_index.sql`. `venues` is C R U - for MALL_ADMIN and - R - - for VENUE_EDITOR and VIEWER.
- `.env.example` defines two auth modes:
  - **emulator:** `FIREBASE_AUTH_EMULATOR_HOST` set; project `demo-gabay`.
  - **real project:** `FIREBASE_PROJECT_ID` set, the host empty, and `GOOGLE_APPLICATION_CREDENTIALS` set to an absolute path outside the repository.

  The real-project mode replaces the spec's RC-16 "no service-account key": SEC-1's step 0 (a) found that the revocation check needs a credential. That affects the owner's steps and the risks.

## 3. Design choices (the spec's DC-1 to DC-12 apply as written; the plan adds these, each with an alternative)

- **DC-13 Only `venues` gets a permission key now.** The slice that builds a module chooses its key along with its routes. *Alternative:* key the map editor to `venue-maps` and Publish to `venue-versions` now. Passed over because the seeded MALL_ADMIN row for `venue-versions` has read set to false (create only), so Publish would vanish from MALL_ADMIN's menu the day FF-3′ sets `built`. *Better when:* keys and modules are one to one.
- **DC-14 Inactive tenants.** A non-SUPERADMIN is never offered one, since every request would answer 403 M-INACTIVE-TENANT; with no active tenant they get AC-18's empty dashboard. A SUPERADMIN is offered every tenant, inactive ones marked "(not active)", because the server lets it act there. *Alternative:* list inactive tenants as disabled entries for everyone. More to read, and nothing to do with them.
- **DC-15 The "Choose a tenant" step is a shell state, not a route.** *Alternative:* a `/choose-tenant` route. One more guard branch, and a `from` to carry through it.
- **DC-16 One `tenantScopeProvider`** keys every tenant-scoped provider. A scope change disposes them, and answers are applied only while `ref.mounted`. *Alternative:* a `CancelToken` per scope in `ApiClient`. It changes every service signature.
- **DC-17 `bootAdmin(AuthService)`**, so the entrypoint test boots the real entry point with the fake. *Alternative:* mocking Firebase's platform channels. That relies on a RECALLED test API and is brittle.
- **DC-18 `SpecFormField` gains `focusNode`, `textInputAction` and `onSubmitted`.** *Alternative:* a `Shortcuts` wrapper for Enter. It misses a phone keyboard's action key.
- **DC-19 Sign-in paths match exactly.** *Alternative:* keep `contains`. `/me` would then also swallow the 401s of `/merchants` and similar paths.
- **DC-21 One branch carries the `tools/lint` and `functions/test` files**, named here. *Alternative:* a tools-lane PR first. It would block step 4 behind another merge.
- **DC-22 `from` is capped at 2048 characters, and a repeated `from` is ignored.** *Alternative:* take the first value. That hides a crafted link instead of refusing it.
- **DC-23 SEC-3 creates `raw-error-text.js` under SEC-2's name**, and SEC-2 adds its half to it. *Alternative:* a separate `raw-error-text-dart` lint. AC-59 asks for one name.

## 4. Risks and sequencing

- **The admin page is at 401 between SEC-1's merge and SEC-3's.** There is no token and no stub. SEC-3's PR opens as soon as it is green, and nobody runs the page from `main` in between. Flutter tests never call the server, so CI stays green.
- **The plugins break the shopper's Android build (RC-1),** or step 0 (a) finds a minimum SDK above the floor. Stop and ask; do not pin another version. iOS cannot be built on this machine and stays unchecked until a Mac or CI run.
- **The real project needs a service-account key on the owner's machine** (SEC-1 step 0 (a)). Without it, every request is 503 and the page shows "the server did not answer". The runbook line and the owner's steps say so.
- **GitHub's secret scanning may alert** if a values file is ever committed (RECALLED). It stays ignored.
- **CI's `build` job** builds the release admin page with no Firebase defines. The artefact refuses to start (AC-2). It is only a size artefact, and DEP-1 passes the staging values.
- **The C1 surface is large** (`admin_shell_test.dart` is about 1,200 lines). The Opus review takes steps 3, 5 and 7 first.
- **SEC-2 may land its half of `raw-error-text` first.** Rebase onto it; it is one file and one registration.
- **Timing is unmeasured.**
