## 3. Design choices (the spec's DC-1 to DC-20 apply as written; the plan adds these, each with an alternative)

- **DC-21 Freeze `schema-0.15.sql` now and run 0001's test on a 0001-only folder.** SEC-1 is the first slice to move `schema.sql` past 0.15, and AC-35 (b) needs a 0.15 database anyway. *Alternative:* keep `migration0001.test.js` on the current schema and run every migration on both sides (the fingerprints still match, since 0002 only drops an index that 0.16 lacks). Simpler, but 0001's test then asserts a moving target and its name lies; OA-3a would redo the fixture.
- **DC-22 The start-up mode line is written by `createApp`, not the verifier.** The verifier is lazy and has no logger; the app has both at build. *Alternative:* log at the first token. Later, and silent for an API nobody calls.
- **DC-23 The harness's default caller is MALL_ADMIN in tenant A.** It is what the stub gave, so hundreds of OA-1/OA-2 assertions keep their answers and only the transport changes. *Alternative:* no default, every call names its role. Clearer, and a far larger C1 diff for no new evidence.
- **DC-24 Guards are mounted by the routers, which take `guards` as a dependency.** Each route's key and action sit beside its handler, where SEC-2's `route-guard-order` lint will read them. *Alternative:* a route table in `api.js` mapping paths to guards. One place to read, but a path pattern written twice.
- **DC-25 `tenantContext` answers 503 for every failed snapshot load, including a connection failure that the error handler would call `Database unavailable`.** AC-23 asks for one message from the chain. *Alternative:* let `dbUnavailable` errors keep S1's text. Two texts for one failure.
- **DC-26 `tenantExists` becomes `tenantById` returning `{ isActive }`.** One query serves the existence and the inactive check for SUPERADMIN. *Alternative:* a second query. One statement more per act-as.

## 4. Risks and sequencing

- **The admin page is unusable between SEC-1's merge and SEC-3's** (EC-51: no bearer token, no header for most users → 401). Handled by order: SEC-3 starts in the screens lane when SEC-1's PR opens, and the two merge back to back; nobody runs the page from `main` in between. The Flutter tests stay green (they do not call the server).
- **OA-3a's migration becomes 0003** and its schema 0.17; its index count re-starts from 136 (its plan already says it is re-checked against SEC-1 as built; §4 row 1 of that plan is done here).
- **Step 0 (a) may say a service-account key is needed** for the revocation call in real mode. Then SEC1.20 waits for the owner's key; nothing automated depends on it (the emulator is the test path). Without a key every real-mode request is 503 (AC-58), which is the safe failure.
- **`api:test` on a database without 0002** fails at the harness's one-time check with a message naming `npm run migrate`; `verify` and CI run `setup-db` first, so only a hand-run is affected.
- **The `schema-drops` and `migrations-immutable` lints** read `schema.sql` pairs and committed migration edits; a `DROP INDEX` in a new migration is outside both (checked: `tools/lint/schema-drops.js` pairs `CREATE TABLE` with `DROP TABLE` only). If the pre-commit hook objects, stop and ask; do not edit the lint.
- **Timing is unmeasured** (DEPLOY-staging §2: SEC-1's elapsed days are the first measure).
