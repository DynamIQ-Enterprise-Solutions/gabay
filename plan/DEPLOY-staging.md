## 0. Recommendation

Build the security core first (R1, R2, R4, R7, R8 are the must-haves; R3 and R5 ride with them), then four deploy-hardening items, then create one private staging project and let CI deploy it on every merge. Staging is for you only: no shopper, no real mall data, no penthouse, throwaway data that is thrown away at R13. Production stays a separate project and a separate, named, manual call.

Why this order, from the code (origin/main 09b2788): the API cannot even start outside development today. `createApp()` builds `createDevStub(...)` unconditionally and that function throws unless `NODE_ENV` is `development` or `test` (`functions/src/app.js`, `middleware/devStub.js`, `config/index.js`). So R1 is not optional for any deploy; and files are saved with `LocalFileStore` on the function's disk (`services/storage/localFileStore.js`), which a Cloud Function cannot keep (§3).

## 4. Continuous deploy

- **Trigger and gate.** `.github/workflows/deploy-staging.yml`, modelled on `build.yml`: runs after a successful run on a **push to main of this repository** (the same three-part `if:` that `build.yml` uses against forks, pinned by `tools/test/workflows.test.js`). e2e today runs only on pull requests (and nightly), on the PR's merge ref, not on main's own commit; so e2e also gets a `push: main` trigger and the deploy waits for **lint and e2e green on the same commit** (a check-runs lookup before any credential step). Alternative: gate on the PR's e2e only, cheaper but not the deployed commit.
- **Steps.** build admin web with the staging `API_BASE`; `db:deploy`; `firebase deploy --only functions,hosting --project gabay-staging`. `concurrency: deploy-staging`, no cancel of a running deploy, so merges deploy one by one in order.
- **Identity.** **Workload Identity Federation**, not a key (checked in `google-github-actions/auth`: WIF "is recommended over Service Account Keys"; keys "must be treated like a password" and "never expire"). The pool carries an attribute condition: this repository and `refs/heads/main` (claim names RECALLED, checked at setup); `permissions: id-token: write, contents: read`; a GitHub environment `staging` limits who can use it. The deploy service account gets only the roles `firebase deploy` and Cloud SQL need (the list is read from the docs at DEP-1's start, not assumed), and it exists **only in the staging project**: it has no way to touch production. This repository is **public** (L177): no secret in it, no `pull_request_target`, no fork code with credentials.
- **Production** is never automatic: a separate project and a named release authorization (standard Stage 5; L109). The owner's standing call is for staging only.
