## 1. What this delivers

A staff member opens the admin page, signs in with email and password, and sees only what their role allows. Nobody reaches an admin screen without signing in. The development switcher, the `X-Dev-Act-As` header and the "Development build: no sign-in" banner are gone ("a real working login", L185).

In `app/` (the admin page and the app's admin side; the shopper app is not touched):

1. **E-19.** `firebase_core` and `firebase_auth`, requested at this slice's start, versions read from pub.dev then, pinned in Blueprint Part 1 (PH2 Q10).
2. **Sign-in.** `/login`: email and password, a `FieldSpec` form (rule 7), English by design (L165), "Forgot your password?" through Firebase's reset link, no sign-up anywhere. A Firebase user with no admin account is told plainly and signed out.
3. **Session.** Firebase's own restore before the first frame; the token and tenant providers; the 401 path; manual sign-out versus expiry (expiry keeps `?from=`); no logout timer.
4. **Routing.** One `go_router` `redirect`, `refreshListenable`, the existing `ShellRoute`, the one app-wide `RouteObserver`. The menu is built from `GET /api/me`'s merged permissions and replaces the app-registry menu. A tenant switcher. The venue switcher is deferred to OA-4a (Q5 (a), L186) [r2].
5. **Removed.** The dev switcher, `X-Dev-Act-As`, the banner, their ARB keys, tests, manual rows and ledger rows.
6. **Its own tests and e2e cases**, screenshots, a changelog entry.
7. **[r2] The real Firebase project.** The admin page signs in against the real Firebase Auth project (Spark plan, created by the owner, L186) while the API and the admin page run on this machine; the Auth emulator stays the automated and manual test path (AC-2, AC-61, §7a).
8. **[r2] The Dart half of `raw-error-text`** (AC-59, from SEC-2's Q4 (c)) and **the narrow `auth.<form>` mode of `schema-forms`** that lets the sign-in password be a `FieldSpec` (AC-6, AC-60, E-30).

**Dependencies on SEC-1 (not yet specified; the plan re-reads SEC-1's spec and fails closed on any difference).** SEC-3 relies on these, taken from the intent and from code that is on `main` today:

- `GET /api/me` returns `{ user: {userId, email, displayName}, isSuperAdmin, platformRoles, tenants: [{tenantId, code, name, isActive, roles, permissions: {<routeKey>: {create, read, update, delete}}}] }` (`functions/src/auth/permissionMerge.js`, `buildAccessProfile`, merged in S1). Permissions are already merged per tenant.

- **[r2]** `GET /api/me` also returns `actAsTenants`, a list of `{id, code, name, active}` for every tenant, **for a SUPERADMIN only** (Q4 (a); SEC-1's r2 adds it); for any other user the field is absent. It is the SUPERADMIN's tenant list (AC-45, AC-47).

That is an operator setting, not SEC-3 code (§7a).

### B. The sign-in screen

- **AC-5:** `/login` shows the title, an email field, a password field, a "Sign in" button and a "Forgot your password?" action. Nothing on the admin page offers "create account", "sign up" or "register": no button, link or text, and no code path calls Firebase's create-user. The auth port (DC-2) has exactly these operations: sign in with email and password, sign out, send a reset email, get an ID token, and the stream of sign-in changes. Verify: widget test (the visible controls; no sign-up text); unit test (the port's methods; the fake and the real class implement the same interface); review.
- **AC-6 [r2] (Q3 (a), E-30):** The email field is a `FieldSpec` on `AppUser.Email` (`text`, `required: true`, `maxLength: 254`, `FieldFormat.email`; the existing `appUserEmail` spec may be reused). The password field is a `FieldSpec` with a new `FieldFormat.password` and `table: 'auth.signIn'`, `name: 'password'`, `kind: ColKind.text`, `required: true`. `FieldFormat.password` makes `SpecFormField` build a hidden-text input with password autofill hints, no input formatter, no trimming and no value echo in semantics. Both fields are placed through `SpecFormField`. No view builds a bare `TextField` or `TextFormField`. The `auth.` mode is AC-60. Verify: `npm run verify` (`schema-forms`, `no-bare-textfield`); widget test (the password is hidden; the typed value is not in the semantics tree; it is not trimmed).
- **AC-7:** The client refuses before any call: a blank or whitespace-only email ("Email is required."), an email that is not an address, an email over 254 characters, and a blank password. The email is trimmed before it is sent; the password is sent exactly as typed (never trimmed). The messages are the existing field validators' (standard §4.6 `Validators`) and name the field. Verify: widget test (each case; the sent values).
- **AC-8:** A correct sign-in loads the account (`GET /api/me`, AC-21), resolves the tenant (AC-43, AC-44), and goes to the `from` address when there is a valid one (AC-42) and to `/admin` otherwise. Verify: widget test (fake AuthService, scripted API).
- **AC-9:** A failed sign-in shows one plain message from the Firebase error code, never the code or the exception text, through a `formatAuthError` that sits beside `formatApiError`. A wrong password and an unknown email show the same text, so the screen never says which email has an account. The mapping covers: invalid credential, wrong password, user not found, invalid email, user disabled, too many requests, no network, and an unknown code (RC-5). Verify: unit test (each code to its text; an unknown code to the generic text; no text contains the code); widget test.
- **AC-10:** While a sign-in is in flight the button is disabled, so a second tap makes no second attempt. After a failure the email is kept, the password is cleared, focus returns to the password field, and the button is enabled. Pressing Enter in either field submits. Verify: widget test (a delayed fake; double tap makes one call; the field states).
- **AC-11:** Both fields declare autofill hints so a password manager can fill them (RC-12), and each control has a screen-reader name. Verify: widget test (`Semantics`, the hints).
- **AC-12:** `/login` makes no API call and sends no `Authorization` or `X-Tenant-Id` header, and shows nothing from an earlier session. Verify: widget test (an `ApiClient` double that fails on any call).

### C. Forgot password

- **AC-13:** "Forgot your password?" uses the email already typed. A blank or malformed email shows the field message and sends nothing. A valid one asks Firebase to send its reset email (RC-6) and shows one plain confirmation. The confirmation is the same whether or not the email has an account (no account enumeration; with Firebase's enumeration protection on or off, RC-6). A too-many-requests or no-network answer shows its own plain message. Verify: unit test (the mapping); widget test (blank, malformed, unknown, known, throttled, offline).
- **AC-14:** The reset does not sign anyone in and does not change the screen's state beyond the message. The page where the new password is typed is Firebase's own hosted page (RC-6): SEC-3 builds no reset screen and sets no continue URL. Verify: manual (against the Auth emulator: request a reset, take the link from the emulator's reset-code list, RC-6, set a new password, sign in with it); widget test (no navigation after the confirmation).

### D. Accounts that have no access

- **AC-15:** Firebase accepts the sign-in but the API answers 403 to the first `GET /api/me` (no `AppUser` row, or a shopper identity): the page says plainly that the account has no access to the admin page and whom to ask (§9), Firebase is signed out, the user is back on `/login` with that message, and nothing of the account is kept. Verify: widget test (fake AuthService, API 403); API test already exists for the 403 itself (`auth.middleware.test`, S1) and SEC-1 adds its e2e case.
- **AC-16 (DC-4):** The API answers 401 to the first `GET /api/me` after a fresh sign-in (an inactive `AppUser`, or a revoked token): the page says the account cannot sign in right now and whom to ask, Firebase is signed out, and the user is on `/login` with that message. It is not the "session ended" message of AC-22. The client tells the two apart by status code and by whether it was a fresh sign-in, never by the response text. Verify: widget test.
- **AC-17:** The first `GET /api/me` after sign-in fails with 503 or no network: the user stays signed in, the page says the server did not answer, with "Try again" and "Sign out" (AC-23); no module screen builds. Verify: widget test (503, then a successful retry).
- **AC-18 (DC-10):** An active `AppUser` with nothing it may open (no role in any tenant, or a map with no readable module) is signed in and sees the dashboard's empty state with "Sign out"; it opens no module. Verify: widget test (a profile with `tenants: []` and not SUPERADMIN).

### E. The session

- **AC-19 (DC-1):** Every API call carries `Authorization: Bearer <ID token>`, with the token obtained from Firebase at call time (it may refresh, so the callback may be asynchronous), and `X-Tenant-Id: <active tenant id>` when a tenant is chosen. No call carries `X-Dev-Act-As`. A per-call `Authorization` header still wins. A request made while signed out carries no token. A sync callback still works, so the shopper app's use of `ApiClient` and its tests are unchanged. Verify: unit test (`api_client_test`: an async token, a sync token, no token, the header absent, the override).
- **AC-20:** The ID token is never read, parsed, stored or logged by Gabay code outside the one `Authorization` injection. Nothing in the client parses `exp`. Verify: review; unit test (a source scan of `app/lib` finds no `exp` parsing and no token in a log call).
- **AC-21 (DC-3, DC-5):** `GET /api/me` is loaded at sign-in, at restore and on "Try again", and is held by one session notifier whose states are: restoring, signed out (with a reason), loading the account, signed in (with the account), account error. Switching tenant does not reload it (the reply already holds every tenant's permissions). A malformed reply is an account error, never a partial menu (EC-43). Verify: unit test (the notifier through each transition with the fake AuthService and a scripted API); widget test.
- **AC-22 (expiry):** Any 401 other than the one on the first `/me` after a fresh sign-in (AC-16) takes the expiry path, once: Firebase is signed out, the session and every tenant-scoped provider are cleared (AC-26), and the browser goes to `/login?from=<the page the user was on, with its query>`, with the plain message "Your session has ended" (§9). Several 401s at once (a page that issues three requests as the session ends) cause one sign-out and one redirect, never a loop. The frozen `Future` of the 401 handler stays (standard A.11). Verify: unit test (three simultaneous 401s, one handler run); widget test (the redirect and its `from`).
- **AC-23 (manual sign-out):** "Sign out" in the account menu (AC-40) signs Firebase out, clears the session and every tenant-scoped provider, and goes to `/login` with no `from` and no message. It needs no confirmation. Verify: widget test.
- **AC-24 (PH2 Q5, no timer):** The client schedules no logout timer and makes no decision from the wall clock. With the page left open and no request made, nothing happens however long it stays; the next request that the API answers with 401 takes the expiry path. Verify: widget test (fake time advanced by nine hours with the fake AuthService: still signed in and on the same page; then one scripted 401: expiry path); review.
- **AC-25:** A saved sign-in that is older than the API's limit (eight hours since sign-in, L151) is handled by the same path: restore, `/me` answers 401, the user lands on `/login?from=<the address that was opened>`. A saved sign-in whose Firebase user was deleted or disabled elsewhere ends the same way once Firebase refuses to refresh the token and signs out (RC-4). Verify: widget test (the 401 on restore); manual (set `auth.idTokenMaxAgeS` to a few seconds on the emulator database, wait, reload).
- **AC-26 (nothing carries over):** On sign-out and on expiry, every cache that holds tenant data is discarded: loaded lists, forms, the account, the active tenant and the remembered-tenant state in memory. A second user who signs in on the same tab sees none of the first user's data, even for an instant. Verify: widget test (sign in as a user of tenant A, load a list, sign out, sign in as a user of tenant B: no tenant A row is ever built).
- **AC-27 (other tabs, RC-3):** If the Firebase sign-in ends in another tab, or Firebase signs this tab out, without this tab's own sign-out action, this tab takes the expiry path of AC-22. If a user signs in in another tab while this tab is on `/login`, this tab follows (the `from` address, else `/admin`). Verify: unit test (the fake emits "signed out" without a sign-out call, and "signed in" while on `/login`); manual (two tabs).
- **AC-28 (DC-6):** Gabay stores no token, no password and no session blob. The only thing it keeps on the device is the remembered tenant (AC-39), in `shared_preferences`; Firebase keeps the sign-in itself (RC-3). Verify: unit test (after a sign-in, the store holds only the tenant key, keyed by user id); review.

### F. Routing and the guard

- **AC-29:** On the admin surface the router has exactly one `redirect`, a `refreshListenable` that fires when the session, the account or the active tenant changes, the existing `ShellRoute` around the dashboard and every module page, and the app's one `RouteObserver`. SEC-3 adds no second observer: if FF-1's slice 2b has put `routeObserverProvider` on `main`, SEC-3 keeps it; if not, SEC-3 adds that one. Verify: unit test (the router has one redirect and one observer; changing each listened state re-runs the redirect, RC-13); review.
- **AC-30 (the guard's order):** For a location on the admin surface the redirect decides in this order: (1) signed out or restoring: `/login` with `from` per AC-42, except `/login` itself; (2) signed in and on `/login` or `/`: `from` if valid, else `/admin`; (3) an account error or a loading account: no redirect, the shell shows its state (AC-41); (4) signed in and under `/admin`: the permission check of AC-31; failure goes to `/unauthorized`. The decision is a pure function of the session, the account, the active tenant and the location, tested without a widget. Verify: unit test (a table of states and locations, each with its destination).
- **AC-31 (CRUD from the URL tail):** Under `/admin`, the first segment after `/admin` names a module in the registry, and each module names the one `PermissionRoute` key it is guarded by. The check reads the active tenant's permission map: a path ending in `/new` needs `create`; a path ending in `/<id>/edit` needs `update`; any other path under the module, a record form route `/admin/venues/<id>` included, needs `read` (that form opens read-only for a user without `update`, as P0-01 AC-36 says); the check walks up the path to the module's key. SUPERADMIN (`isSuperAdmin`) passes every check for a module in the registry. For anyone else a module with no key, or a key the reply does not grant, fails closed. An id that is no module in the registry shows the existing "not available" page, not `/unauthorized`. A read-only user who types `/admin/venues/new` lands on `/unauthorized`. Verify: unit test (each of the four seeded roles' fixtures against typed-out paths: `/admin`, `/admin/venues`, `/admin/venues/new`, `/admin/venues/7`, `/admin/users`, an unknown id).
- **AC-32:** A test walks every route registered under `/admin` by `adminRoutes()` and every module in the registry, and fails when one has no verdict: a built module without a key, a key the registry names that no migration seeds (AC-35), or a registered route whose first segment is no module. A later slice cannot ship an unguarded screen. Verify: unit test.
- **AC-33:** The guard applies to the admin surface only. The shopper surface's routes and shell are unchanged and have no sign-in until R10. Verify: widget test (the shopper router has no redirect to `/login`).
- **AC-34 (DC-8):** On the admin surface `/` and `/about` need a sign-in. `/` goes to `/admin` once signed in; its build-page content (sample message buttons) is no longer reachable from the admin page. "About" (version lines and the list of changes) is reached from the account menu (AC-40). `/login` is the only page open to a signed-out visitor, apart from Firebase's hosted reset page, which is not Gabay's. Verify: widget test (signed out, each of `/`, `/about`, `/admin`, `/admin/venues` goes to `/login`; signed in, `/` goes to `/admin`, About opens from the menu).
- **AC-35 (menu and backend agree, standard §4.5):** A test reads the migration that seeds `PermissionRoute` and fails when a module with `built: true` names a key that migration does not seed, so the menu never shows a page whose backend refuses the role. Verify: unit test (reads `db/migrations/` as `tools:test` reads other files; depends on SEC-1).
- **AC-36 (`/unauthorized`):** `/unauthorized` says plainly that the account does not have access to the page and offers "Back to the dashboard". A signed-out visitor never sees it (they are sent to `/login`). It is in the shell. Verify: widget test.

## 3. Edge cases

Each one gets a test in the plan or a one-line reason why not. "W" is a widget test, "U" a unit test, "M" a manual case.

**Offline or stale data**
- **EC-1:** The API is unreachable or answers 503 on restore: the user stays signed in; the shell shows the account error with "Try again" and "Sign out"; never the sign-in screen and never a sign-out (AC-17). W.
- **EC-2:** Offline at a sign-in attempt: the plain no-network message; the typed email is kept (AC-10). W.
- **EC-3:** The token needs a refresh and there is no network: the request fails as a network error and shows through `formatApiError`; the session is not treated as expired. W (an async token callback that throws a no-network error).
- **EC-4:** The page is left open past eight hours with no request: nothing happens until the next request, which answers 401 and takes the expiry path (AC-24, PH2 Q5). W.
- **EC-5:** The user's role or grants change on the server while the page is open: the menu and the dashboard stay as loaded until the next account load (sign-in, restore or "Try again"). The server enforces regardless; a forbidden call shows the plain 403 message on its page (EC-29). One-line reason not to test more: the staleness is by design (no timer, no polling) and the server's refusal is SEC-1's test.
- **EC-6:** A saved Firebase sign-in older than the limit at reopening: AC-25. W, M.
- **EC-7:** A saved sign-in whose Firebase user was deleted or disabled: Firebase refuses to refresh and signs out (RC-4); the page takes the expiry path. U (the fake emits signed-out), M against the emulator if it can reproduce it (RC-4; if not, one-line note in the report).
- **EC-8:** A stale shopper package: not applicable. The admin page holds no package. The shopper app is not touched.

**Empty and maximum data**
- **EC-9:** An `AppUser` with no role anywhere and not SUPERADMIN: AC-18 (the empty dashboard with "Sign out"). DC-10. W.
- **EC-10:** One tenant: AC-43. Five tenants (the PRD §7 pilot size) and more than five: AC-52; the list scrolls and has no cap, search or paging. W.
- **EC-11:** Maximum lengths: an email of exactly 254 characters is accepted by the client; 255 is refused with the field named. A display name of 120 characters and a tenant name of the schema's length show truncated and complete in the screen-reader value (AC-40). W.
- **EC-12:** A user with every module (SUPERADMIN, 22 modules today) and a user with one module: menu and dashboard handle both at ×1.4. W (the existing shell tests, updated).
- **EC-13:** A password pasted with a trailing space is sent verbatim; a very long pasted password is sent as typed and Firebase decides (no client maximum is invented). U.

**Tenant boundary** (the server's tenant checks are SEC-1's; these are the client's)
- **EC-14:** With no tenant chosen (SUPERADMIN) no `X-Tenant-Id` is sent (AC-47). W.
- **EC-15 (cross-tenant URL):** Tenant A is active and the user opens a record address of tenant B (`/admin/venues/<B's id>`): the API answers 404 or 403, and the page shows the plain refusal through `formatApiError`, never tenant B's data, and offers the way back. The guard cannot decide this (the address holds no tenant), so the test is on the page's error state with a scripted refusal. W.
- **EC-16:** Switching tenant while on a deep address goes to `/admin`; lists of the old tenant are dropped and its in-flight answers ignored (AC-45). W.
- **EC-17:** Two users on one browser: the remembered tenant is per user (AC-46). U.
- **EC-18:** A remembered tenant the account no longer holds is dropped (AC-46); the account's remaining tenant is used if there is one, otherwise the "Choose a tenant" step of AC-44. U.
- **EC-19:** Sign-out then sign-in as another user on the same tab shows nothing of the first (AC-26). W.
- **EC-20:** The server refuses the chosen tenant with 403 (a membership removed since the last account load): the page shows the plain 403 message; the next account load drops the tenant (EC-5). One-line reason not to test further: the refusal is SEC-1's.

**Each role** (fixtures typed out from the L41 matrix as SEC-1 seeds it)
- **EC-21:** SUPERADMIN: every module, no tenant until chosen, any tenant in `actAsTenants` (AC-37, AC-47). W.
- **EC-22:** MALL_ADMIN: modules by `read`; writes by flags (AC-37, AC-39). W.
- **EC-23:** VENUE_EDITOR: Venues read-only; typed `/admin/venues/new` goes to `/unauthorized` (AC-31). W, U.
- **EC-24:** VIEWER: every module the matrix gives it, read-only; typed `/admin/venues/new` and `/admin/users` go to `/unauthorized` (AC-31). W, U.
- **EC-25:** One user, MALL_ADMIN in tenant A and VIEWER in tenant B: the menu and the write controls follow the active tenant (AC-37, AC-45). W.
- **EC-26:** A role code with no dashboard in the app (MERCHANT, UNIT or MAINTENANCE, next release): shown by its code in the account menu; the permission map still decides the menu; if nothing is allowed, AC-18. U.

**Permission denied**
- **EC-27:** `/unauthorized` for an address the user may not open (AC-36). W.
- **EC-28:** A signed-out visitor to `/unauthorized` goes to `/login`. U.
- **EC-29:** A module the menu shows while the API answers 403 (a disagreement between the two): the plain permission message through `formatApiError`, no raw text (AC-35 exists to prevent the disagreement). W.
- **EC-30:** A write control hidden in the client but called directly (curl): the server refuses (SEC-1). Not a client test; one-line reason.
- **EC-31:** An id that is no module: the existing "not available" page with the way back (AC-31). W.

**Concurrent sessions and edits**
- **EC-32:** Two tabs: sign out in one, and the other takes the expiry path; sign in in one while the other is on `/login`, and the other follows (AC-27, RC-3). U, M.

**Invalid input**

- **EC-43:** A `/api/me` reply with a malformed or unexpected shape: an account error with "Try again"; never a crash and never a partial menu (AC-21). U.

**Lookups**

## 7. Design choices, and the Firebase and library claims to check at step 0

### Design choices (not requirements; each with an alternative)

- **DC-1. The token callback becomes asynchronous.** `ApiClient.tokenProvider` changes from `String? Function()` to a function that may return a `Future`, because a Firebase ID token may need a network refresh at call time (RC-4). The injection interceptor already runs asynchronously, and a sync function remains valid, so the shopper app and the existing tests are unaffected. *Alternative:* keep it synchronous and cache the token from the SDK's token-change stream; passed over because a stale cached token would be sent when the SDK has not yet refreshed. *Better when:* the SDK is shown to refresh proactively and reliably on web and mobile (RC-4).
- **DC-2. One auth port, one session notifier.** A stateless `AuthService` interface wraps `FirebaseAuth` (AC-5); a fake implements it for every widget and unit test; one notifier holds the session states (AC-21). *Alternative:* call `FirebaseAuth.instance` from the view models; passed over because the plugin cannot run in a widget test and every test would need platform channels. *Better when:* never, for this repository's test rules.
- **DC-3. Restore is two steps.** Firebase's own restore of a saved sign-in is awaited before `runApp` (a local operation), and `GET /api/me` loads afterwards behind a loading page, so no sign-in screen flashes and the first frame is not held by the network. *Alternative:* await `/me` too before `runApp`; passed over because a slow or absent API would leave a blank page for up to the connect timeout (10 s). *Better when:* the owner wants no loading page at all.
- **DC-4. First-`/me` failures are told apart by status and by "fresh sign-in", not by text.** 403 means no access; 401 means the account cannot sign in now; 503 or no network means try again (AC-15 to AC-17). *Alternative:* match the server's message strings (`"Account is not active"`); passed over because a reworded server message would silently change the screen.
- **DC-5. `/me` is a sign-in path for the 401 handler.** `ApiClient`'s existing `signInPaths` list names it, so its 401 does not reach the global expiry handler; the session notifier decides (expiry on restore or reload, the AC-16 message on a fresh sign-in). *Alternative:* a per-request flag on the one call; both work, the existing list is the smaller change.
- **DC-6. Gabay stores no session.** Firebase keeps the saved sign-in (RC-3); Gabay keeps only the remembered tenant. *Alternative:* the standard §4.4's session blob in `shared_preferences`; passed over because it duplicates Firebase's state, can disagree with it, and puts an identity on the device that Firebase does not control. Recorded as a difference from §4.4 (G4).
- **DC-7 [r2]. Configuration by `--dart-define-from-file`, not a generated options file.** The five public web config values come from a JSON file passed to the build (AC-2); the file is git-ignored until step 0 confirms the values may be committed (RC-14, the CI secret guard), with a committed placeholder. *Alternative:* a committed `firebase_options.dart` from the FlutterFire tool; passed over because it ties the repository to one project, the local and staging builds would need two files, and the tool is a new dev tool outside the Blueprint's pins. *Better when:* the project is single and fixed and the owner wants no build flag.
- **DC-8. `/` and `/about` need sign-in on the admin surface; About moves into the account menu.** *Alternative:* leave `/` and `/about` public; passed over because the build page carries sample controls and the rule is "nobody reaches an admin screen without signing in". *Better when:* the owner wants the version page readable by anyone.
- **DC-9. The registry's role scope notes go.** The notes ("Buildings and levels only", "Confirm or fix only", "Local days only") described the role table that this slice deletes; the permission map cannot say them. *Alternative:* keep a note table keyed by role code and module; passed over because it is a second role table. The notes can return as ARB text keyed by permission when a slice needs one.
- **DC-10. A user with nothing to open stays signed in on an empty dashboard with "Sign out".** *Alternative:* sign them out with the no-access message of AC-15; passed over because the account is valid and the role may arrive from an admin later without a new sign-in being needed. *Better when:* the owner prefers the same message for every account that cannot do anything.
- **DC-11. After a failed sign-in the email stays and the password is cleared.** *Alternative:* keep both; passed over because a wrong password left in the box helps no one and clearing it is the usual safe default.
- **DC-12. Another tab's sign-out is treated as expiry** (with `from`), not as a manual sign-out, because this tab did not choose it (AC-27). *Alternative:* treat it as manual; passed over because the user would lose their place.
