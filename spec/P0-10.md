## 1. What this spec covers

Optional shopper sign-in, sign-up, sign-out, "Forgot password" and account deletion, built in the retrofit's R10 on the client session that R8 builds:

1. **The shopper account routes** (api-coder): recording a shopper's account after each Firebase sign-in, reading it, and deleting it (the Firebase user and the `ShopperAccount` row together). They are mounted outside `/api/public` (Blueprint Part 1), behind S1's `auth`, which already resolves a UID to an `AppUser` first, then a `ShopperAccount` (Q12 of PH2, built in S1).
2. **Sign-in in the shopper app** (flutter-coder): visible on the Me tab's top row and never forced (D1, Q11); email and password, Google, and Sign in with Apple on every platform (D1b, L109, Q4); "Forgot password" (Q10); linking a second method to the same email (Q8); sign-out; the signed-in state on Me; the privacy notice screen (Q13, a marked placeholder).
3. **Deletion in the app and on the web** (flutter-coder): in the Me tab, and on a public page in the Flutter Web build at its own path, outside the admin shell (Q1).
4. **The seeded shopper** (`shopper@gabay.test`, L119) as the test account, against the Auth emulator.

## 2. Settled context

- **D1 (ruled 2026-09-25):** anonymous use is complete. The sign-in is in the MVP, never forced and never hidden. Deletion ships with the login, in the app (Apple 5.1.1) and on the web (Google Play). Shopper identity is kept apart from admin identity, in its own table and on its own routes outside the GET-only public router. Signing in never attaches a position to an account (invariant 4).
- **D1b (L109):** the methods are email and password, Google, and Sign in with Apple, all through Firebase Auth. Apple satisfies Guideline 4.8 next to Google. There is no SMS and no Facebook.
- **Firebase Auth (L98, E-08):** Firebase holds credentials, refresh and brute-force protection. Per PRD §6.13 the app never handles a password itself, so the password goes only to the Firebase Auth SDK. The API verifies every ID token with `firebase-admin`, checking revocation (`firebaseVerifier.js`). Firebase Auth processes sign-in data in the United States. Account data sits in Singapore. The privacy notice names both places (PRD §7, L116).
- **Built in S1 (on main):**
  - `identityStore.findByFirebaseUid` returns `{kind: 'admin', …}` when the UID is in `AppUser`. Otherwise it returns `{kind: 'shopper', shopperAccountId, email, displayName}` when the UID is in `ShopperAccount`, or `null`.
  - `auth` gives 401 for a missing or bad header, a bad, expired or revoked token, a sign-in older than `auth.idTokenMaxAgeS` (default 28,800 s, measured from `auth_time`) or an inactive `AppUser`. It gives 403 "This account has no access" for a valid identity with no Gabay account, and 503 when Firebase or the database cannot be reached.
  - A shopper has no actor (`runWithActor(null)`). `requireAdminUser` refuses a shopper with 403 on admin routes, and `/api/me` is admin only.
  - The comment on `identityStore` records "AppUser wins" as a design choice for the product owner to rule. It is now ruled (Q7, below): AppUser wins. `DeletionRequestedAt` is not read there: it is "the shopper sign-in and deletion path of P0-10".
- **`ShopperAccount` (schema 0.14; Blueprint §3.8, DC5):**
  - It is platform scoped, with no `TenantId`, because one shopper uses many malls.
  - Columns: `FirebaseUid` (unique), `Email` (VARCHAR(254), nullable, unique where present), `EmailVerifiedAt`, `AuthProvider` (VARCHAR(20): `password`, `google.com`, `apple.com`), `DisplayName` (VARCHAR(120), nullable), `DeletionRequestedAt` ("Apple / Google Play deletion paths; the Firebase user is deleted with the row"), `CreatedAt` and `UpdatedAt`.
  - It has no audit columns (Part 3: "self-created by the shopper").
  - It never holds a position, a route or a parked spot.
- **`AuditLog` (schema 0.14):** `TenantId`, `UserId`, `ActingAsTenantId`, `IPAddress`, `EntityName`, `EntityId` and `PayloadDiff` are nullable; `Method`, `Route`, `StatusCode`, `RequestId` and `CreatedAt` are required. Q14's ruling fits these columns with no schema change.
- **What stays on the phone (L88, L99):** favourites, recent destinations, settings, the parked car and venue packages stay on the phone and are never tied to an account.
- **E-19 (reserved, L149 Q10):** `firebase_core` and `firebase_auth` are requested when R8 (was S10) starts, with versions read from pub.dev then. Google and Apple sign-in use `firebase_auth`'s own provider sign-in, with no package beyond E-19 (Q3, ruled; the API is RECALLED, §12, and checked in the plan).
- **E-20 (L153), still in force during R10** (it closes at R13):
  - Localhost only, with no deploy of any kind ("no Firebase project, no Hosting, no Function, no preview channel"). Test data is throwaway.
  - Sign-in runs against the Auth emulator (project `demo-gabay`), so real Google and Apple sign-in cannot be exercised here. They are checked at the first deploy (Q2, ruled).
  - Items 3, 4 and 9 of §5 may be waived only to a later R-slice.
- **The Me tab today:** P0-04 r2 puts "Change mall" above FF-SK's placeholder, and P0-14 (FF-7) adds the "For everyone" settings. R10 adds the account as the Me tab's top row (Q11, ruled).
- **Wording (A2, §M ruling 3, L109):** P0-14 (FF-7) comes before R10, so every new phrase gets both English and Tagalog in ARB. flutter-coder drafts the Tagalog, each line marked draft. The product owner corrects and approves every line through FF-7's review sheet (key, English, Tagalog, where it shows, Tagalog screenshots) in R10's pull request; only approved lines merge, and the approval goes in R10's L-row. G2 applies in full here, with no waiver.
- **The owner is the DPO (L116).** The privacy notice text (N1) and the DPO contact (N2) are marked placeholders in R10, replaced before the first deploy and reviewed by counsel; a retrofit-ledger row tracks them (§M ruling 1).
- **Session length (§M ruling 2, L151):** a shopper stays signed in for 30 days (`auth.shopperIdTokenMaxAgeS` = 2,592,000, a setting). Admins stay at 8 hours (`auth.idTokenMaxAgeS` = 28,800).
- **Scale (A5):** account volumes are measured at the pilot; nothing is set before (Q17, ruled).

## 3. Acceptance criteria

### A. The shopper account routes (api-coder)

- **AC-1:** A request from a verified Firebase identity with no `AppUser` row, sent to the route that records an account, creates exactly one `ShopperAccount` row when none exists for its UID. The row holds the Firebase UID, plus, from the Firebase user, its email, email-verified time (AC-39), provider and display name where the Firebase user has them. The provider is the method of this sign-in (`password`, `google.com` or `apple.com`). The app calls this route at every sign-in (Q12). A repeat call for the same UID creates no second row and refreshes `Email`, `EmailVerifiedAt`, `DisplayName` and `AuthProvider` from the Firebase user, setting `UpdatedAt`. No name is asked from the shopper: `DisplayName` comes only from Google or Apple. A display name longer than 120 characters is stored cut to its first 120 characters. An email longer than 254 characters is refused with 400 in the standard error shape, nothing is written, and the app shows a plain ARB sentence, ends the session on this phone and is back in the signed-out state; the Firebase user left without a row is handled by hand through the DPO contact (N2) (R11 (iii)). Verify: API (Auth emulator token; rows inside a rolled-back transaction; a second call after the emulator user's name and email change shows the new values; a 121-character name and a 255-character email).
- **AC-2:** Two record requests for the same new UID at the same moment leave one row and both answer success (`UQ_ShopperAccount_FirebaseUid`). Verify: API (concurrent requests).
- **AC-3:** The route that reads the account returns only the caller's own account, as an allow-listed field set named in the plan, which never includes the Firebase UID. No path, query or body value selects the account: it is always the token's. A request naming another shopper's id gets the caller's own account or a 4xx, never the other shopper's. Verify: API (asserts the exact key set; two seeded shoppers).
- **AC-4:** The deletion route, called by a signed-in shopper, deletes that shopper's Firebase user and `ShopperAccount` row, at once, in one request, with no second sign-in (Q5). After success, the shopper's earlier ID token gets 401 on every route, and the UID resolves to nothing. Verify: integration (Functions and Auth emulators, local database).
- **AC-5:** The deletion route works in this order (Q5): set `DeletionRequestedAt` on the row, delete the Firebase user through the Admin SDK, then delete the row.
  - (a) If setting `DeletionRequestedAt` or deleting the Firebase user fails, it answers 503 in the standard error shape, the Firebase user and the row are still there (the row may keep `DeletionRequestedAt` set) and the account keeps working. A retry by the same shopper completes the deletion.
  - (b) If deleting the row fails after the Firebase user was deleted, it answers 503 and never reports success. The row is left with `DeletionRequestedAt` set and cannot be used, because every token for that UID now gets 401 (EC-6). It is removed later as EC-6 says. The shopper's retry gets 401 and the phone signs out (AC-23).
  - Verify: API (fake admin SDK and fake database, each failing at each step; the row's state asserted after each).
- **AC-6:** On every shopper account route: with no or a malformed `Authorization` header, 401; with a bad, expired or revoked token, 401; with a sign-in older than `auth.shopperIdTokenMaxAgeS` (default 2,592,000 s, 30 days, measured from `auth_time`), 401; with Firebase or the database unreachable, 503 and nothing written (fail closed). The shopper limit applies to shopper identities and to the not-yet-recorded identity on the record route. `AppUser` identities keep `auth.idTokenMaxAgeS` (28,800 s) on every route (L151). Verify: API (a shopper token aged 9 hours is accepted; one aged past 30 days gets 401; an admin token aged 9 hours still gets 401 on admin routes).
- **AC-7:** A token whose UID is an `AppUser` gets 403 with the message "This is a staff account. Use a shopper account here." (an error code the app maps to ARB, AC-43) on every shopper account route, for each seeded role (SUPERADMIN, MALL_ADMIN, VENUE_EDITOR, VIEWER). No `ShopperAccount` row is created for it. The `AppUser` identity wins (Q7). Verify: API.
- **AC-8:** A shopper token on `/api/me` and on every admin feature route gets 403 "This account has no access" (S1's `requireAdminUser`, re-asserted over the routes R1–R6 fitted). Verify: API.
- **AC-9:** The shopper account routes are mounted outside `/api/public`. `/api/public/*` stays GET only and still ignores `Authorization` (P0-04 AC-7 and AC-8 still pass). Verify: API.
- **AC-10:** The shopper account queries read and write only `ShopperAccount` (and, through R3, `AuditLog` as AC-41 says), with no tenant predicate (platform scope, DC5) and every value bound. `X-Tenant-Id` changes nothing. `tenant-predicate` and `sql-interpolation` pass. Verify: unit (the linters in `npm run verify`) and API (with and without the header).
- **AC-11:** The request bodies are validated with an allow-list (R5's zod). No request or response of these routes carries a password, a position, a route, a parked spot, favourites or recents (invariant 4; PRD §6.13). Verify: API (an extra `password` or position field is refused or ignored and never stored) and the review privacy pass.

### B. Sign-in in the shopper app (flutter-coder)

- **AC-12:** Signed out, the shopper reaches every feature of PRD §6.4–§6.10 that is built (the map, mall picker, delivery, search, routing, step-free routing, "Where are you?", the out-of-venue state, the live dot and the guided walk), and nothing in them asks the shopper to sign in. Verify: widget (the app booted with no session through each tab and a route) and review.
- **AC-13:** The account is the Me tab's top row, in the place of the demo's identity row (Q11). Signed out, the row reads "Sign in or create an account" and opens the sign-in screen; it is always visible while signed out. Signed in, it shows the account (AC-21) with "Sign out" and "Delete account" below it. No prompt to sign in appears anywhere outside the Me tab, ever. Verify: widget.
- **AC-14:** Sign-in offers email and password, Google, and Sign in with Apple, on Android, on iOS and on the web deletion page alike (Q4), and nothing else (no phone or SMS, no Facebook). Verify: widget (each platform's build of the sign-in screen).
- **AC-15:** Sign-up with an email and password creates the Firebase user, sends Firebase's verification email (AC-39), then records the account (AC-1). Me shows the signed-in state with the email only after the account is recorded. Verify: widget (fake auth and API) and integration (Auth emulator).
- **AC-16:** Sign-in with an email and password signs in an existing account. A wrong password, an unknown email, a malformed email or a password Firebase refuses is shown as a plain sentence from ARB, never Firebase's or dio's raw text (standard §4.3, `formatApiError` and `sanitizeErrorText`). Verify: widget (each Firebase error code mapped).
- **AC-17:** Google and Apple sign-in complete through Firebase Auth's own provider sign-in (Q3) against the Auth emulator and record the account with `AuthProvider` `google.com` or `apple.com`. In R10 they are proven against the Auth emulator's provider flow only. A "real providers" check (Google on Android, Apple on iOS and the web) is written into `docs/ops/DEPLOYMENT_RUNBOOK.md` for the first deploy, and P0-10 stays `IN PROGRESS` in FEATURE_PIPELINE until it passes (Q2). Verify: manual (the emulator's provider flow on the Android emulator, output and screenshots pasted), widget (fake auth), and review (the runbook row and the pipeline note exist).
- **AC-18:** The password is handed only to the Firebase Auth SDK. It is never in a request to Gabay's API, never written to the phone's storage (`shared_preferences` or files) and never logged. Verify: unit (a recording fake `ApiClient` and a fake preferences store), review.
- **AC-19:** A shopper who closes a sign-in or the Google or Apple sheet without finishing is back where they started, signed out, with no error dialog. Verify: widget.
- **AC-20:** A sign-in survives an app restart until it ends: on sign-out, on deletion, on a 401 from Gabay's API, or at the 30-day limit (`auth.shopperIdTokenMaxAgeS`, AC-6). After the limit, the next request to a shopper account route gets 401 and the phone signs out (AC-23). Verify: widget (fake persisted session; a fake API answering 401 after the limit) and manual (restart on the emulator).
- **AC-21:** Signed in, Me shows the account: its email, or, where the account has no email (for example an Apple sign-in that shared none), the method of the latest sign-in (`AuthProvider`, refreshed at every sign-in, AC-1). It never shows the UID. Verify: widget.
- **AC-22:** Sign-out on Me ends the session on this phone and Me returns to the signed-out state. Favourites, recents, settings, the parked car, the held packages and an active trip are unchanged (L88, L99). Verify: widget.
- **AC-23:** A 401 from a shopper account route signs the shopper out on this phone. Me shows the signed-out state, the app keeps working anonymously, and no blocking dialog appears (PH2 Q5: a 401 ends the session). Verify: widget (fake API).
- **AC-24:** Signing in, signing out, linking a method and deleting the account never end an active trip, change the shown mall or start a package check or swap. Verify: widget.
- **AC-25:** With no connection, the sign-in, sign-up, "Forgot password" and linking actions say a connection is needed and make no call. A shopper who is already signed in stays shown as signed in. Verify: widget.
- **AC-26:** The privacy notice is an in-app screen (ARB, English and Tagalog), linked from sign-up before the account is created and from Me, and shown on the web deletion page (Q13). In R10 its text is a placeholder (N1, §M ruling 1): the screen says visibly that it is a placeholder notice, and it names Singapore for account data and Firebase Auth's processing in the United States (PRD §7, L116). There is no age gate. The real text, approved by the product owner as DPO and reviewed by counsel, replaces it before the first deploy, tracked by a retrofit-ledger row (PH4 §7). Verify: widget (the link on sign-up and Me; the placeholder mark; both place names) and review (the ledger row).
- **AC-27:** Every new phrase is in `app_en.arb` and `app_tl.arb` (the untranslated-phrase test passes). The Tagalog is drafted by flutter-coder, marked draft, and merged only after the product owner approves each line through FF-7's review sheet with Tagalog screenshots in R10's pull request; the approval is recorded in R10's L-row (G2, A2, §M ruling 3, L109). Every new control has a screen-reader name. Nothing overflows at text ×1.4 on a 320 dp wide phone. Verify: widget, the ARB test, and review (the signed review sheet).
- **AC-28:** Every colour comes from `gabay_tokens.dart` through the theme, in light and dark (rule 6). Verify: the `colour-literals` lint, and screenshots (light and dark, phone and tablet).
- **AC-29:** The email field is a `FieldSpec` bound to `ShopperAccount.Email` (its 254-character limit comes from the column). The password field follows the pattern R8's plan rules for the admin sign-in form's password field (Q16); if that ruling is not recorded when R10's plan is written, the plan stops and asks. There is no bare `TextField` or `TextFormField`. Verify: `no-bare-textfield` and `schema-forms`.

### C. Deletion in the app and on the web

- **AC-30:** Signed in, Me offers "Delete account". It opens a confirmation dialog, with Cancel as the default (standard §4.6), that says what is deleted: the sign-in and Gabay's account record. Confirming with a connection deletes the account (AC-4), signs the phone out and shows on Me that the account was deleted. The confirmation dialog is the only step: there is no second sign-in before deletion (Q5). Verify: widget (fake auth and API) and integration (emulators).
- **AC-31:** Deleting the account leaves the phone's favourites, recents, settings, parked car and held packages as they were (L88, L99; Blueprint §3.8 keeps them out of the account). Verify: widget.
- **AC-32:** With no connection, or with a response that is not the API's (a captive portal's page, a redirect, an HTML body), deletion makes no change and says a connection is needed. The shopper stays signed in. Verify: widget (fake responses, as P0-04 AC-21).
- **AC-33:** When deletion fails with 503 (AC-5), the shopper stays signed in and sees that the account was not deleted, with Retry. If the retry gets 401 (AC-5 (b)), the phone signs out as AC-23 says. Verify: widget.
- **AC-34:** A public web page in the Flutter Web build, at its own path outside the admin shell, with no admin menu and no development banner (Q1), lets a shopper sign in with the method they used (any of the three, AC-14) and delete their account, with the same confirmation (AC-30) and the same effect as AC-4. It links the privacy notice (AC-26) and carries a line naming the DPO's contact for anyone who can no longer sign in. In R10 that contact is a placeholder (N2, §M ruling 1), visibly marked as one and replaced before the first deploy, tracked by the same retrofit-ledger row as AC-26. On localhost it is reached in a browser on this machine. The page's path is the plan's to set. Its language follows the browser's language (Tagalog or Filipino gives Tagalog, anything else English), with a language switch on the page; its phrases are shopper phrases with Tagalog, reviewed under A2 as AC-27 says (R12). Verify: widget (web build; a browser language of `tl`, of `fil` and of `en-US`; the switch) and manual (localhost, emulators, screenshots in both languages).
- **AC-35:** Signing in on the deletion page grants nothing else: from it, no admin route or admin screen is reachable with a shopper identity. A staff identity there gets AC-43's refusal. Verify: API and widget (web).

### D. Seeds and settings

- **AC-36:** The seeded `shopper@gabay.test` (password from `.env` `SEED_PW_SHOPPER`) signs in on the app against the Auth emulator and Me shows it signed in. After a deletion test, `npm run seed` restores it (the seed's delete-then-insert path). Verify: manual (pasted) and the seed's own test.
- **AC-37:** `auth.shopperIdTokenMaxAgeS` is a `GlobalSetting` with its default 2,592,000 seeded and listed in Blueprint invariant 16's registry. A value that is not a positive number is ignored and the default is used, as with `auth.idTokenMaxAgeS`. It is read by the API only; it is not sent in the public mall list, because the phone learns the limit from the 401 (AC-20). Q5's ruling brings no setting. Verify: unit.

### E. Added in r2 by the 2026-10-12 rulings

- **AC-38:** The sign-in screen offers "Forgot password". It sends Firebase's password-reset email to the typed email and shows a plain ARB sentence; Firebase's errors (malformed email, unknown email) are mapped to ARB as AC-16's are, never raw text. On localhost the reset link appears in the Auth emulator. Gabay's API is not called and no password reaches it (AC-18). Verify: widget (fake auth; each error code mapped) and integration (Auth emulator).
- **AC-39:** Sign-up with an email and password sends Firebase's verification email (Q9). Nothing is blocked while the email is unverified: the account is recorded and works as any other. `EmailVerifiedAt` is set by the first record call (AC-1, at a sign-in) that finds the Firebase user's email verified, and holds the time Gabay saw it, since Firebase keeps no verification time (RECALLED, §12). Google and Apple sign-ins record the verified state the provider gives. On localhost the verification link appears in the Auth emulator. Verify: widget (fake auth) and integration (emulator: sign up, follow the link, sign in again, `EmailVerifiedAt` set).
- **AC-40:** One account per email (Q8). When a shopper signs in with a method other than the one their email signed up with, the app says "You signed up with ⟨method⟩. Sign in with it first." in ARB words, with ⟨method⟩ named. After they sign in with that method, the app offers to link the new method; accepting links it to the same Firebase user, so either method then signs in to the same `ShopperAccount` row. Declining leaves the account as it was. No second row is created for the email. Verify: integration (Auth emulator: password then Google with the same email) and widget (fake auth: the message, the offer, accept and decline).
- **AC-41:** The audit row R3 writes for a shopper account route's POST, PUT or DELETE keeps the route, method, status and time only, with the request id the table requires: `TenantId`, `UserId`, `ActingAsTenantId`, `IPAddress`, `EntityName`, `EntityId` and `PayloadDiff` are NULL, and no column holds the email, the Firebase UID or the `ShopperAccountId` (Q14). A deletion therefore leaves proof that one happened, but no personal data. Logs never print the shopper's email. Verify: API (the audit row of a record and of a deletion asserted column by column) and review (log statements).
- **AC-42:** Every shopper account route runs `auth → requireShopperUser → validate → handler` (Q15). R7's `route-guard-order` lint knows this as a third mount kind beside public and admin, and fails a shopper route that skips or reorders a step. The record route accepts exactly the verified identity with no account (§10). Shopper routes have no `PermissionRoute` or menu rows. Verify: unit (the lint's own tests, with a passing and a failing shopper route) and API.
- **AC-43:** A staff identity (an `AppUser`'s credentials) used to sign in on the shopper app or the deletion page gets AC-7's refusal: the app shows "This is a staff account. Use a shopper account here." in ARB words, ends the session on this phone or page, and is back in the signed-out state (Q7: staff use the shopper app signed out or with a separate shopper account). Verify: widget (fake API answering AC-7's 403) and API (AC-7).
- **AC-44:** R10 adds no client package beyond E-19's `firebase_core` and `firebase_auth`: Google and Apple go through `firebase_auth`'s own provider sign-in (Q3; the API is RECALLED and checked in the plan). Verify: review (`app/pubspec.yaml` diff; no EXCEPTIONS entry added for P0-10).

## 4. Edge cases

Each gets a test or a one-line reason why not (G1).

| # | Case | Expected | Verify |
|---|---|---|---|
| EC-1 | Offline: sign-in, sign-up, "Forgot password", linking or deletion tried | AC-25, AC-32: no call, no change, "needs a connection" | widget |
| EC-2 | Stale or missing venue package while signing in | No effect: accounts never touch delivery (AC-24) | widget |
| EC-3 | Captive portal during record or deletion | Treated as offline. Not recorded or not deleted, and the next try repeats it (AC-32) | unit, widget |
| EC-4 | First sign-in races itself (two record calls, or two phones at once) | One row (AC-2) | API |
| EC-5 | Firebase user created but the record call failed (database down, app killed) | The next sign-in records the account (AC-1). Until then Me does not show the signed-in state (AC-15), and Gabay's API gives 403 "no access" on account routes other than recording | API, widget |
| EC-6 | Row exists with `DeletionRequestedAt` set but its Firebase user is gone (AC-5 (b)) | Tokens for that UID are refused (`auth/user-not-found` → 401), so no one can use the row. It is removed by a later sign-up with that email (EC-7) and by the sweep at the first scheduled-function slice, which removes only rows whose `DeletionRequestedAt` is set and whose Firebase user no longer exists (Q5). ## 10. Design notes for the plan (not requirements)

- The routes' paths and response shapes, and the web deletion page's path, are the plan's to set, under `/api/` outside `/api/public` (Blueprint Part 1), each shown to the product owner with the plan.
- S1's `auth` refuses a valid identity with no account (403). The record route (AC-1) must accept exactly that case and nothing broader. The plan names how: a narrower middleware for that one route, or a flag on `auth`. DESIGN CHOICE; the alternative is to create the row inside `auth` on the first request, which would make every route a writer.
- S1's `auth` checks the sign-in age before it knows the identity's kind. AC-6 needs the limit chosen by kind, so the check moves after resolution or reads both settings. Any existing S1 test this changes is named in the plan with its reason (C1).

**Q19 [spec-writer] Rows and Firebase users left behind (raised by the Q5 and Q12 rulings).** Three cases the rulings do not reach.
**Ruled 2026-10-12 (residual sheet R11): (a) in each case.** (i) "removed by the next deletion call" is dropped; a leftover is removed by a new sign-up with the same email or by the sweep. (ii) A sign-up matching an old row with no deletion mark: confirm through the Admin SDK that the old Firebase user is gone, then remove the row. (iii) A provider email over 254 characters: sign out and handle it by hand through the DPO contact. Applied in AC-1, EC-6, EC-7, EC-10, EC-38, §8 item 1.
- **(i) "Removed by the next deletion call" (Q5 (a)).** The deleted shopper's own token gets 401 from S1's `auth` before any handler runs, so that shopper can never make the next deletion call. The words can only mean someone else's call, or be dropped.
  - (a) **Recommended:** drop it. A leftover row is removed by a sign-up with that email (EC-7) and by the sweep at the first scheduled-function slice. Each deletion call touches only the caller's own row (AC-3's rule).
  - (b) Any shopper's later deletion call also removes leftover rows (`DeletionRequestedAt` set, Firebase user gone), checked through the Admin SDK. Cleans up sooner; one shopper's request then deletes another's row.
- **(ii) A sign-up whose email matches a row with no `DeletionRequestedAt`** (its Firebase user removed outside Gabay, for example by hand in the emulator UI or the Firebase console). `UX_ShopperAccount_Email` refuses the new row.
  - (a) **Recommended:** the record route asks the Admin SDK whether the old row's Firebase user still exists; if not, it removes the old row and inserts the new one, as for a leftover. If it does exist, Q8's one-account-per-email rule already stops the sign-up in Firebase (RECALLED), so this cannot be reached.
  - (b) Refuse the record with a plain message; the DPO removes the old row by hand.
- **(iii) A provider-given email over 254 characters** (AC-1 refuses it). The Firebase user exists but has no row, and the deletion route needs a row, so Gabay cannot delete it. The password sign-up form already refuses such an email before Firebase is called (AC-29).
  - (a) **Recommended:** the app ends the session on this phone and shows the plain message; the leftover Firebase user is removed by hand through the DPO contact (N2). Providers' emails over 254 characters should not occur (RECALLED: the email standards cap an address at 254).
  - (b) The record route also deletes that Firebase user through the Admin SDK before answering.

## 12. RECALLED claims (each checked against its docs before it carries weight in the plan)

- `firebase_auth` signs in with Google and Apple through `signInWithProvider` on Android and iOS, and through a popup or redirect on the web, with no extra package (Q3, AC-44).
- The Auth emulator offers a fake sign-in page for federated providers (Google, Apple), usable from the Android emulator and a browser (AC-17, §5).
- Firebase's default "one account per email address" refuses a second method with the same email (`account-exists-with-different-credential`) until the methods are linked, and `firebase_auth` links a credential or provider to the signed-in user (AC-40).
- Apple shares the email only at the first sign-in, and may give a private relay address (EC-9).
- After a user is deleted, another phone's Firebase session ends at its next token refresh (EC-17), and the Admin SDK's revocation-checking verification of that user's token fails with `auth/user-not-found` (AC-5 (b), EC-6).
- Google Play's account-deletion requirement asks for a web URL in the Play Console where users can request deletion, and allows a request form (Q1). Its wording was cited in plan.html D1, not re-read this session.
- Firebase's email and password sign-up enforces a minimum password length unless a password policy is set (EC-11).
- The Auth emulator's host must be reachable from a phone over USB or Wi-Fi, as the Functions emulator is (P0-04 §5's RECALLED items apply).
- Firebase sends its own password-reset and verification emails (`sendPasswordResetEmail`, `sendEmailVerification`), and the Auth emulator shows their links instead of sending mail (AC-38, AC-39, §5).
- The Firebase user record has an email-verified flag but no verification time (AC-39).
- The ID token carries the sign-in method (`firebase.sign_in_provider`), from which the record route sets `AuthProvider` (AC-1).
- An email address is at most 254 characters under the email standards (Q19 (iii)).
- The Admin SDK's user lookup by UID reports a user that no longer exists as `auth/user-not-found`, which the record route reads to confirm an old row's Firebase user is gone (R11 (ii), EC-7).
- A Flutter Web build can read the browser's preferred languages at start-up (for example through `PlatformDispatcher.locales`), and `tl` or `fil` arrives as a language code a browser may send (R12, AC-34).
