## 2. Definitions

P0-06 r2 §2's terms apply (metre cost, real metres, leg, shortcut edge, passage, behind a passage, way, venue frame, estimate). Added:

- **Step-free mode:** the shopper's saved "wheelchair route" option. On or off; off by default (PRD §6.4 lists it with the saved settings; the demo starts off).
- **Width setting:** `routing.stepFreeMinWidthM`, default 1.2 m (L88; `plan/FF-3-publish-engine.md` §4.4). A `routing.*` key, so publish resolves it for the venue's tenant and writes it into the package (ruling A3, confirmed by A6; P0-03 AC-72).
- **Clearance:** the width in metres publish stores on an edge (P0-03 AC-30, AC-42): from the walkable geometry, and for an edge through a door the smaller of that and `Opening.ClearWidthM`; where the door is unmeasured (NULL), the geometry figure (P0-03 AC-23 warns).
- **Width-checked edge (B12):** every edge that is not a connector edge: walk edges, edges through a door, and the floor edges across a store (passage and shortcut alike). Connector edges are not width-checked: they carry no width data, and their type decides (B10).
- **Step-free connector (B10):** a connector whose type is marked step-free (`ConnectorType.IsStepFree` TRUE) **and** whose type's `CostModel` is neither `STAIRS` nor `ESCALATOR`. So `ELEVATOR`, `RAMP` and a mall's own `LEVEL` types pass when marked step-free; a type not marked step-free never passes, whatever its model; a stairs- or escalator-model type never passes, even if marked. There is no gradient check: marking a ramp type step-free is the mall's statement that it meets 1:20 (B11; BP 344).
- **Step-free filter:** the edge predicate applied when step-free mode is on:
  - a connector edge passes only if its connector is a step-free connector (B10, B11);
  - a width-checked edge passes only if its clearance is at least the width setting (B12);
  - a shortcut edge never passes; a passage's store-crossing edges pass on trips to or from the places it serves, under P0-06 AC-24's rules (L92), and are width-checked like any other (B12);
  - the start edge is exempt: the filter applies from its end nodes onward (B13; AC-15);
  - everything P0-06 already bans (one-way against direction, evacuation-only connectors, a closed store) stays banned.
- **Step-free way:** a way every edge of which passes the step-free filter.
- **Restroom set:** the amenity types of the "Restroom" row of P0-05's closed chip table in the constants file, `CR` and `CR_PWD` (B2, PRD §6.5 as authority).
- **Accessible restroom:** an amenity of the restroom set whose `AmenityType.IsAccessible` is TRUE (seeded today: `CR_PWD`, "Accessible restroom").

## 3. What the engine reads from the package (requirements on P0-03)

All of it is already in P0-03 r2's allow-list (§3.7). P0-07 adds no package content: no gradient check (B11) and no connector width (B12) means no new data.

1. Per edge: kind, connector id or store unit id, and clearance (P0-03 AC-42).
2. Per connector: its type's `CostModel` and step-free flag (P0-03 §3.7, "connectors: type, …, cost model, step-free flag"), its one-way flag, and its ends or stops.
3. Per amenity: its type and the type's accessible flag (P0-03 §3.7, "amenities with type, synonyms and accessible flag").
4. The passages and the places each serves (P0-03 AC-39).
5. `routing.stepFreeMinWidthM`, resolved at publish (P0-03 AC-72).

## 4. Acceptance criteria

### 4.1 The filter (engine)

AC-1: With step-free mode on, no way (the lead or the other) uses a stairs or escalator connector, in either direction, whatever the connector type's flag (L88, PRD §6.7, B10). Verify: unit (vector V-SF-1: the least-cost way takes an escalator; with step-free on, the lift way is returned. V-SF-2: a level reached only by stairs: no step-free way).

AC-2: With step-free mode on, a connector edge is used only if its connector is a step-free connector (§2; B10): its type is marked step-free and its cost model is neither `STAIRS` nor `ESCALATOR`. No ramp gradient is checked (B11). Verify: unit (vector V-SF-7: an `ELEVATOR` type and a `RAMP` type marked step-free are used; a `LEVEL` type marked step-free is used; an `ELEVATOR` type marked not step-free is refused; an `ESCALATOR` type and a `STAIRS` type each marked step-free are refused; a `RAMP` marked step-free whose rise over the distance between its ends is steeper than 1:20 is used).

AC-3: Step-free connectors are ranked by metre cost like any edge (L86, P0-06 AC-1). A one-way ramp or lift pair is used only in its direction (L86, P0-06 AC-4). Verify: unit (vector V-SF-4: a lift and a ramp to the same level, the cheaper chosen; a one-way ramp against direction refused).

AC-4: With step-free mode on, no way uses a width-checked edge (§2; B12) whose clearance is under the width setting: walk edges, edges through a door, and the floor edges across a store. An edge whose clearance equals the setting passes ("narrower than 1.2 m" is avoided, L88; the demo's `e.w < 1.2`). Connector edges are not width-checked; their type decides (AC-2). Verify: unit (vector V-SF-3: a corridor of clearance 1.199 m refused and one of 1.200 m used; a door with `ClearWidthM` 0.9 on an otherwise wide corridor refused. Vector V-SF-8: a passage whose doors are wide and whose floor edge has clearance 1.0 m gives no step-free way to the place behind it; a lift has no clearance and is used).

AC-5: The width setting comes only from the open package's `routing.stepFreeMinWidthM` (ruling A3, confirmed by A6). Its platform default is 1.2, a seeded platform `GlobalSetting` row, as P0-06 AC-18 seeds `routing.stairsSaveM`. Verify: unit (fixture packages with 1.2 and 1.5 each apply their own value); seed test (the platform row exists); the resolution at publish is P0-03's test (AC-72).

AC-6: With step-free mode on, no shortcut edge is used, whatever the "Shortcuts through stores" option (L92, PRD §6.7, Blueprint §4.2). Verify: unit (V-RG2-5's layout with wide clearances, shortcuts allowed, step-free on: 18 m by the corridor, not 11.5 m through the store).

AC-7: With step-free mode on, a routable passage is used on trips to or from the places it serves, as P0-06 AC-24 rules. Every edge of the crossing, its doors and its floor, is width-checked like any other (L92: "its doors are held to the same 1.2 m"; B12 for the floor). If every passage to a place has an edge under the setting, the place has no step-free way. Where two passages serve a place (P0-03 D10), a passage whose edges are all wide enough is used when the other's are not. Verify: unit (vectors V-SF-5a passage with wide doors and floor used; V-SF-5b passage door 0.9 m: no step-free way; V-SF-5c two passages, one narrow; V-SF-8 for the floor).

AC-8: A closed passage is never crossed with step-free mode on either (ruling E11). The shopper sees P0-06's own reason, "⟨store⟩ is closed and it is the only way in" (P0-06 AC-24; r3 for the two wordings E11 leaves, B14 via AC-14), with no "Turn off wheelchair route": the second search finds no way either. Verify: unit (vector V-SF-10b: closed passage, step-free on; the result is P0-06's reason, not "no step-free way").

AC-9: With step-free mode on, the stairs rule (P0-06 AC-16, AC-17) is not applied and "Prefer stairs" has no effect: no step-free way can take stairs (PRD §6.6: "Wheelchair routes … are unchanged"). The lead way is labelled "Shortest (N m)" (P0-06 AC-15, ruling E12). Verify: unit (step-free on with "Prefer stairs" on: the same result as with it off).

AC-10: With step-free mode on, the other way follows P0-06 AC-12 to AC-14 under the same filter, so it is also a step-free way (PRD §6.7: "no route uses stairs or escalators"; the demo computes its alternatives with the same options). Verify: unit (vector V-SF-6: two lifts, the lead via Lift A, the other way "via Lift B"; and a case where the only other way takes an escalator, so none is offered and the sheet says "There is no other way to get there.").

AC-11: Under the filter, A* returns the reference Dijkstra's cost on the same filtered graph within 0.001 m on every step-free vector (P0-06 AC-1, AC-7). The estimate uses the coefficients P0-06 AC-36 derives at load over all the package's edges. These remain a consistent lower bound on any subset of edges, so the filter needs no re-derivation (P0-06 §8; §7 DC-2). The start-edge exemption (AC-15) adds no edge to the graph, so the bound still holds. Verify: unit (`heuristic_test`: consistency checked on the edges that pass the filter in every step-free vector).

AC-12: The step-free vectors (V-SF-1 to V-SF-10) are in P0-06's shared, language-neutral vector file (P0-06 AC-32, DC-7), each with its edges' clearances, its connectors' types, cost models and flags, the step-free option, the expected cost and, where unique, the path; the no-route vectors carry the expected result kind. `npm run verify` runs them (invariant 6). The same query on the same package always gives the same way (P0-06 AC-11). Verify: unit (the vector runner; a broken step-free vector fails verify).

AC-13: With step-free mode on, when no step-free way exists, the result carries no way, no points and no legs: a stepped route is never returned or shown in its place (PRD §6.7: "never shows a stepped route on its own"). Its reason follows AC-14. Verify: unit (the result shape on V-SF-2, and on V-SF-10a to V-SF-10c).

AC-14: When step-free mode is on and the search finds no step-free way, the same search runs again with step-free mode off (same origin, destination and other options), silently: its way is never shown, drawn or returned (B14).
- If that search finds a way, the result is "no step-free way" and the route view shows the AC-20 state, with "Turn off wheelchair route".
- If it finds none, the result is P0-06's own no-route reason (unreachable from here; can't start from here; not open; "⟨store⟩ is closed and it is the only way in", and the two wordings P0-06 r3 adds by mirroring E11's sentence), shown as P0-06 AC-31 shows it, with no "Turn off wheelchair route".

Verify: unit (vectors V-SF-10a: a place reachable only by escalator gives "no step-free way"; V-SF-10b: a place behind a closed passage gives E11's reason; V-SF-10c: a place unreachable even with step-free off gives "unreachable from here"); widget (each of the three shows its wording, and only the first shows "Turn off wheelchair route").

AC-15: The start edge is exempt from the filter (B13): when the origin snaps (P0-06 AC-8, AC-9) onto an edge the filter would refuse (narrower than the setting, or a store-crossing edge inside a walk-through store), the route leaves along that edge as P0-06 rules, and the filter applies from its end nodes onward. Verify: unit (vector V-SF-9a: origin on a 0.9 m corridor that opens onto wide ones: a step-free way is returned; V-SF-9b: origin on a floor edge inside a walk-through store: the way leaves by its doors, which are width-checked; V-SF-9c: origin on a narrow start edge leading only to other narrow edges: "no step-free way" per AC-14).

AC-16: The step-free filter is one predicate in `lib/core/routing/`, used by the route search, the other-way search and P0-05's whole-graph distance search (PRD §6.5: "honouring step-free mode"; Blueprint §4.7, DC12). ## 5. Scale targets

- **Graph size:** up to about 20,000 nodes per venue, venues up to about 100,000 m² (PRD §7, "Scale"). The step-free vectors run with P0-06 AC-34's batch: random pairs on the published Aurora seed and on the generated 20,000-node graph, with step-free on, all equal to the reference Dijkstra under the filter. Verify: integration (correctness in verify).
- **Routing latency:** P0-06 r3's target: Spike 2's measured p95 + 50%, a provisional setting (already ruled; decision sheet header). Spike 2 has measured A* p95 at 2.13 ms on the realme C55, so the target is 3.2 ms, rounded to one decimal (residual sheet R37; `perf.routeP95TargetMs`, R43; report `phase-reports/feature-first/Spike-2.md`, being written on 2026-10-12). A step-free query is a route query on the same engine (FEATURE_PIPELINE P0-07: "a filter on the same engine"), so it is timed in P0-06 AC-34's batch with step-free on, measured as P0-06 r3 measures, and judged by that target under A5's rule: a miss is reported to the product owner with the figure, and they decide whether it blocks. A query that ends in "no step-free way" or another no-route reason runs the second search of AC-14 (B14); its time is recorded separately as a provisional figure, with no pass or fail, because no document states a number for it (A5).
- **The width setting:** 1.2 m (L88; the demo's `wheelchairMinWidthM`), a setting, not a measurement. A tenant's own value is accepted (AC-29, B18).
- No other target is stated by the intent, the PRD or the Blueprint for this entry.

## 7. Design choices (not requirements; each with an alternative)

DC-1 to DC-7 were accepted by the product owner on 2026-10-12 (A7, L165).

- **DC-1 One filter predicate** shared by the route, other-way and distance searches (AC-16). *Alternative:* a separate filtered graph built per mode at load; better if profiling shows the per-edge check dominates query time (AC-34's figures), at the cost of memory.
- **DC-2 No re-derived estimate under the filter** (AC-11). The load-time coefficients bound every subset. *Alternative:* derive a second pair over the step-free edges only; tighter, so fewer nodes expanded, better if step-free query times prove slow.
- **DC-3 Clearance compared at the database's 0.001 m resolution** (`DECIMAL(9,3)`; P0-06 DC-3): passes when clearance ≥ setting − 0.0005. *Alternative:* an exact comparison of the stored numbers; equivalent if Spike 2 rules integer millimetres in the package.
- **DC-4 A missing or invalid width setting uses the platform default 1.2** (EC-3, AC-29), as P0-06 DC-11 does for `routing.stairsSaveM`. *Alternative:* treat the package as unreadable; stricter, better if a missing safety setting should block routing.
- **DC-5 A missing, negative or non-finite clearance makes the package unreadable** (EC-4), extending P0-06 DC-4's load check. *Alternative:* read it as 0 (narrow), so only step-free routing loses the edge; better if one bad edge should not stop ordinary routing.
- **DC-6 "No step-free way" is a no-route reason in P0-06's closed result set** (AC-28), not a fifth route-view state. *Alternative:* a separate state; better if it later gains content the other reasons lack.
- **DC-7 The step-free vectors V-SF-1 to V-SF-10 live in P0-06's shared vector file** (AC-12). *Alternative:* a separate step-free file; equally shared, but two files to keep in step.

**RECALLED, to verify by a doc check in the plan:** none beyond P0-06 r2 §7's (the long-lived isolate, `package:sqlite3` in a background isolate).

## Questions for the user

Each is tagged `[spec-writer]`, with the recommended option first.

**Q1 [spec-writer] Which connector types a wheelchair route may take.** **Ruled 2026-10-12 (L165, B10): option 1.** Both checks (§2, AC-2, EC-26). L88 says "lifts and ramps only". The schema also has a per-type `IsStepFree` flag (L37) that each mall can set on its own types, and a fifth cost model, `LEVEL`.
1. *(Recommended, ruled)* Both checks. The type must be marked step-free, and its cost model must never be stairs or escalator. A mistakenly marked escalator type is still refused, and a mall's own step-free type (a `LEVEL` link, for example) is used.
2. The flag alone, as the schema comment says. The mall decides entirely, including mistakes.
3. The cost model alone (lift or ramp), as the demo and L88's wording do. The flag is ignored, and a mall's `LEVEL` link is never used.

**Q2 [spec-writer] The ramp gradient, 1:20 (BP 344).** **Ruled 2026-10-12 (L165, B11): option 1.** No gradient check; marking the type step-free is the mall's statement that it meets 1:20 (§2, AC-2, EC-27). The database stores a ramp's rise (`RiseM`) and its two end points, but not its walked length. For a switchback ramp, the straight line between the ends understates the run, so the slope cannot be measured reliably.
1. *(Recommended, ruled)* No gradient check in the router. A ramp is used when its type passes Q1. By marking the type step-free, the mall attests that it meets 1:20.
2. The router refuses a ramp whose rise ÷ the distance between its ends is steeper than 1:20, with a new `routing.*` setting. This wrongly refuses compliant switchbacks.
3. As option 1, plus a publish warning for such ramps (a P0-03 change, built in FF-5).

**Q3 [spec-writer] Which kinds of edge get the 1.2 m width check.** **Ruled 2026-10-12 (L165, B12): option 1.** Every non-connector edge, store floors included, against its published clearance; connectors judged by their type (§2, AC-4, AC-7). Walkways and doors are settled (L88). Two kinds were not:
- the floor across a passage store (PRD: "its doors are held to the same 1.2 m");
- connectors, which have no width data (no lift-door or ramp-width column).

Options:
1. *(Recommended, ruled)* Every non-connector edge is checked against its published clearance, the store floor included (P0-03 AC-42 already gives every edge a clearance). Connectors are judged by their type alone (Q1).
2. Only walkways and doors. The store floor and connectors are not width-checked.
3. As option 1, plus a connector width column (schema, editor and publish changes) so that lifts and ramps are checked too.

**Q4 [spec-writer] A start point on an edge the wheelchair route would refuse.** **Ruled 2026-10-12 (L165, B13): option 1.** The start edge is exempt; the filter applies from its ends onward (AC-15, EC-19, EC-42). Examples: the shopper sets "Start here" in a corridor narrower than 1.2 m, or inside a walk-through store, whose floor edges step-free never uses.
1. *(Recommended, ruled)* The start edge itself is exempt: the shopper is already there. The filter applies from its end nodes onward.
2. No exemption. The shopper gets the "no step-free route" message.
3. Snap the start only to edges that pass the filter (nearest passable walkway), even if it is farther away.

**Q5 [spec-writer] Which message shows when wheelchair mode is on and no route is found.** **Ruled 2026-10-12 (L165, B14): option 1.** Try again silently without wheelchair mode; if that finds a route, the wheelchair message with "Turn off wheelchair route"; if not, routing's own reason and no "Turn off" (AC-8, AC-14, AC-20). The demo always shows "There is no wheelchair route" with "Turn off wheelchair route", even when turning it off would not help (a closed passage, or an unreachable place).
1. *(Recommended, ruled)* Run the same search again with wheelchair mode off, and never show its result. If a route exists, the shopper sees the wheelchair message and "Turn off". If none exists, the shopper sees P0-06's own reason ("⟨store⟩ is closed and it is the only way in", or "unreachable from here") and no "Turn off" button.
2. Always the wheelchair message, as in the demo.
3. The wheelchair message, with P0-06's reason added beneath it when turning off would not help.

**Q6 [spec-writer] "Accessible CRs are offered first": the rule.** **Ruled 2026-10-12 (L165, A11): option 1.** P0-07 owns the rule as one function: accessible restrooms reachable step-free first, closest first; then other reachable restrooms; unreachable last. P0-05 applies it to the Restroom chip, "Nearest CR", voice "nearest restroom" and search results (accessible restrooms before other restrooms; other rows keep their distance order) (AC-24, EC-39). It applies with wheelchair mode on (PRD §6.7 places it there).

2. Accessible restrooms only. Plain ones are hidden unless no accessible one can be reached.
3. Accessible first only when it is no more than a set distance farther than the nearest plain one (a new setting).
