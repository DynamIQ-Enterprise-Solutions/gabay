## 1. What this delivers

**Part A, now (Spark, no cost, no code):**
1. **The owner's short checklist** (AC-43 to AC-47): the account check, the project `gabay-staging` (fallback `gabay-staging-dq`) with Analytics off, Authentication with email and password on and sign-up off, and the web app registration whose public configuration SEC-3 uses. Each step has a read-back; no secret is ever read back.
2. **The local check** (AC-48, AC-49): the API on localhost verifies real Firebase tokens for the project; the standard §6 items that can be shown without a deploy are shown against it.
3. **Records** (AC-52).

**Part B, when the owner chooses Blaze:**
1. **The rest of the owner's checklist** (AC-5 to AC-16, AC-53, AC-54): billing check, the USD 5 budget alert before billing is linked, Blaze, the SQL Connect instance (hourly price read back), the bucket, the GitHub environment and variables, the deploy service account, the Workload Identity Federation pool and provider, the connection-path spike inherited from DEP-0, the first accounts.
2. **The workflow `deploy-staging.yml`** (AC-17 to AC-33): after a push to `main` of this repository, a **gate job** with no credentials waits for `lint` and `e2e` green on the same commit; only then a **deploy job** takes a federated identity, builds the admin page with the staging API address, runs `db:deploy`, and runs `firebase deploy --only functions,hosting --project <PROJECT_ID>`. A repository variable pauses it; a manual run with a commit redeploys an earlier one. Pinned like the other three workflows.
3. **Keyless identity** (AC-14, AC-32): Workload Identity Federation limited to this repository and `refs/heads/main`, a GitHub environment `staging`, and a deploy service account that exists only in the staging project.
4. **The staging check** (AC-37 to AC-39, §6): standard §6 items 1 to 6, 8 to 10 and 12 shown against the deployed URLs; item 7 reviewed; item 11 not applicable.
5. **Records** (AC-40, AC-41).

Nothing here touches production, the shopper app, the venue map code or any route.

## 2. Terms and preconditions

**Terms.**
- **"The owner"** is the product owner, Genesis Perez. **"The session"** is the main session that receives the owner's read-backs.
- **"Required checks"** are the jobs named `lint` (`lint.yml`) and `e2e` (`e2e.yml`), the two checks L136 requires on pull requests.
- **`<PROJECT_ID>`** is the project ID the owner reads back at A-2: `gabay-staging`, or `gabay-staging-dq` if the first is taken (Q5 (a)). It is a literal in the workflow and every command (DC-5).
- **"The commit"** is the commit a run deploys: the `workflow_run`'s `head_sha`, or the manual run's `commit` input (AC-30).
- **"Read-back"** is a short line or a screenshot the owner pastes to the session, showing the console's own value. **It never shows** a password, a key, a token, a setup link, a card number, a Secret Manager value or a `.env` value (CLAUDE.md; standard §6 item 3). The one exception is the web app's public configuration (A-4; AC-4).

**Part A preconditions.** None to start: the owner can create the project today. The local check (AC-49) needs the slices it shows to be merged (SEC-1 for guards, SEC-2 for the limiters and audit, SEC-3 for sign-in); an item whose slice is not merged is reported **not yet shown**, never as passed.

**Part B preconditions (checked first; if one is false the session stops and reports it).**
- The owner's call to move the project to Blaze is recorded as an L-row (L186: "a later owner call, recorded then").
- SEC-1 to SEC-3 and DEP-0 are merged and their staging check is shown (E-20 as amended).
- DEP-0's accepted spec states, in words this spec can cite: how `db:deploy` reaches Cloud SQL from a CI runner (the connector inside the tool, or the proxy binary); the names of the two logins and their Secret Manager entries; the `firebase.json` Hosting block; where the repository's pinned `firebase-tools` is installed; the explicit command that loads the invented Demo Malls venues and tenant; and **when the connection-path spike runs** (AC-53). **If DEP-0's spec leaves any of these open, DEP-1 returns it as a question; it is not decided here.**
- The Part B checklist steps O-1 to O-10 are read back **before** the workflow's pull request merges, because the merge itself starts the first deploy (DC-9). A merge before them would produce a red run that has done nothing wrong.

It looks up the commit's check runs (RECALLED: the REST check-runs list and the `checks: read` permission; §11) and decides, **before any credential step exists in the run**:
  1. a check run counts only if its name is exactly `lint` or `e2e`, **and it was created by GitHub Actions** (RECALLED: the `app` field), so another app's check named `e2e` cannot satisfy the gate; the names the gate looks for are the same strings as the job names in `lint.yml` and `e2e.yml` (AC-34);

  3. both newest runs must be `completed` with the conclusion `success`. `failure`, `cancelled`, `timed_out`, `skipped`, `neutral`, `action_required` and `stale` each end the gate as **not green**;

  6. the lookup reads all pages of the answer, not the first page only.

## 9. Design choices

Each is a DESIGN CHOICE, not a requirement, and names an alternative that also meets what is stated.

- **DC-1 The trigger is `workflow_run` of `lint` plus `workflow_dispatch`**, because the intent names the three-part fork guard that `build.yml` already pins, and a `workflow_run` is the pattern this repository has. *Alternative:* `on: push` to `main` with the same gate. It needs no fork guard (only this repository's pushes reach `main`) and `github.sha` would be the commit itself; it was not chosen because the intent fixes the guard. It would be the better choice if the owner wants the smaller trigger surface.
- **DC-2 Two jobs: `gate` (no credential) then `deploy` (`id-token: write`).** The job that can mint a token cannot start until the gate has passed, by `needs`, and its permission is not visible to the gate's code. *Alternative:* one job with the gate as its first steps. It is simpler, but then `id-token: write` exists in a job that has run a lookup script.
- **DC-3 The gate's logic is a file under `tools/` with its own tests**, run over recorded API answers, like `ci-migrations.js`. The workflow step passes the token and the commit through `env:`. *Alternative:* an inline script in `actions/github-script`. It needs no new file, but it cannot be unit-tested apart from the workflow and puts logic inside a pinned snapshot.
- **DC-4 The gate looks up check runs by name and by the GitHub Actions app**, as the intent says. *Alternative:* list the workflow runs of `lint.yml` and `e2e.yml` for the commit (identified by file, not by a name another app could use). It is more exact about which workflow ran; it was not chosen because the intent says check runs and L136's required checks are check names.
- **DC-5 The project ID is a literal in the workflow, pinned by the snapshot; the other values are repository variables** (the intent says a repository variable for the pause). A literal cannot be changed from a settings page. *Alternative:* all as variables (a settings change retargets the deploy with no review), or environment-scoped variables for the ones only the `deploy` job reads. The API address is a variable because it exists only after O-5 and the pull request is written before it (EC-4).
- **DC-6 The gate's wait limit and poll interval are named constants**, not settings: they are CI values, not mall options (rule 5). *Alternative:* a repository variable, which anyone with admin could change.
- **DC-7 No post-deploy health step in the workflow.** The intent's step list ends at the deploy; the first deploy's health is shown by hand (AC-38) and the running site by DEP-0's uptime check. *Alternative:* one `GET /api/health` after every deploy, which would make each merge self-checking (a Suggestion).
- **DC-8 The provider's condition also names the repository's numeric ID if the token carries it**, besides the repository name and `refs/heads/main`. *Alternative:* the name only, as the intent says. It is enough today and fails the way EC-20 describes after a rename or a name reuse.
- **DC-9 The first deploy is the run that Part B's own merge starts.** *Alternative:* merge the workflow with `STAGING_DEPLOY=off` and start the first run by hand once the owner steps are all read back. It costs one extra step; it would be the better choice if the owner wants the merge and the first deploy to be separate events.
- **DC-10 The environment `staging` has no required reviewers**, so a merge deploys with no hand step (L184: "merge updates one by one"). Its protection is the deployment-branch rule (`main` only) and, independently, the provider's condition. *Alternative:* a required reviewer, which makes every deploy a click.
- **DC-11 The `commit` input is checked against `main`'s history before anything else.** *Alternative:* trust the dispatcher (anyone with write access), which lets a branch commit reach staging. The environment rule would still stop credentials on a non-`main` ref, but a commit on `main`'s history needs no second reason.
- **DC-12 The owner enables the APIs once; the deploy account may not enable APIs.** It narrows the account to what a deploy needs and makes a missing API a loud first-deploy failure. *Alternative:* let the deploy account enable APIs (a broader role), which saves the owner one step and adds a permission an attacker with the token would otherwise not have.
- **DC-13 Everything that runs third-party install scripts (the npm installs, the Flutter pub get) runs before the credential step.** *Alternative:* install after authentication, which is no faster and puts a credential in the environment of every install script.
- **DC-14 [r2] Two parts, with Spark first (L186).** The project exists on Spark with real Auth now; the paid parts wait for the owner's Blaze call. *Alternative:* create nothing until Blaze and do all of r1 at once. That costs the owner nothing sooner but leaves SEC-3 and the local check with only the emulator, and gives no early read of Google's console behaviour (Part A's step 0 items).
- **DC-15 [r2] Part A's ACs are numbered after Part B's** so r1's numbers, and every cross-reference in it, stay valid. *Alternative:* renumber in reading order, which is tidier and breaks every reference to r1 (none is cited by a plan yet, so it would also be acceptable).
- **DC-17 [r2] Part A uses the sibling specs' account mechanism and adds no tool (the main session's technical choice).** SEC-3 §7a (interim, psql) before DEP-0, and `staging:admin --local-db` from DEP-0 on. *Alternative (b):* pull `staging:admin` forward so it runs before DEP-0 merges. Rejected: it would reorder DEP-0. *Alternative (c):* defer the signed-in items to Part B. Not needed, since the mechanism exists.
- **DC-16 [r2] Part A's local check is not the staging check.** E-20's condition names "their staging check", which only a deployed site can give. *Alternative:* let the local check stand for it. It would close E-20's condition without a deployed site, which the amendment does not say.
