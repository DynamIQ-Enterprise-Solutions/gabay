## 1. What this delivers

On localhost, in the admin page, behind FF-0's development stub and inside FF-SK's admin shell (the "Map editor" module, P0-11, FF-10):

- A dimensioned floor editor for one venue, one level at a time, drawn with `flutter_map` and `CrsSimple` in the venue's one planar frame (E-04 as widened by L161; E10). It offers the three P0 modes of L39 on one canvas, every tool on every level (G5): **grid boxes with the object library**, **free polygons**, and **tracing over an uploaded floor plan**. CAD/IMDF import and drafts from uploaded plans are P1-03 (L108), not this.
- Every shape can be moved, resized and rotated (L39; PRD §6.2).
- Doors with their clear width (L88) and entrance mark; stores assigned to units with an optional "spoken as" (L112; `Occupant.SpokenName`) and their status (G8); the store's walk-through mark (L29, L92; `Unit.PassThrough`); amenities, transit points and landmarks (L29, L30; G10); nested facility sections (L29, P0-01 B8; G6).
- Connectors: stairs, escalators and ramps with their two ends, height climbed (`RiseM`) and real direction (L86); lifts with the floors they serve (`NavConnectorStop`); an optional "spoken as" (L112; `NavConnector.SpokenName`); the "Evacuation only" switch (G9). Each type's metre costs are shown read-only until R11 (A23).
- The derived walkable area shown on the level, a preview of the walkways the publish engine would make from the saved draft (G3), and graph corrections drawn on them: block an area, add a path, remove a path (L32; P0-03 DC-6).
- The venue boundary and building footprints drawn as polygons (P0-01 B2 and §6). A drawn boundary is kept across level changes through a new `Venue.BoundaryIsDrawn` flag (G4): one migration, schema 0.15, and P0-01 r3's AC-34 condition.
- The review gate's other half: every element still marked `NeedsReview` is listed, highlighted, and can be confirmed or edited (L108; PRD §6.2). This is what lets MEZZ office and the penthouse publish (P0-03 AC-67, D13), and the penthouse's confirmed doors are what P0-13's on-site run waits for (F1, N11).
- Every refusal P0-03's publish can give has an editor action that fixes it (§2.6).
- Saves follow the named **Batched Save** rule: "the editor saves on explicit Save or Publish" (plan.html, named rules), as one all-or-nothing transaction (G1). Property panels follow the named **Panel** rule: "property panels are `FieldSpec` forms; geometry is validated at publish".
- Pieces of R11 built early, each to R11's definition and recorded in FF-10's slice row (A23): file uploads (§3.15, built whole for the floor-plan underlay, PH3 §9; A21) and the `memo` form kind (PH3 §4; J12).

## 2. Acceptance criteria

The request's tenant is always `req.tenantCompanyID`, filled by the stub (rule 2; FF-0 §2); FF-SK's switcher picks the account and, for an account holding two tenants, the tenant (A10 of round 1). "Refused" means an HTTP 4xx with the standard body `{ error: "<message for a person>" }`, nothing written, and never a 500 from a constraint the service could check first (standard §3.8). "Element" means a row of `Unit`, `Opening`, `FloorObject`, `FloorUnderlay`, `Occupant`, `Amenity`, `TransitPoint`, `Anchor`, `NavConnector`, `NavConnectorStop` or `NavCorrection`, plus the venue boundary and a building footprint.

### 2.1 Opening the editor

- AC-1: The admin opens the editor for a venue from the "Map editor" module (FF-SK's registry entry is flipped to built, with its route) and from FF-1's venue screen. It shows level chips for every level of the venue: each building's levels, highest ordinal first (P0-01 AC-15's order), and the outdoor ground level. Choosing a chip shows that level. Verify: widget test.
- AC-2: A level opens with its floor rectangle (0,0)–(`WidthM`, `DepthM`) and a grid at `GridCellM` (L39; Blueprint §3.3), and every element on that level: units, doors, floor objects, the underlay, stores, amenities, transit points, landmarks (`Anchor`, G10), connector ends and lift stops on that level, corrections, the venue boundary and the footprints of buildings (one frame per venue, E10). Active beacons on the level are drawn read-only (beacons are edited by FF-9 and FF-11). Verify: API test (one load returns every kind, each with its id, properties, geometry in level metres and its `UpdatedAt`); widget test.
- AC-3: Real scale: a 9 × 9 m box on a 40 × 40 m floor measures 9 × 9 m on screen at every zoom, and the panel shows 9.000 × 9.000 (PRD §6.2). The admin pans and zooms. Verify: widget test (measured against the projection); unit test of the metres-to-screen transform.
- AC-4: The editor reads only the draft tables. It never reads or writes `VenueVersion` or a package (the frozen-row trap, invariant 3). Verify: review, plus an integration test that a save leaves every `VenueVersion` row unchanged.

### 2.2 Drawing: the three P0 modes (L39)

- AC-5 **Grid boxes:** the admin places a unit as a box by dragging on the grid or by typing its centre, width, depth and rotation. With snapping on (DC-2), the box's edges and centre snap to `GridCellM`. The unit is stored with `ShapeKind = 'BOX'`, `CenterX`, `CenterY`, `WidthM`, `DepthM`, `RotationDeg`, and a `GeometryGeoJson` that the server derives from them (DC-3). Verify: widget test; API test (the stored polygon matches the box parameters, rotation included).
- AC-6 **Object library (G13):** the admin places a floor object by choosing an `ObjectType` in an `object-types` picker (rule 5; FF-0's lookups route). The seeded library holds the three platform types Pillar, Shaft and Furniture with no default sizes, so the admin types each object's size (G13; N9's fallback, §M 4). A type that has `DefaultWidthM`, `DefaultDepthM` or `DefaultHeightM` set (for example a tenant's own type once R11's screens exist) prefills them. `BlocksWalk` is copied from the type and can be changed (schema comment, "copied from ObjectType, overridable"). An object can sit inside a unit (`FloorObject.UnitId`). Verify: widget test (a seeded type opens with empty size fields; a fixture type with defaults prefills them); API test.
- AC-7 **Free polygons:** the admin draws a unit outline point by point and closes it; afterwards they can move, insert and delete points. The unit is stored with `ShapeKind = 'POLYGON'` and its `GeometryGeoJson`; a closed ring needs at least three distinct points. The same tool draws polygon floor objects, `BLOCK_AREA` corrections, the venue boundary and building footprints. Verify: widget test; API test.
- AC-8 **Traced underlay (A21; N4):** the admin chooses a floor-plan image for a level, marks two points on it and types the real distance between them. The image is then drawn at real scale under the shapes, and the admin can move and rotate it.
  - **Files:** PNG and JPG only; at most 10 MB (N4, §M 1). The accepted types and the cap live in the one shared upload config beside the constants file (A21, A26), never in a `GlobalSetting`, and the client and the server read the same config. The client refuses a wrong type or an oversized file before sending; the server refuses them too, in the standard shape, naming the file and the reason.
  - **One per level:** a level has at most one underlay; a new image chosen for a level replaces the old one at the next Save (A21). The replaced file is removed in the same Save (R15): its `StoredFile` row in the Save's transaction, the stored file from the local folder after the commit; a file left behind by a failed removal is reported in the server log, and the Save still succeeds.
  - **When it is sent:** the image is shown at once from the browser and reaches the server only with the next Save, inside its all-or-nothing outcome (the Batched Save rule; G1): a refused Save keeps no `StoredFile` row and no stored file from it.
  - **Stored:** the `FloorUnderlay` row stores pixels A and B, `RealDistanceM` (above 0, `CK_FloorUnderlay_Dist`), `OffsetX`, `OffsetY` and `RotationDeg`. The file is a `StoredFile` with `Purpose = 'UNDERLAY'`, owned by the request's tenant (composite FK), with its `MimeType`, `SizeBytes` and `Sha256` recorded by the server.
  - **Uploads are §3.15 built whole (A21; PH3 §9; Appendix C, Phase 4):** a per-feature `multer` instance in the route file with `limits.fileSize` from the shared config and a generated file name (the user's file name never becomes part of a path); storage in the git-ignored local folder through P0-03's storage interface, `StoragePath` a key shaped like the future Cloud Storage path, never a disk path (DC-16, D2), with the ledger row closed at the deploy call; no static mount, every file streamed back through an authorized route under the request's tenant.
  - The underlay never goes into a package (P0-03 §3.7, D11).

  Verify: API tests (a PNG and a JPG accepted and the calibration stored; a wrong type, an empty file, a file of exactly 10 MB accepted and one byte over refused; a path-like file name never reaches the storage key; another tenant's file answers 404 on the serving route and is refused in a batch; a missing file answers 404; a refused Save leaves no `StoredFile` row; a replacing Save leaves no row or stored file of the old image, and a refused replacing Save keeps the old one; a failed removal of the old file after the commit is logged and the Save still answers success); widget test (two-point calibration gives the stated metres; the client refuses an oversized file before sending); manual case (trace a store over a real plan image).
- AC-9 **All three on one canvas (G5):** every tool is available on every level, and the admin can mix them: trace over the underlay with boxes and polygons, and place library objects (DC-1). Verify: widget test.
- AC-10 **Move, resize, rotate (L39):** every shape can be moved, resized and rotated: box and polygon units, box and polygon floor objects, doors, `BLOCK_AREA`, `ADD_PATH` and `REMOVE_PATH` lines, the boundary and footprints. Points (amenities, transit points, landmarks, connector ends, lift stops) can be moved. A box keeps `ShapeKind = 'BOX'` and stores the new rotation in `RotationDeg`; a polygon stores its transformed points. The property panel and the canvas stay in step both ways: dragging updates the panel's numbers, and typing a number moves the shape. Verify: unit tests of move, scale and rotate on boxes and polygons (round trip to the stored form); widget test.

### 2.3 What is drawn

- AC-11 **Doors (`Opening`):** the admin places a door on a unit's edge; it snaps to the outline (DC-7) and is stored as a line segment (GeoJSON `LineString`, the form the seeds use, `db/seeds/lib/geo.js`). The panel holds: Name (optional, up to 200), IMDF category (from the constants file, invariant 14), clear width in metres (`ClearWidthM`, optional, above 0 when set; blank means "not measured", which publish warns about, P0-03 AC-23, L88) and "Venue entrance" (`IsVenueEntrance`). A door's unit is the unit it was placed on (`Opening.UnitId`) or none, for an opening in a walkway. Verify: API test; widget test.
- AC-12 **Unit properties:** Name (optional, up to 200), IMDF unit category (constants file; IMDF 1.0.0, RECALLED: the list is checked against the IMDF specification in the plan), walkable (`IsWalkable`; default from the category, DC-8) and the walk-through mark (AC-14). Verify: API test; widget test.
- AC-13 **Store assignment (PRD §6.2; L83; L112; G7; G8):** on a unit, the admin assigns a store (`Occupant`): Name (required, up to 200), category (`occupant-categories` picker), search keywords (optional, up to 400, a `memo` field built to R11's definition, PH3 §4 and J12; they feed search, P0-05), "Spoken as" (`SpokenName`, optional, up to 200; blank stores NULL, so the voice uses Name, L112), status (`store-statuses` picker) and Active.
  - **One store per unit (G7):** a unit holds at most one active store, checked in the service (no migration). Adding or reactivating a store on a unit that already has an active one is refused with 409 naming that store. A store moving out is deactivated, which keeps its status history.
  - **Status (G8):** a new store starts Open. MALL_ADMIN and SUPERADMIN change it; VENUE_EDITOR sees it read-only (AC-46). Each change of an existing store's status writes one `StoreStatusChange` row (the store, its unit at the time, the old and new status, the actor) in the Save's transaction. Creating a store writes no history row: the history records changes only, the first change's From holds the opening status, and a store never changed can still be deleted (AC-34) (R14). Shoppers see the status after the next publish (P0-03 AC-47); live status changes come with P1-01's module.
  - **No logo (A21):** no logo upload until a feature shows logos to shoppers; `Occupant.LogoFileId` is never written by FF-10. Recorded under G4 against PRD §6.2.

  Verify: API test (a second active store refused with 409; a status change writes one history row with the right old and new status; a save with no status change writes none; creating a store writes none, and that store can then be deleted); widget test; integration test (after a publish, the package carries the store's `SpokenName`, P0-03 AC-45).
- AC-14 **Walk-through mark (L29, L92):** the unit panel has "Shoppers may walk through this store" (`PassThrough`). It is offered on non-walkable units only (DC-9). Nothing else is set: passages are worked out at publish (L92 ruling 3). Verify: API test; widget test.
- AC-15 **Amenities (L29):** the admin places an amenity as a point (X, Y) with its type (`amenity-types` picker), an optional Name (up to 200) and an optional unit (proposed as the unit under the point; the admin can change or clear it). Refuge and assembly areas are amenity types chosen in this picker (G9); FF-10 adds no evacuation tool. Verify: API test; widget test.
- AC-16 **Transit points (L30):** the admin places a transit point as a point with its type (`transit-types` picker), a Name (required, up to 200) and an optional Note (up to 200). Verify: API test; widget test.
- AC-17 **Landmarks (`Anchor`; G10):** a named point tool places a landmark that is neither a store nor an amenity, such as a fountain or an atrium (Name required, up to 200; optional unit). Publish treats it as a place (P0-03 D5). Verify: API test; widget test.
- AC-18 **Stairs, escalators and ramps (L86; PRD §6.2):** the admin places a connector's From end on one level and its To end on another. The panel holds: type (`connector-types` picker), Name (required, up to 200), "Spoken as" (`SpokenName`, optional, up to 200, L112), one-way or two-way (`IsBidirectional`; one-way runs From → To, as the real escalator does, L86), height climbed (`RiseM`, DC-10), and "Evacuation only" (`IsEvacuationOnly`, G9; publish and routing already read it, P0-03 AC-13, AC-35). The panel also shows the chosen type's `CostBaseM` and `CostPerRiseM` read-only, labelled as the metre cost of a floor change (A23; tuning them is R11, recorded under G4). The connector shows on both levels. Verify: API test; widget test (the costs shown and not editable); integration test (a one-way escalator saved here publishes with a From → To edge only, P0-03 AC-34).
- AC-19 **Lifts (PRD §6.2 "elevators with the floors they serve"):** for a connector whose type's `CostModel` is `ELEVATOR`, the admin adds and removes the floors it serves, one stop per level (`UQ_NavConnectorStop`), each with its X, Y. A lift has no To end and no required `RiseM` (P0-03 D7). Its From end is kept equal to one of its stops by the server (DC-20). Verify: API test (a second stop on one level refused with 409 naming the level; To fields on a lift refused with 400); widget test.
- AC-20 **Incomplete connectors save (DC-19):** a stairs row without its To end yet, or a lift with one stop, can be saved; publish refuses it with the faulty end shown (P0-03 AC-15). Verify: API test.
- AC-21 **Graph corrections (L32; P0-03 DC-6):** on a level, the admin draws "Block this area" (`BLOCK_AREA`, a polygon), "Add a path" (`ADD_PATH`, a line) and "Remove a path" (`REMOVE_PATH`, a line), each with an optional Note (up to 200). Each is drawn over the level's walkable area (AC-22) and the walkway preview (AC-23; G3). Verify: API test; widget test; integration test (a `BLOCK_AREA` saved here removes walkways in the next publish).
- AC-22 **Derived walkable area (G3):** a toggle shows the level's walkable area as the publish engine derives it: walkable units, minus non-walkable units, minus floor objects that block walking, minus `BLOCK_AREA` corrections (P0-03 AC-24). It comes from a read-only server route per level, computed by the same code publish uses (one derivation, never a second copy in Dart), for the saved draft. Nothing is stored. Verify: API test (the route's area equals the generator's for fixtures; no row is written); widget test.
- AC-23 **Walkway preview (G3; P0-03 r3, the FF-10 part):** a second toggle asks the same read-only route for the walkways the publish engine's own generator makes from the saved draft of that level. Nothing is stored: no `VenueVersion`, no package, no graph row. The overlay is labelled "Preview of the saved draft", and says that unsaved changes are not in it. Built by engine-coder (A25). Verify: API test (the preview equals the walkways a publish of the same fixture produces for that level; no row is written in any table); widget test.
- AC-24 **Venue boundary (B2; invariant 10; G4):** the admin draws and edits the venue's boundary as a polygon; it covers the whole property (L30).
  - **The flag:** a migration adds `Venue.BoundaryIsDrawn BOOLEAN NOT NULL DEFAULT FALSE` (the next zero-padded migration number at build time; none exist yet, `db/migrations/README.md`), with `db/schema.sql` going to 0.15 (FF-10's change is 0.15 and R11's is 0.16, residual sheet R35), Blueprint Part 3, `SCHEMA_READING_GUIDE.md` and the affected `FieldSpec`s in the same change.
  - While the flag is FALSE, P0-01 AC-34 keeps deriving the boundary after every level change. Saving a drawn boundary from the editor sets it TRUE, and a level create, edit or delete no longer replaces the boundary (P0-01 r3's AC-34 gains this condition). "Reset to cover the levels" sets it FALSE and stores the derived rectangle at once (the zero-size rectangle for a venue with no levels, P0-01 AC-34).
  - The flag is never a form input; it is set only by these two editor actions (AC-36) and by the seed.
  - **The seeded venues start with it TRUE** (R13): their boundary comes from the source data and covers the whole property (L30), so editing a level in FF-1 does not replace it; "Reset to cover the levels" is still available. A seed change only, with no P0-02 revision (§L).

  Verify: API test (a drawn boundary kept across a level create, edit and delete; reset restores the derived rectangle and clears the flag; a zero-size or unclosed boundary refused with 400); seed test (every seeded venue has the flag TRUE; a level edit on a seeded venue keeps its seeded boundary); `npm run verify` (the migration on a 0.14 database and `schema.sql` twice); widget test.
- AC-25 **Building footprints (P0-01 §6):** the admin draws and edits a building's outline (`Building.FootprintGeoJson`, optional) as a polygon. Saving a footprint does not change the building's `UpdatedAt` used by FF-1's form, so an open building form is not made stale (DC-21, as P0-01 AC-34 does for the boundary; recorded in P0-01 r3). Verify: API test; widget test.
- AC-26 **Nested facility sections (L29; P0-01 B8; G6):** inside a unit, the admin draws section units on the same level with the parent set (`Unit.ParentUnitId`). A section can hold its own store (for example "Shoes" inside the department store, PRD §6.5). A department store's floors are its unit on each mall level it occupies, with its own escalators as ordinary connectors; a free-standing store is a building (FF-1). Whether a section lies inside its parent's outline is not checked at save (the Panel rule). A parent on another level, a parent in another venue, and a unit made its own ancestor are refused with 400. Verify: API test (each refusal; a three-deep chain accepted; a section outside its parent's outline accepted); widget test.

### 2.4 Saving (Batched Save)

- AC-27 **(G1):** Nothing reaches the server until the admin presses Save or Publish (the Batched Save rule); a chosen underlay image included (AC-8). The editor shows how many changes are unsaved. Save sends every create, update and delete across the venue's levels as one batch, applied in one transaction, all or nothing. On success the editor reloads the changed elements with their new ids and `UpdatedAt`. Verify: API test (a batch with one invalid element writes nothing, its underlay file included); widget test (counter, Save disabled while a save is in flight, so a double press saves once).
- AC-28 **Two admins, one level (G1):** each updated or deleted element carries the `UpdatedAt` it was loaded with (empty for a row never edited), as P0-01 B5 does. If any has changed since, the whole save is refused with 409, the message names each element ("Someone else changed Store 12 on Level 2. Reload to see their change"), nothing is written, and the editor keeps every unsaved change. Verify: API test (a stale element refused; a never-edited row's empty token accepted once, then stale); widget test.
- AC-29 **Leaving with unsaved changes (DC-17):** switching venue, leaving the module or closing the tab with unsaved changes asks first (Stay / Leave without saving). Switching level does not ask: unsaved changes on other levels are kept until Save. Verify: widget test; manual case (the browser's own leave warning).
- AC-30 **Undo (G2):** Undo and Redo step through the unsaved changes; "Discard changes" drops them all after a confirmation whose default action is Cancel. A chosen underlay image is one change like any other: undone or discarded, it is never sent. Verify: widget test.
- AC-31 **Errors:** a failed save (API unreachable, 4xx, 5xx, a batch over `MAX_JSON_BODY`, 5 MB, an underlay over the 10 MB cap) is shown through `formatApiError`, never as raw text, and every unsaved change is kept for a retry (standard §4.3, §3.8). A 400 names the element and the field. Verify: widget test; API test (an oversized body answers 413 in the standard shape).
- AC-32 **Values the server refuses (400, naming the element and field):** every case the schema or a stated rule would refuse is checked first:
  - text longer than its column; a required name blank or whitespace only (optional text that is blank stores NULL);
  - decimals in P0-01 AC-38's form only (".5" and "5." refused), with no more places than the column's scale;
  - box `WidthM` and `DepthM` above 0 (`CK_Unit_BoxParams`, `CK_FloorObject_Geom`); `HeightM` above 0 when set; `ClearWidthM` above 0 when set; `RealDistanceM` above 0; `RiseM` 0 or more (DC-10); `RotationDeg` 0 to under 360;
  - a lift with To fields, or a non-lift with stops;
  - a geometry of the wrong kind or structure for its element (DC-5);
  - a closed set value outside its constants list (`ShapeKind`, `CorrectionKind`, the IMDF categories, the upload types).

  Verify: API test (each case); widget test (the panels' validators refuse the same before sending).
- AC-33 **References the server refuses:** every level, unit, connector, building and file named in a batch belongs to the request's tenant and the venue being edited; a door's unit, a floor object's unit, an amenity's unit, a landmark's unit, a store's unit and a section's parent are on the same level as the element; a lift stop's level is in the connector's venue (`NavConnectorStop` carries no `VenueId`, DC9, so the service checks it through its connector). A lookup id must be the platform's or the request tenant's (DC8; the global-lookup trap) and active for a new reference (P0-01 B10). Anything else is refused with 400 (or 404 for an id of another tenant), never a 500 from a foreign key. Verify: API test (each case, including another tenant's `ConnectorTypeId` and another venue's level as a connector's To end).
- AC-34 **Deleting elements (G12; amends P0-01 B4 in P0-01 r3):** a unit is deleted with its own doors in one action, after a confirmation that lists them (default action Cancel). A unit that still has sections, a store, floor objects or amenities inside it is refused with 409 naming them. A store with status history (`StoreStatusChange`) is deactivated, never deleted. A connector with lift stops is deleted with its stops. Deleting an underlay removes its `FloorUnderlay` row and, in the same Save, its file: the `StoredFile` row in the Save's transaction, the stored file from the local folder after the commit, a failed removal reported in the server log (R15, as AC-8). A store never changed has no status history (R14), so it can be deleted. Verify: API test (each allowed and refused case; a deleted underlay leaves no `StoredFile` row or stored file); widget test.

## 3. Edge cases

Each one gets a test in the plan, or a one-line reason why not.

**Offline or stale data**
- The API is lost mid-save: the error is shown, nothing is half-written (AC-27), no underlay file is kept from it (AC-8), and every unsaved change is kept (AC-31).
- The API is lost while a level loads: the error state with Retry; the other levels' unsaved changes are kept.
- The API is lost while the walkable area or the walkway preview loads: that overlay shows its error with Retry; drawing and unsaved changes are unaffected.
- The admin's loaded level is stale because another admin saved: their own save gets 409 naming the elements (AC-28). Reloading the level with unsaved changes asks first.
- The walkway preview is of the saved draft: after an unsaved edit it is labelled as not including it (AC-23); it refreshes after a Save.
- The tab is closed with unsaved changes: the browser's leave warning; after leaving, they are lost (DC-17), a chosen but unsaved underlay image included. Manual case only: a widget test cannot close a browser tab.
- A shopper's package is never stale because of a draft edit: drafts reach no shopper until a publish (AC-49).
- The underlay file is missing from the local folder (for example after `setup-db`): the serving route answers 404, the level opens without the image and says the plan image is missing; the calibration row is kept.
- An underlay replaced or deleted, and removing the old stored file fails after the Save commits (the file locked or already gone): the Save stays successful, the server log reports the file left behind, and no `StoredFile` row points at it (AC-8, AC-34, R15).
- A seeded venue's level created, edited or deleted in FF-1: the seeded boundary is kept, because the seeds set `BoundaryIsDrawn` TRUE (AC-24, R13).

**Empty and maximum data**
- A venue with no levels: the editor says to add a level in "Venues, buildings and levels" first, with a link (for a VIEWER, without the link).
- A level with nothing on it: the empty floor with its grid; the review list's empty state says "Nothing to review"; the walkway preview says there are no walkways.
- A venue with no buildings (outdoor ground only): only the outdoor chip.
- "Reset to cover the levels" on a venue with no levels: the zero-size rectangle, the flag cleared; publish refuses it (P0-01 AC-34).
- The largest seeded level (Aurora: 2,320 units across the venue, P0-03 EC-37) and the synthetic 100,000 m² venue: measured and recorded, no pass or fail (§5; A5).
- A polygon with three points (the minimum) is accepted; two distinct points, or a ring that does not close, refused (DC-5).
- Lengths at their maximum accepted, one more refused, counted in characters ("Parañaque" and other non-ASCII names), as P0-01: names 200, `SearchKeywords` 400, `SpokenName` 200, notes 200.
- Decimal limits: `DECIMAL(9,3)` coordinates and sizes up to 999999.999; `RotationDeg` 359.99 accepted and 360.00 refused; one decimal place too many refused when typed, never rounded silently (P0-01 AC-38); dragged values rounded to the column's scale (DC-4).
- A batch over 5 MB (`MAX_JSON_BODY`): 413 in the standard shape, nothing written, changes kept (AC-31).
- An underlay of exactly 10 MB accepted; one byte over refused by the client before sending and by the server (AC-8); an empty file refused.
- Hundreds of unreviewed elements (a whole floor from P1-03 later): the review list pages through the scaffold (AC-37).
- A level with thousands of elements loads in one response (DC-6); timing is measured and recorded (§5).
- A seeded object type has no default size: the size fields open empty and are required (AC-6).

**Tenant boundary**
- Another tenant's venue, level, element or stored file in a load, save, delete or file request: 404, nothing written (AC-48).
- Another tenant's lookup row, underlay file or level named in a batch: refused (AC-33, AC-8).
- A lift stop on a level of another venue of the same tenant: refused (AC-33).
- `X-Tenant-Id` for a tenant the acting user lacks: 403 (FF-0).

**Each role**
- VIEWER, VENUE_EDITOR, MALL_ADMIN, SUPERADMIN: client hiding per AC-46, one widget test each.
- A VIEWER's save, or a VENUE_EDITOR's store status change, sent directly (curl with `X-Dev-Act-As`) succeeds until R2. Not tested now: no role check exists before R2 (E-20, waiver 3); the ledger row records it.
- A VENUE_EDITOR without a grant on the venue: R1/R2's check; on the ledger.

**Permission denied**
- A 403 from the stub's header checks is shown through `formatApiError`, on the level load, the overlays, the file request or the save, never as raw text.

**Concurrent edits**
- Two admins change the same element: the second save gets 409 (AC-28).
- Two admins change different elements on one level: both saves succeed (each element's own `UpdatedAt`).
- One admin deletes an element another is editing: the other's save gets 409 naming it (the row is gone), and their values are kept.
- One admin deletes a never-changed store (no history row, R14) while another changes its status: whichever save is second gets 409 naming the store (AC-28); the store is either deleted or has one history row, never both.
- Two admins each add an active store to the same unit: the second save is refused with 409 naming the first store (AC-13, G7). G7 rules a service check with no index, so the plan names how the check holds when both saves run at the same moment.
- Two admins each choose an underlay for the same level: the second save is refused with 409, because the level already has an underlay or the one it replaces changed since (AC-28); its image is kept for a retry, and one level never holds two (AC-8). The plan names how the service holds the one-per-level rule against two saves at the same moment (no unique index exists on `FloorUnderlay.LevelId`).
- A level is deleted or resized in FF-1 while the editor has it open: a save naming the deleted level gets 404 with its unsaved changes kept; a smaller floor rectangle leaves shapes outside it, shown with a note, and only the venue boundary limits them, at publish (G11).
- A type or store status is deactivated while a panel is open: the save keeps the value (AC-44).
- A venue boundary drawn while another admin creates a level in FF-1: the drawn boundary is kept, because the flag is TRUE (AC-24, G4).

**Publish in progress**
- A save during a `BUILDING` publish succeeds and lands in the next version (AC-35).
- Publish pressed in the editor while another publish of the venue runs: the save goes through, then FF-3's screen shows "A publish is already running for this venue" (P0-03 AC-62).
- The walkway preview requested during a publish: answered from the saved draft, independent of the publish (AC-23).
- FF-10 never writes `VenueVersion` (AC-4).

**Invalid input**
- Each AC-32 and AC-33 case.
- A polygon that crosses itself: saved (only structure is checked at save, DC-5), and publish refuses it as "This shape can't be read" (P0-03 AC-18); the editor marks it on the canvas.
- A door away from its unit's outline: saved; publish's wall and reachability checks judge it (DC-7).
- A section outside its parent's outline: saved (G6).
- A shape beyond its level's floor rectangle: saved, shown with a note (G11).
- A stairs connector with both ends on one level, or without its To end: saved; publish refuses it (DC-19; P0-03 AC-15).
- `RiseM` blank on stairs, an escalator or a ramp: saved; publish refuses it (the rise trap; P0-03 AC-15d). The panel prefills it (DC-10).
- An element id that is not a positive integer in a batch or a URL: 400 or 404 before any query (P0-01 G4: id 0 refused up front).
- A malformed JSON body: 400 "Malformed JSON body" (`errors.js`).
- Unknown extra fields: ignored, never written, until R5's zod; a body `BoundaryIsDrawn`, `LogoFileId` or connector cost is ignored (AC-36, AC-13, AC-18).
- An underlay that is not PNG or JPG, is empty, or is over 10 MB: refused, naming the file (AC-8). A path-like file name: accepted as an image, but the name never reaches the storage key (AC-8).
- A section whose parent chain loops: refused (AC-26).

**Lookups**
- No active object types: the library is empty, and boxes and polygons still work.
- A tenant's own type and a platform type with one label: both offered (as FF-0).
- An element whose type was deactivated: AC-44.

## 5. Scale targets

- **Routing graph: up to about 20,000 nodes per venue** (PRD §7). This bounds the walkway preview (AC-23, G3).

- **Peak concurrent admins and requests per hour: measured at the pilot** (PRD §7, L109; Blueprint OQ1). No target is set here.
- **Seed shape for reference, not a target:** Aurora, about 400 places on five levels (FEATURE_PIPELINE P0-02, L102) and 2,320 units across the venue (P0-03 EC-37).

- **Underlay file: 10 MB at most, PNG or JPG, one per level** (N4 and A21, ruled 2026-10-12, §M 1).
- **Editor timings: no target (A5, ruled 2026-10-12).** No document states a number for the editor, so level load, pan and zoom frame time, save time, walkway-preview time and the element count are measured on Aurora's busiest level and the synthetic 100,000 m² venue and recorded in the slice report, with no pass or fail.

## 6. Design choices in this spec

Each fills a gap no ruling covers and names an alternative that would also satisfy what is stated. **All twenty-one were accepted by the product owner on 2026-10-12 (A7, L165); DC-1 follows G5.**

- **DC-1** One canvas per level with all three P0 modes as tools; the underlay is a layer under the shapes. *Alternative:* the admin picks one mode per level.
- **DC-2** Snapping to `GridCellM` is on by default and a toggle turns it off; rotating by the handle is free, and an exact angle is typed in the panel. *Alternative:* rotation snaps to fixed steps.
- **DC-3** The server derives a box's `GeometryGeoJson` from its centre, size and rotation; a body geometry for a box is ignored. *Alternative:* the client sends both and the server checks they agree.
- **DC-4** Dragged coordinates are rounded to 0.001 m and dragged angles to 0.01°, the columns' scales; typed values follow P0-01 AC-38 (refused, never rounded). *Alternative:* refuse any dragged value with more places (unworkable with a mouse).
- **DC-5** At save, only structure is checked: the GeoJSON type per element (Polygon for units, polygon objects, `BLOCK_AREA`, the boundary and footprints; LineString for doors, `ADD_PATH` and `REMOVE_PATH`), a closed ring, at least three distinct points, finite numbers. Self-intersection and every wall, reachability and boundary rule stay with publish (the Panel rule; P0-03 AC-12 to AC-18). *Alternative:* full geometric validity at save.
- **DC-6** A level loads whole in one response (as P0-03's drawing route, D16). *Alternative:* load by viewport tiles.
- **DC-7** Doors snap to their unit's outline, and the server does not check that a door lies on it. *Alternative:* the server refuses a door off its unit's outline.
- **DC-8** `IsWalkable` defaults from the IMDF category through one map in the constants file (the seeds use walkway, parking and footbridge as walkable), and the admin can change it. *Alternative:* always chosen by hand.
- **DC-9** The walk-through mark is offered on non-walkable units only (a walkable unit is already walked through). *Alternative:* allowed on any unit and ignored by publish.
- **DC-10** `RiseM` is 0 or more, prefilled with the difference of the two levels' `ElevationM` (as the seeds do), and editable. *Alternative:* left blank until typed.
- **DC-11** Confirming keeps `DraftConfidence` (the package never carries it, D11). *Alternative:* set it to NULL on confirm.
- **DC-12** The editor's Publish saves first, then opens FF-3's screen (the Batched Save rule names Publish as a save point). *Alternative:* Publish is disabled while changes are unsaved.
- **DC-13** FF-3's problem rows gain "Open in editor" (built in FF-10 as P0-03 r3's FF-10 part, §L). *Alternative:* the admin finds the element from its level and name.
- **DC-14** A searchable element list per level, with a "needs review" filter, beside the canvas: the accessible way to select an element. *Alternative:* canvas selection only, with a separate review page.

## 9. Questions for the user

Each is tagged [spec-writer], with the recommended option first. Q1 to Q18 were ruled on 2026-10-12 (L165; `plan/FF-5-11-decisions.md`); their options are kept for the record. Q19 to Q21, new in r2, were ruled on 2026-10-12 (`plan/FF-5-11-residual.md`, APPROVED, R13 to R15).

**Q1 [spec-writer] How does a Save behave when two admins work on one venue?** **Ruled 2026-10-12 (G1): (a).** Applied in AC-27 and AC-28.
- (a) *Recommended:* one Save is one transaction, all or nothing. Each changed element carries the `UpdatedAt` it loaded (P0-01 B5's rule); if any changed since, the whole save is refused with 409 naming them, and the admin keeps every unsaved change. Leaving with unsaved changes asks first. Simple and predictable; the same rule as FF-1.
- (b) Each element is saved on its own within the batch; the ones that clash are reported and the rest are kept. Fewer redos, but a level can end up half-changed.
- (c) One admin per level at a time: opening a level for editing takes a lock with an expiry. No clashes, but a forgotten tab blocks others.

**Q2 [spec-writer] Undo in the editor?** **Ruled 2026-10-12 (G2): (a).** Applied in AC-30.
- (a) *Recommended:* Undo and Redo through the unsaved changes, plus "Discard changes". Drawing without undo is slow to correct, and the unsaved batch is already held in the page.
- (b) "Discard changes" only; undo later.

**Q3 [spec-writer] How does the admin see the derived walkable area and the walkways while correcting?** **Ruled 2026-10-12 (G3): (a), built by engine-coder (A25) as P0-03 r3's FF-10 part.** Applied in AC-21 to AC-23.
- (a) *Recommended:* a read-only server route per level returns the derived walkable area and, on request, a preview of the walkways generated by the publish engine's own code for the saved draft, with nothing stored. One derivation, no Dart copy (One Router's spirit).
- (b) The walkable area from a server route; walkways only from the last published version (P0-03's drawing route with `versionNo`).
- (c) Both only after a publish.

**Q4 [spec-writer] Once the admin draws the venue boundary, does a level change still replace it?** **Ruled 2026-10-12 (G4): (a); schema 0.15 and P0-01 r3.** Applied in AC-24; the seeded venues' starting value is Q19 (ruled R13: TRUE).
- (a) *Recommended:* a migration adds `Venue.BoundaryIsDrawn BOOLEAN NOT NULL DEFAULT FALSE`. While false, AC-34 keeps deriving; drawing sets it true and the drawn boundary is kept; "Reset to cover the levels" sets it false. P0-01 AC-34 gains one condition.
- (b) No migration: the service stops deriving when the stored boundary differs from the rectangle it would derive. Fragile: a drawn rectangle that happens to match is overwritten.
- (c) After FF-10, the boundary is never derived: zero-size until drawn, and publish refuses until it is. Changes P0-01 AC-34.

**Q5 [spec-writer] Do you confirm the three P0 modes as one canvas with every tool (DC-1)?** **Ruled 2026-10-12 (G5): (a).** Applied in §1, AC-9 and DC-1.
- (a) *Recommended:* yes, one canvas, every tool on every level, mixed freely.
- (b) The admin picks a mode per level, and the tools follow it.

**Q6 [spec-writer] How are nested facilities modelled?** **Ruled 2026-10-12 (G6): (a).** Applied in AC-26.
- (a) *Recommended:* sections are child units on the same level as their parent; a department store's floors are its unit on each mall level it occupies, with its own escalators as ordinary connectors; a free-standing store is a building (already possible in FF-1). Whether a section lies inside its parent is not checked at save (the Panel rule).
- (b) As (a), and a section outside its parent's outline is refused at save.
- (c) A department store with its own floors is always a building, and `ParentUnitId` is for sections only.

**Q7 [spec-writer] How many stores can one unit hold?** **Ruled 2026-10-12 (G7): (a).** Applied in AC-13.
- (a) *Recommended:* at most one active store per unit, checked in the service (no migration). A store moving out is deactivated, which keeps its status history.
- (b) Several active stores per unit (for example kiosks sharing a stall).
- (c) One per unit, enforced by a partial unique index (a migration).

**Q19 [spec-writer] (new in r2) Do the seeded venues start with `BoundaryIsDrawn` TRUE?** **Ruled 2026-10-12 (residual sheet R13): (a).** Applied in AC-24, §3, §4 item 2. G4's flag defaults to FALSE. The seeds store each venue's boundary from its source data: the demo venues' site rectangle (`db/seeds/lib/demo.js`, `geo.rectPolygon(v.siteRect)`) and the spike venues' extent (`spike.js`). That rectangle can differ from P0-01 AC-34's derived one (from (0,0) to the largest level), so with FALSE the first level edit in FF-1 replaces the seeded boundary.
- (a) *Recommended:* the seeds set it TRUE for every seeded venue, because their boundary comes from the source data and covers the whole property (L30); a level edit then keeps it, and "Reset to cover the levels" is still there. A seed change only (no P0-02 revision, §L).

It matters for AC-34: "a store with status history is deactivated, never deleted".
- (a) *Recommended:* no row at creation: the history records changes only, the first change's From holds the opening status, and a store never changed can still be deleted (AC-34). The seeds already write none.
- (b) A first row at creation, From empty: the history starts at opening, and every store saved from FF-10 can then only be deactivated, never deleted.

**Q21 [spec-writer] (new in r2) What happens to the file of a replaced or deleted underlay?** **Ruled 2026-10-12 (residual sheet R15): (a).** Applied in AC-8, AC-34, §3. A21 says a new upload replaces the old one; nothing says whether the old `StoredFile` row and its stored file are kept.
- (a) *Recommended:* removed by the same Save: the `StoredFile` row in the Save's transaction, the stored file from the local folder after the commit; a file left behind by a failed removal is reported in the server log. No orphan files build up.
- (b) Kept: the old file stays stored and unreferenced, for a later clean-up that does not exist yet.
