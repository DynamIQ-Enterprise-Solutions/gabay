## 2. Acceptance criteria

The request's tenant is always `req.tenantCompanyID`, filled by the stub (rule 2; FF-0 §2); FF-SK's switcher picks the account and, for an account holding two tenants, the tenant. The editor reaches the server only through the one `ApiClient`, which sends the stub's headers. ### 2.1 OA-4a-1: Draw a floor

- AC-58 [OA-4a-1] **Opening the editor.** The "Map editor" module page (`/admin/map-editor`, FF-SK's `/admin/:moduleId` route) lists the tenant's venues to choose from (S9's list scaffold); the editor itself is `/admin/map-editor/:venueId` (DC-E26). It is also opened from FF-1's venue screen (the entry itself is P0-01 r4's screen). The editor loads `GET …/map` through the `ApiClient` and shows the four states: loading, error with Retry, empty (draft `null`: "Start a blank map", AC-59; "Import a map file" joins in OA-4b-2), and data. A venue of another tenant, or one that does not exist, shows "Not found" and no editor. An inactive venue opens and is editable (OA-2 DC-20), marked inactive. The editor reads the draft and the list of published versions only; it calls publish only through AC-74. Verify: widget test (the four states, not-found, inactive); API-through test (a load against the real route and the local database); manual case.
- AC-59 [OA-4a-1] **Blank start (office §8.7).** On an empty venue the admin fills a dialog: first building's name and type (a `building-types` picker), first floor's name and short name, and its width and depth (each within the level-size range). The dialog creates a document that passes the server validator: `spec` 1, `units` m, `catalog` the catalog route's current version (OA-1 §2.1), `site.boundary` the floor's rectangle, one building (the main one, AC-144), one indoor level at origin (0, 0), and every other field at its default. It is saved at once with `baseVersion` equal to the `draftVersion` the load gave (0 for a new map). Every dialog field is a `FieldSpec` (AC-66). Verify: widget test; API-through test (the created document is accepted by `PUT …/map/draft`); manual case.
- AC-60 [OA-4a-1] **The canvas and its scale (E-04; PRD §6.2; G5).**
  - It is a `flutter_map` with `CrsSimple`. The map's unit is the metre; `x` runs right and `z` runs **down** the plan (the projection flips the map library's y axis); a rotation of 0 faces up the plan (−z) and positive angles turn clockwise (office §3). One projection module holds all three conventions and is tested on its own.
  - It shows the active level's rectangle (`origin`, `size`) with a 10 cm grid (the plan sets when it fades out at low zoom), and the site boundary and every building's footprint as faint outlines on every level (r2 DC-18, kept). Only the active level's elements are drawn (office §11: one level at a time).
  - **One canvas, every tool on every level, mixed freely (r2 G5, DC-1 kept).**
  - Wheel zooms at the pointer; right or middle drag pans; the scale is clamped to 4 to 400 pixels per metre (office §8.3).
  - Real scale: a 9 × 9 m unit on a 40 × 40 m floor measures 9 × 9 m on screen at every zoom, and the panel reads 9.000 × 9.000 (PRD §6.2).

  Verify: unit tests of the projection (round trip; the four axis vectors; rotation direction; 9 × 9 m at several zooms); widget test (pan, zoom clamp, the layers); manual case.
- AC-61 [OA-4a-1] **Floor tabs and Add floor (office §8.1).** Tabs show the document's levels grouped by building, the outdoor level first, then each building's levels with the highest ordinal first (DC-E6); a tab shows the level's short name and, as a tooltip and for the screen reader, its full name. Choosing a tab shows that level; **switching level never asks anything** (r2 AC-29's rule, kept). "+ Add floor" opens a dialog with `FieldSpec`s for name, short name, optional spoken name, building (a pick among the document's buildings, or "Outdoor ground" while the document has none), ordinal, elevation, height, size and origin. Defaults come from the chosen building's highest level (DC-E7). The dialog refuses what the validator would: an ordinal already used in that building, a second outdoor level, an outdoor level whose ordinal is not 0, more than `MAX_LEVELS` levels. The floor panel edits an existing level's fields. A size or origin change that would leave any element or connector stop of the level outside its rectangle is refused, with the count of elements outside; the rectangle must also stay inside the venue extent. Adding a floor is one undo step and a structural save (AC-70). Verify: widget test (order, grouping, each refusal, no confirmation on switching); unit test of the defaults; API-through test (a document with an added outdoor level is accepted).
- AC-62 [OA-4a-1] **Select, move, resize, rotate (L39; PRD §6.2).** The Select tool (`V`) picks the topmost element under the pointer (the hit order is fixed and written in the plan); a drag on an element moves it; a drag on empty canvas draws a marquee (AC-85). Handles on a selected element:
  - a unit, a correction polygon, a footprint or the boundary: a handle on each vertex (drag to move, a handle at each edge's middle to insert a vertex, Delete on a selected vertex removes it, never below 3 vertices or above 64); eight bounding-box handles to resize (scaling the outline about the opposite corner, DC-E32); a rotate handle (turns about the centre; 15° steps, Shift for free);
  - a wall: a handle on each end;
  - an item or a connector footprint: resize handles only on the dimensions its catalog type or kind lets vary, within the range; a rotate handle;
  - a point (amenity, transit point, anchor, stop): moves.

  A resize or reshape that would make a polygon smaller than `POLY_MIN_AREA_M2`, a wall shorter than `WALL_MIN_LENGTH_M`, or an item outside its resize range stops at the limit. Each gesture is one undo step. The panel's numbers follow the canvas while dragging, and typing a number moves the shape (AC-66). Verify: unit tests (move, scale and rotate of each element kind; the limits); widget test (each handle); manual case.
- AC-63 [OA-4a-1] **Walls (office §8.2).** The Wall tool (`W`): click–click chains; `Enter` or `Esc` ends the chain; a segment shorter than `WALL_MIN_LENGTH_M` is ignored with a message. A new wall has thickness `WALL_THICKNESS_DEFAULT_M` and kind `solid`. Each placed segment is one undo step. Verify: widget test; unit test.
- AC-64 [OA-4a-1] **Units (office §8.2, L39).** The Unit tool (`M`): drag a rectangle to make a four-point polygon (smaller than `POLY_MIN_AREA_M2` is ignored); the polygon tool (`P`, DC-E2): click points, close by clicking the first point or `Enter`, 3 to `MAX_POLY_POINTS` points. A new unit has the category `room` (DC-E3), its `walkable` filled from the category (OA-1 AC-9; the panel shows it), and no name. A polygon that crosses itself is saved (the validator does not refuse it) and is flagged by the server's `SHAPE_SELF_CROSSING` finding (P0-03 r4 AC-112, shown by AC-126), not by an editor check. Verify: widget test; unit test (the default category and walkable value).
- AC-65 [OA-4a-1] **Doors and windows (office §8.2; L88).** The Door tool (`O`): click on a wall to place an opening at that fraction of the wall (`at`, 3 decimals), width `DOOR_WIDTH_DEFAULT_M` (0.9, DC-E5) or the wall's length when shorter, kind `door`. The panel holds kind (door or window), width (`OPENING_WIDTH_MIN_M` to `OPENING_WIDTH_MAX_M`, no longer than its wall), position, optional name (200), clear width (blank means "not measured"; above 0 and no more than the width) and, for a door only, "Venue entrance". Deleting a wall deletes its openings (AC-88). Which unit a door belongs to is set from the unit's side (AC-91). Verify: widget test; unit test (placement fraction; the width limits).

  **Machinery this needs** (built to the plan, listed here because rule 7 depends on it): `ColKind.decimal` (kept by the FF-1 client trim, re-plan §3.1); a closed-set field is a `text` spec with the set named (`closedSet: 'WallKind'`), rendered as a select over the generated set with its labels from ARB, never free text (DC-E11); a code field is an `fk` spec whose `SelectOption.value` is the lookup **code** (DC-E12); a point's components are addressed as `size.0`, `size.1`, `origin.0`, `origin.1` and checked as metres (the lint's document mode gains this, DC-E11, because OA-1 declares a point as canvas-only). - AC-67 [OA-4a-1] **Typed values (r2 AC-32's client side, kept).** A typed decimal is accepted only in P0-01 AC-38's form (".5" and "5." refused) with no more places than the field's scale (3 for metres, degrees and ratios; 7 for `mpp`, latitude and longitude), and is never rounded silently; a **dragged** value is rounded to 0.001 m and 0.001° (DC-E4's reading of r2 DC-4). A number outside its range is refused with a message naming the range. Text is trimmed; a required text that is blank or only spaces is refused; an optional text left blank is removed from the element; control characters (U+0000 to U+001F, U+007F) are refused, a pasted line break included; **length is counted in Unicode code points**, as the validator counts (OA-1 AC-18), so "Parañaque" and an emoji count as the server counts them. Verify: unit tests (each rule, including a 200-code-point name with an emoji and 201); widget test.
- AC-68 [OA-4a-1] **Snapping (office §8.3).** The grid is 10 cm (`SNAP_GRID_M`); wall ends snap to other wall ends within 12 screen pixels (`SNAP_END_PX`, so the radius shrinks as the admin zooms in); wall angles snap to 15° steps (`SNAP_ANGLE_DEG`); **Shift** frees the angle; **Alt** ignores the grid. An item whose catalog `mount` is `wall` snaps flat against the nearest wall face, facing the pointer's side. The snap target is drawn while it is active. Verify: unit tests (each snap and each modifier); widget test.
- AC-69 [OA-4a-1] **Snapshot undo (office §8.4; r2 G2's intent, kept).** Undo and Redo (`Ctrl+Z`; `Ctrl+Shift+Z` or `Ctrl+Y`; and two buttons) step through whole-document snapshots, at most `UNDO_STEPS_MAX` (100). A gesture is **one** step: a drag is one step (the snapshot is taken at its start, the document is mutated live, and it is marked dirty at its end), as is a click-placed wall, a typed field change, a delete, a duplicate, a row of stores. A new change clears Redo. Loading, Reload, Restore and Clear reset the stack except where AC-96, AC-97 and AC-124 say otherwise. Undo changes only the drawing; stores (OA-4b) are saved apart and are not undone (AC-113). Memory is bounded (DC-E10) and measured (AC-98). Verify: unit tests (the cap; one drag, one step; redo cleared); widget test; manual case.
- AC-70 [OA-4a-1] **Autosave and its states (L170 Q7; office §8.4).** The editor saves the document 1.5 s after the last change (`AUTOSAVE_DEBOUNCE`), and **at once** after a structural action (a blank start, an added or deleted floor, a restore, a clear, an import). The save sends `{ layout, baseVersion }`, where `baseVersion` is the `draftVersion` the editor last loaded or received. The top bar shows one of six states, in words and an icon (never colour alone): none, dirty, saving, saved (with the time), error, conflict. Only one save runs at a time; a save that finishes while the document has changed again leaves the state dirty and saves again. A successful save stores the answer's `draftVersion` and `updatedAt`. Verify: widget test with a fake clock (debounce, immediate saves, one in flight, the re-save); API-through test (a drawn document is accepted and `draftVersion` rises by 1 each save); manual case.
- AC-71 [OA-4a-1] **The conflict stop (L170 Q7; OA-2 AC-16).** A 409 puts the editor in **conflict**: all saving stops and a stale write is never retried or merged. A banner says "Someone else changed this map" with **Reload**; Reload asks first, because it discards the changes on screen that were not saved (default Cancel), then loads the server's draft and resets the undo stack. While in conflict the drawing tools and panels are disabled so that no more work is lost (DC-E8), Publish is disabled (AC-74), and leaving the page asks (AC-73). Verify: widget test; API-through test (two clients on one base: one 200, one 409, the stored draft is the winner's, repeated 20 times as OA-2 AC-16); manual case with two tabs.
- AC-72 [OA-4a-1] **Save errors.** A failed save (the API unreachable, a 5xx, a 413) puts the editor in **error**, shown through `formatApiError`, never as raw text; the document stays on screen and is not lost. The editor does not retry by itself (DC-E9): a "Try again" button and the next change each start a save. A 400 with `problems` lists them (at most 20, with the total, OA-1 AC-26); each problem is a path, and clicking one selects the element its path names (the editor resolves `levels[i].units[j]…` against its own document); a problem on a backdrop key (OA-2 AC-19) selects the level. A refused save never changes the document. Verify: widget test (each error kind; clicking a problem selects the element); API-through test (an invalid document gives `problems` and `total`).
- AC-73 [OA-4a-1] **Leaving the page.** Leaving the editor (another module, another venue, another tenant in the switcher, or any route change) first finishes any pending or running save. If the state is error or conflict, the editor asks "Stay" or "Leave without saving" (default Stay). Closing or reloading the tab while the state is dirty, saving, error or conflict shows the browser's own leave warning and makes a best-effort save (RECALLED: how much a page may send while it unloads is checked in the plan). Verify: widget test (the route-change cases); manual case (the browser warning: a widget test cannot close a tab).
- AC-74 [OA-4a-1] **Publish from the editor, and a running publish (r2 AC-42's intent; OA-2 notes "For OA-4").** The editor's Publish button (shown to MALL_ADMIN and SUPERADMIN only, AC-137) waits for any running save, refuses with "Fix the save problem first" while the state is error or conflict, and then opens the publish module for this venue (FF-3′'s screen once it exists; the module placeholder until then). When the load reports `publishing` (a publish of this venue is `BUILDING`), a banner names the version, and Publish is disabled; the banner is refreshed on load and whenever Publish is pressed (DC-E29). Autosave carries on during a build, and a save made meanwhile lands in the next version (OA-2 AC-28). Verify: widget test (the disabled states, the banner, the wait for a save); API-through test of the 501 message shown through `formatApiError` once the publish module calls it.
- AC-75 [OA-4a-1] **Constants, ids and caps.** Every cap, range, default and text length comes from `VenueMapConstants` (generated from the schema file) and every closed set from `closed_sets.dart`; no such literal appears in editor code (C8; verified by review and a test that fails if a value in the schema file changes and the editor's behaviour does not follow). The editor's own office values live in one constants file, each with its office citation: `AUTOSAVE_DEBOUNCE` 1.5 s, `CHECKS_DEBOUNCE` 400 ms, `UNDO_STEPS_MAX` 100, `SNAP_GRID_M` 0.1, `SNAP_END_PX` 12, `SNAP_ANGLE_DEG` 15, `NUDGE_M` 0.1 and `NUDGE_BIG_M` 1, `DUPLICATE_OFFSET_M` 0.5, `ROTATE_STEP_DEG` 90 and `ROTATE_FINE_DEG` 15, zoom 4 to 400 pixels per metre, `DOOR_WIDTH_DEFAULT_M` 0.9, and the id length. A new element's id is `<kind prefix>-<6 base36 characters>` (levels `L<n>`), unique across the whole document (office §3), regenerated on a collision. A tool refuses to place or create an element beyond its cap, naming the cap and the count. Verify: unit tests (id uniqueness and retry; each cap refusal); review.
- AC-76 [OA-4a-1] **Nothing is dropped or reordered; everything stays inside its level.** The editor holds the document in a typed model that keeps **every** field it loaded, including those it does not edit (`site.georeference`, a building's `mapUp`, a level's `floor` and `spokenName`, `review` flags, backdrops). A document loaded and saved without any edit comes back deep-equal to what was loaded (OA-1 AC-12; the server's canonical copy), with the same ids and the same order of every array. Every coordinate the editor writes lies inside the active level's rectangle, edges included, and is rounded to 0.001; an angle is normalised to [0, 360). A drag or a duplicate that would leave the rectangle stops at the edge (AC-85). Verify: unit test (a round trip over OA-1 AC-1's every-element fixture); widget test (the clamp).
- AC-77 [OA-4a-1] **Finishes are keys; colours come from the tokens (rule 6; re-plan §1.2).** The document holds only finish keys. `app/lib/core/theme/gabay_tokens.dart` gains a light and a dark colour for **every** value of `FloorFinish` and `ItemFinish` (closed-sets.json says each key has its own token), and the renderer maps a key to its token. Verify: unit test (every key of both sets, in both themes, has a token: a new key without one fails); `npm run verify` (`colour-literals`).

- AC-88 [OA-4a-2] **Deleting (office §8.3).** The rules, each one undo step, with the confirmation of the last paragraph:

  - deleting an **opening** removes it from every unit's `doors`;

- AC-91 [OA-4a-2] **Reference pickers.** A unit's `parent` and `doors`, an amenity's `unit` and a landmark's `unit` are set by **arming** the control and clicking the target on the canvas, or by choosing it from the level's element list; only targets on the same level are offered; `Esc` disarms. Verify: widget test; unit test (the cycle rule).
- AC-144 [OA-4a-2] (stage OA-4a) **The main building (L176, Q18).** The main building is the **first entry** of the document's `buildings` array, and the shopper side's shortcuts follow the array's order (L176; no schema change). The editor keeps the main building first:
  - the Site panel lists the buildings in array order and marks the first one "Main building";
  - "Add building" appends at the end; the first building of an empty array is the main one;
  - the admin can move a building up or down the list; a building other than the main one **cannot be moved above it**, and the main building has no "move up";
  - "Make this the main building" is the **only** way another building gets the first place: it moves that building to the first place and shifts the others down one, keeping their relative order;
  - deleting a building that is not the main one never changes which is first; deleting the **main** building asks first (default Cancel), names the building that becomes main (the next in the array by default) and lets the admin choose another of the remaining ones; the choice is part of the same undo step;
  - nothing else reorders `buildings`: a duplicate, a floor added or deleted, a restore or an import's own order are not editor reorders, and a load followed by a save keeps the order (AC-76);
  - a document with no building (an outdoor ground only) shows no main building;
  - **the building type code is not consulted**: the first entry is the main building whatever its type. OA-3 uses the `MAIN` type code only to choose the first entry when it converts the seeds (OA-3 AC-21a, DC-25: the first `MAIN`-type building, else the first); the package keeps the document's order, the main building at position 0 (P0-03 r4 AC-131).   Verify: unit tests (each rule: add, move, make-main, delete either kind, order kept by a round trip); widget test (the mark, the missing "move up", the delete dialog); API-through test (the order survives a save and a load, OA-1 AC-12). *Added after the L176 ruling and numbered last so that Part B's pointers stay valid.*

### 2.3 OA-4a-3: Check, find and recover

- AC-92 [OA-4a-3] **The Checks panel and the editor's own checks (office §8.6 items 4 to 6; P0-03 r4 §3.14.8).** Warnings only, **never blocking** (the save and publish are unaffected). They are computed in the editor, from the document alone, 400 ms after the last change (`CHECKS_DEBOUNCE`, separate from the autosave). Each carries the ids of the elements to select; clicking one selects them, switches to their level and centres them. **The editor's own checks are exactly the ones that need no graph, no store and no beacon, which P0-03 r4 leaves to the editor** ("unnamed units, overlaps, furniture inside a wall"), and **none of them is a finding kind of P0-03 r4 AC-107** (AC-123's rule; a test compares the two sets). ### 2.4 OA-4a-4: Trace a plan

All of OA-4a-4 follows office §9 and OA-2's backdrop routes. The server stays authoritative for every limit; the client checks first so the admin is told before anything is sent.

- AC-99 [OA-4a-4] **Choosing a file.** The "Floor plan" panel's chooser (through `package:web`, E-23) takes a PNG, JPEG or WebP image, or a PDF (AC-105). The client reads the file's first bytes and decides the type **from them**, never from the name; refuses a size over `BACKDROP_MAX_BYTES` (15 MB) and a pixel size outside `BACKDROP_MIN_SIDE_PX` to `BACKDROP_MAX_SIDE_PX` a side or over `BACKDROP_MAX_PIXELS`, each with a message naming the limit, before sending. Verify: unit tests (the type by magic bytes, each limit); widget test.
- AC-100 [OA-4a-4] **Upload and placement.** The file is sent as multipart form data, one file in the field `file` (OA-2 as built; Q4), through the `ApiClient`, with progress. The answer `{ id, width, height }` gives the level its `backdrop`: `id` the key, centred on the level, scaled so the whole image fits (a guess), `rot` 0, `opacity` 0.5 (`BACKDROP_OPACITY_DEFAULT`), not locked; the editor goes straight to **calibrate** mode (AC-101). Placing it is one undo step, and the document is saved after the upload, so the key it names exists (OA-2 AC-19). The server's refusals are shown as it words them: 415 "Use a PNG, JPEG or WebP image", 400 damaged or over a pixel limit, 413, and 409 "This venue already has 20 floor-plan images". Verify: widget test (each refusal); API-through test (an upload, then a save naming the key).
- AC-101 [OA-4a-4] **Calibrate (office §9 step 3).** The admin clicks the two ends of something whose real length they know and types the metres (above 0). The new scale is `mpp = mpp · metres / clickedLength`, anchored so that the **first clicked point stays put**. A result outside `BACKDROP_MPP_MIN` to `BACKDROP_MPP_MAX` is refused with a legible message. `mpp` is stored to **7 decimals** (OA-1 AC-14's lesson: 3 decimals is a 6 % error across a building). Two identical clicks are refused. Verify: unit tests (the formula, the anchor, the range, the 7-decimal result; the 4,000-pixel example gives 33.333 m within 0.001 m); widget test.
- AC-102 [OA-4a-4] **Move, rotate, opacity, lock.** Dragging moves the image (`cx`, `cz`); a handle or a typed angle rotates it (`rot`); an opacity control sets 0.05 to 1; **Lock** stops the image from being picked or moved. `opacity`, `rot`, `locked`, `cx` and `cz` are `FieldSpec`s (AC-66); `mpp` is shown, not typed. Each change is one undo step. Verify: widget test; unit test.
- AC-103 [OA-4a-4] **"Make the floor this size" (office §9 step 4).** Offered only while **nothing has been drawn on the level** (no wall, opening, unit, item, correction, amenity, transit point or landmark, and no connector serving it), because anything drawn would stay put while the picture moved. It sets the level's `size` to the image's real size (pixels × `mpp`) and moves the image so that its top-left corner is the level's origin. It is refused, with the reason, when either side falls outside the level-size range or the rectangle would leave the venue extent. One undo step. Verify: unit test; widget test (offered and not offered).
- AC-104 [OA-4a-4] **Replace and remove.** A level has at most one backdrop (OA-1 §2.5.9). Choosing another file replaces it; **Remove** clears it. The old image's key is simply no longer named, and the server prunes it 24 hours after its upload (OA-2 AC-41); the panel says so. Verify: widget test.
- AC-105 [OA-4a-4] **PDF input (office §9; E-13 amended).** A chosen PDF is **rasterised in the browser** by a self-hosted `pdfjs-dist` (the Blueprint pin) with `eval` disabled, never loaded from a CDN; a page picker shows the pages; the chosen page is rendered to a PNG at the largest scale that keeps its sides inside the pixel limits, at most `BACKDROP_MAX_PIXELS` and within `BACKDROP_MAX_BYTES` (DC-E14), and that PNG goes through AC-99 and AC-100. The server never sees a PDF. An encrypted or damaged PDF gives a message and changes nothing. `isEvalSupported: false` and the CVE class are RECALLED and are checked in the plan's step 0 (§8). Verify: widget test (a fixture PDF: the page picker, the rendered size, an encrypted fixture); manual case.
- AC-106 [OA-4a-4] **Display.** The image is fetched **through the `ApiClient` as bytes** and drawn as a rotated image layer under the shapes at real scale (DC-E13: the stub identifies the caller by request headers, which a browser image element cannot send), cached by key (the bytes never change). ## 3. Edge cases

Each one gets a test in the plan, or a one-line reason why not.

**Offline or stale data**
- EC-1: The API is lost while the map loads: the error state with Retry (AC-58).
- EC-2: The API is lost mid-autosave: state error, the drawing is kept, "Try again" and the next change save again (AC-72). Nothing is half-written, because the server stores the whole document or none (OA-2 EC-2).
- EC-3: Another tab saved: the next autosave is a 409, the conflict stop (AC-71).
- EC-4: A draft saved under an older catalog version loads and saves unchanged (OA-1 EC-4; AC-78).
- EC-5: Another admin restored a version or cleared the draft: the draft's version moved, so the next autosave is a 409 (AC-71).
- EC-6: A backdrop's bytes are missing from the local folder (for example after `setup-db`): the level opens without the image, says so, keeps its calibration, and the editor's check E4 shows (AC-106).
- EC-7: A backdrop key was pruned (24 hours unused) and Undo brings it back: the save is refused with the problem for that level (OA-2 AC-19), shown by AC-72.
- EC-8: The tab is closed with unsaved changes: the browser's warning and a best-effort save; manual case only, because a widget test cannot close a tab (AC-73).
- EC-9: A shopper's package is never stale because of a draft edit: drafts reach no shopper until a publish (AC-131).

**Empty and maximum data**
- EC-10: A venue with no map: the empty state, Blank start, and (OA-4b-2) Import (AC-58, AC-59).
- EC-11: A draft after a clear: the same empty state; History still lists the published versions (AC-95, AC-96).
- EC-12: A level with nothing on it: the empty floor with its grid; the Checks panel's empty state (AC-92).
- EC-13: A venue with no building (an outdoor ground only): only the outdoor tab, no main building (AC-61, AC-144).

## 5. Scale targets

- **Venue size: up to about 100,000 m² per site** (PRD §7). The editor holds one document, up to `MAX_MAP_BYTES` (4 MiB, OA-1 AC-32; office §4.3), and draws one level at a time.
- **Routing graph: up to about 20,000 nodes per venue** (PRD §7). It bounds the full checks of OA-4c (AC-133).
- **Tenants: up to about 5 at the pilot** (PRD §7). **Peak concurrent admins: measured at the pilot** (PRD §7; Blueprint OQ1); **one editor per venue at a time** (L170 Q7; office's known limit), so no concurrency target applies to a single map.
- **The office caps, as named constants in the schema file** (OA-1 §2; each from office §4.2 unless noted): 10 levels, 10 buildings, 40 connectors, 2,000 walls, 2,000 openings, 300 units, 5,000 items, 2,000 corrections, 5,000 points of each kind a level, 64 points a polygon, a 300 m venue extent, and the document size. **The seeds exceed several of them** (Bayview Grand has 19 levels and a 1,300 × 760 m site; Aurora's site is 510 × 720 m; the four Demo Malls hold 66 levels, 2,320 units and 163 connectors): **OA-3 measures the mall values** (the largest seed × 2, rounded up; L170 Q15; OA-3 AC-23) and the editor reads whatever the generated constants say (AC-75, AC-120). Their values are not known at this revision, and OA-3's Q3 (the extent and elevation rule) is still open. The largest seeded venue holds about 400 stores (Aurora; L102), which bounds the Stores panel's list (AC-108).
- **Request and file limits:** the body 5 MB (`MAX_JSON_BODY`) with the document below it; a backdrop 15 MB, 50 to 10,000 pixels a side, 50 megapixels, 20 a venue, pruned after 24 hours (office §9; OA-2).
- **The editor's own office values** (office §8.3, §8.4): autosave 1.5 s, checks 400 ms, 100 undo steps, zoom 4 to 400 pixels per metre.
- **Editor timings: no target (A5; re-plan O9).** No document states a number, so load, frame time, autosave round trip, undo memory and the full-checks time are measured on the synthetic maximum document (AC-98), on the seed documents (AC-119) and on Aurora (AC-133), and recorded with no pass or fail.

## 6. Design choices in this spec

Each fills a gap no ruling covers and names an alternative that would also satisfy what is stated. They are listed at sign-off for the product owner's approval (L174); none is a product question.

- **DC-E1** The three stages are split into sub-slices (4a-1 to 4a-4, 4b-1, 4b-2, 4c), each ending in something visible in the browser (§1). *Alternative:* one slice per stage; each would hold 40 to 60 criteria.
- **DC-E2** Keys beyond office's: `P` for the polygon unit tool (L39's free polygon; office has only the rectangle and vertex editing), `B` for the row of stores (office's `B` is the desk block), and a key for the ramp tool and for each point and correction tool chosen in the plan without clashing with office's. *Alternative:* the rectangle and vertex editing only, with no polygon tool.
- **DC-E3** A new unit's category is `room`, which is not walkable under DC-8's map. *Alternative:* the admin must choose a category before the unit is created.
- **DC-E4** A door is linked to a unit from the unit's panel (AC-91), and a dragged value is rounded to the document's 3 decimals (r2 DC-4's reading). *Alternative:* link a door automatically to the unit whose outline it lies on.
- **DC-E5** A new opening is 0.9 m wide (office §4.2's example), or the wall's length when shorter. *Alternative:* the last width used.
- **DC-E6** Floor tabs are grouped by building, the outdoor level first, each building's levels highest ordinal first (r2 AC-1's order). *Alternative:* ascending, as office's tabs run.
- **DC-E7** The Blank start and Add floor defaults: a new floor takes the chosen building's highest level's size and origin, its elevation is that level's elevation plus its height, and its ordinal is the next free one above; the first floor of a blank map is ordinal 0 at elevation 0 (as OA-3's spike-shaped documents, OA-3 AC-18; an indoor ordinal 0 is allowed, because ordinals are distinct only within a building), and the next one in a building is ordinal 1. *Alternative:* no defaults.
- **DC-E8** The drawing tools are disabled in the conflict state. *Alternative:* the editor stays editable, and the changes are lost on Reload.
- **DC-E9** After an error the editor retries only on the next change or on "Try again". *Alternative:* a timed automatic retry.
- **DC-E10** Undo snapshots are immutable, structurally shared objects (a change copies only what it touches), not serialised JSON. Office stores JSON snapshots; 100 of them near the 4 MiB cap would be about 400 MB. *Alternative:* office's JSON snapshots with a byte budget that shortens the stack.
- **DC-E11** A closed-set field is a `text` `FieldSpec` carrying `closedSet: '<Set>'`, rendered as a select; a point's components are `size.0`, `size.1`, `origin.0`, `origin.1` in the lint's document mode. *Alternative:* a new `ColKind` for closed sets, and a schema that splits `size` and `origin` into two number fields (this changes OA-1's document).
- **DC-E12** Code-valued lookup fields use the lookup picker with `SelectOption.value` set to the **code**, because the document stores codes (OA-1 §3.5). *Alternative:* store ids in the document (rejected by the re-plan §1.2, because exports must move between databases).
- **DC-E13** A backdrop's bytes are fetched through the `ApiClient` and drawn from memory. *Alternative:* an image element with the URL, which cannot send the stub's headers.
- **DC-E14** A PDF page is rendered to a PNG at the largest scale inside the limits. *Alternative:* a JPEG, which is smaller but lossy for line drawings.
- **DC-E15** The `connector-types` lookup row carries read-only `costModel` (needed in 4a-2 to filter by kind) and, from 4b-1, `costBaseS` and `costPerRiseS`. A new connector's served levels default to the active level and the next one in its building. *Alternative:* a separate route for connector-type details (Q3).
- **DC-E16** The element list and the Stores panel list are searched in memory (the document is local; the venue's stores are bounded by its units). *Alternative:* the S9 paged list with server search, which is the standard's form for unbounded server lists.
- **DC-E17** A multi-selection edits no field in common. *Alternative:* edit shared fields (for example the finish) for all.
- **DC-E18** The editor's own checks are office §8.6's items 4 to 6 adapted (AC-92): unnamed non-walkable units, overlapping items, items inside walls, and the editor-only missing floor-plan image. They are exactly the checks P0-03 r4 leaves to the editor, and none is a P0-03 r4 finding kind. *Alternative:* also units overlapping units (office has no such check), or a unit counts as named when it holds a store (needs the stores, so from OA-4b-1 only).
- **DC-E19** A duplicate drops references to elements outside the selection. *Alternative:* keep them pointing at the originals.
- **DC-E20** A group rotates about the centre of the selection's bounding box (office says "centroid"); connectors are left out of group gestures. *Alternative:* the mean of the elements' centres; connectors move with the group and are refused at the edge of any served level.
- **DC-E21** A level's building and outdoor setting are chosen when it is added and shown, not edited afterwards. *Alternative:* a building picker in the floor panel.
- **DC-E22** Delete cascades keep what they can: a deleted unit's inner units are kept (their `parent` is cleared); a confirmation lists the rest (AC-88). *Alternative:* delete the inner units too.
- **DC-E23** "Start over" can be undone within the page. *Alternative:* Clear cannot be undone, and the confirmation is the only guard.
- **DC-E24** The editor's route and the file layout follow `plan/FF-10-map-editor.md` §5.2's `features/editor/` shape (service, view model, canvas and projection, tools, panels, element list, overlays), named in the plan.
- **DC-E25** History shows the version number and the time only (the server gives the publisher as a number). *Alternative:* OA-2 serves the publisher's name.
- **DC-E26** The editor is `/admin/map-editor/:venueId` under FF-SK's `/admin/:moduleId` route, with the query `?level=&select=&at=`; the module page `/admin/map-editor` lists the venues. *Alternative:* path segments for the level and the selection, or a route outside the module path.
- **DC-E27** The row of stores creates unnamed units only (no walls, doors or stores). *Alternative:* it also numbers the units.
- **DC-E28** Ids are `<prefix>-<6 base36>` with prefixes by kind. *Alternative:* longer random ids.
- **DC-E29** The `publishing` banner is refreshed on load and when Publish is pressed, not polled. *Alternative:* polling.
- **DC-E30** The store routes (OA-3 leaves them to OA-4, its §11): one list of the venue's stores with their key status (from OA-3 AC-11's loader), and a create-or-update keyed by unit key, a status change, a deactivate and a remove, each under the venue lock. The plan names the paths and bodies. *Alternative:* a paged list and per-store ids (S9's scaffold). Whether import's merge shares the writer is Q2.
- **DC-E32** Resizing a unit, a correction polygon, a footprint or the boundary scales its outline within its bounding box (the eight handles of AC-62). *Alternative:* edit vertices only, with typed width and depth for rectangles.
- **DC-E31** The main building changes only through "Make this the main building", a move in the list, or the delete dialog (AC-144); VENUE_EDITOR may use them (a draft edit; a publish is still an admin's). *Alternative:* a flag on the building, or only MALL_ADMIN and SUPERADMIN may change it.

## B3. r2's edge cases (withdrawn as a block; r3's are in §3, and §10.4 says where each r2 group went)

Each one gets a test in the plan, or a one-line reason why not.

**Offline or stale data**
- The API is lost mid-save: the error is shown, nothing is half-written (AC-27), no underlay file is kept from it (AC-8), and every unsaved change is kept (AC-31).
- The API is lost while a level loads: the error state with Retry; the other levels' unsaved changes are kept.
- The API is lost while the walkable area or the walkway preview loads: that overlay shows its error with Retry; drawing and unsaved changes are unaffected.
- The admin's loaded level is stale because another admin saved: their own save gets 409 naming the elements (AC-28). Reloading the level with unsaved changes asks first.
- The walkway preview is of the saved draft: after an unsaved edit it is labelled as not including it (AC-23); it refreshes after a Save.
- The tab is closed with unsaved changes: the browser's leave warning; after leaving, they are lost (DC-17), a chosen but unsaved underlay image included. Manual case only: a widget test cannot close a browser tab.
- A shopper's package is never stale because of a draft edit: drafts reach no shopper until a publish (AC-49).
- The underlay file is missing from the local folder (for example after `setup-db`): the serving route answers 404, the level opens without the image and says the plan image is missing; the calibration row is kept.
- An underlay replaced or deleted, and removing the old stored file fails after the Save commits (the file locked or already gone): the Save stays successful, the server log reports the file left behind, and no `StoredFile` row points at it (AC-8, AC-34, R15).
- A seeded venue's level created, edited or deleted in FF-1: the seeded boundary is kept, because the seeds set `BoundaryIsDrawn` TRUE (AC-24, R13).

**Empty and maximum data**
- A venue with no levels: the editor says to add a level in "Venues, buildings and levels" first, with a link (for a VIEWER, without the link).
- A level with nothing on it: the empty floor with its grid; the review list's empty state says "Nothing to review"; the walkway preview says there are no walkways.
- A venue with no buildings (outdoor ground only): only the outdoor chip.
- "Reset to cover the levels" on a venue with no levels: the zero-size rectangle, the flag cleared; publish refuses it (P0-01 AC-34).
- The largest seeded level (Aurora: 2,320 units across the venue, P0-03 EC-37) and the synthetic 100,000 m² venue: measured and recorded, no pass or fail (§5; A5).
- A polygon with three points (the minimum) is accepted; two distinct points, or a ring that does not close, refused (DC-5).
- Lengths at their maximum accepted, one more refused, counted in characters ("Parañaque" and other non-ASCII names), as P0-01: names 200, `SearchKeywords` 400, `SpokenName` 200, notes 200.
- Decimal limits: `DECIMAL(9,3)` coordinates and sizes up to 999999.999; `RotationDeg` 359.99 accepted and 360.00 refused; one decimal place too many refused when typed, never rounded silently (P0-01 AC-38); dragged values rounded to the column's scale (DC-4).
- A batch over 5 MB (`MAX_JSON_BODY`): 413 in the standard shape, nothing written, changes kept (AC-31).
- An underlay of exactly 10 MB accepted; one byte over refused by the client before sending and by the server (AC-8); an empty file refused.
- Hundreds of unreviewed elements (a whole floor from P1-03 later): the review list pages through the scaffold (AC-37).
- A level with thousands of elements loads in one response (DC-6); timing is measured and recorded (§5).
- A seeded object type has no default size: the size fields open empty and are required (AC-6).

**Tenant boundary**
- Another tenant's venue, level, element or stored file in a load, save, delete or file request: 404, nothing written (AC-48).
- Another tenant's lookup row, underlay file or level named in a batch: refused (AC-33, AC-8).
- A lift stop on a level of another venue of the same tenant: refused (AC-33).
- `X-Tenant-Id` for a tenant the acting user lacks: 403 (FF-0).

**Each role**
- VIEWER, VENUE_EDITOR, MALL_ADMIN, SUPERADMIN: client hiding per AC-46, one widget test each.
- A VIEWER's save, or a VENUE_EDITOR's store status change, sent directly (curl with `X-Dev-Act-As`) succeeds until R2. Not tested now: no role check exists before R2 (E-20, waiver 3); the ledger row records it.
- A VENUE_EDITOR without a grant on the venue: R1/R2's check; on the ledger.

**Permission denied**
- A 403 from the stub's header checks is shown through `formatApiError`, on the level load, the overlays, the file request or the save, never as raw text.

**Concurrent edits**
- Two admins change the same element: the second save gets 409 (AC-28).
- Two admins change different elements on one level: both saves succeed (each element's own `UpdatedAt`).
- One admin deletes an element another is editing: the other's save gets 409 naming it (the row is gone), and their values are kept.
- One admin deletes a never-changed store (no history row, R14) while another changes its status: whichever save is second gets 409 naming the store (AC-28); the store is either deleted or has one history row, never both.
- Two admins each add an active store to the same unit: the second save is refused with 409 naming the first store (AC-13, G7). G7 rules a service check with no index, so the plan names how the check holds when both saves run at the same moment.
- Two admins each choose an underlay for the same level: the second save is refused with 409, because the level already has an underlay or the one it replaces changed since (AC-28); its image is kept for a retry, and one level never holds two (AC-8). The plan names how the service holds the one-per-level rule against two saves at the same moment (no unique index exists on `FloorUnderlay.LevelId`).
- A level is deleted or resized in FF-1 while the editor has it open: a save naming the deleted level gets 404 with its unsaved changes kept; a smaller floor rectangle leaves shapes outside it, shown with a note, and only the venue boundary limits them, at publish (G11).
- A type or store status is deactivated while a panel is open: the save keeps the value (AC-44).
- A venue boundary drawn while another admin creates a level in FF-1: the drawn boundary is kept, because the flag is TRUE (AC-24, G4).

**Publish in progress**
- A save during a `BUILDING` publish succeeds and lands in the next version (AC-35).
- Publish pressed in the editor while another publish of the venue runs: the save goes through, then FF-3's screen shows "A publish is already running for this venue" (P0-03 AC-62).
- The walkway preview requested during a publish: answered from the saved draft, independent of the publish (AC-23).
- FF-10 never writes `VenueVersion` (AC-4).

**Invalid input**
- Each AC-32 and AC-33 case.
- A polygon that crosses itself: saved (only structure is checked at save, DC-5), and publish refuses it as "This shape can't be read" (P0-03 AC-18); the editor marks it on the canvas.
- A door away from its unit's outline: saved; publish's wall and reachability checks judge it (DC-7).
- A section outside its parent's outline: saved (G6).
- A shape beyond its level's floor rectangle: saved, shown with a note (G11).
- A stairs connector with both ends on one level, or without its To end: saved; publish refuses it (DC-19; P0-03 AC-15).
- `RiseM` blank on stairs, an escalator or a ramp: saved; publish refuses it (the rise trap; P0-03 AC-15d). The panel prefills it (DC-10).
- An element id that is not a positive integer in a batch or a URL: 400 or 404 before any query (P0-01 G4: id 0 refused up front).
- A malformed JSON body: 400 "Malformed JSON body" (`errors.js`).
- Unknown extra fields: ignored, never written, until R5's zod; a body `BoundaryIsDrawn`, `LogoFileId` or connector cost is ignored (AC-36, AC-13, AC-18).
- An underlay that is not PNG or JPG, is empty, or is over 10 MB: refused, naming the file (AC-8). A path-like file name: accepted as an image, but the name never reaches the storage key (AC-8).
- A section whose parent chain loops: refused (AC-26).

**Lookups**
- No active object types: the library is empty, and boxes and polygons still work.
- A tenant's own type and a platform type with one label: both offered (as FF-0).
- An element whose type was deactivated: AC-44.

## B6. r2's design choices DC-1 to DC-21 (withdrawn as a block; §10.2 gives each one's fate)

Each fills a gap no ruling covers and names an alternative that would also satisfy what is stated. **All twenty-one were accepted by the product owner on 2026-10-12 (A7, L165); DC-1 follows G5.**

- **DC-1** One canvas per level with all three P0 modes as tools; the underlay is a layer under the shapes. *Alternative:* the admin picks one mode per level.
- **DC-2** Snapping to `GridCellM` is on by default and a toggle turns it off; rotating by the handle is free, and an exact angle is typed in the panel. *Alternative:* rotation snaps to fixed steps.
- **DC-3** The server derives a box's `GeometryGeoJson` from its centre, size and rotation; a body geometry for a box is ignored. *Alternative:* the client sends both and the server checks they agree.
- **DC-4** Dragged coordinates are rounded to 0.001 m and dragged angles to 0.01°, the columns' scales; typed values follow P0-01 AC-38 (refused, never rounded). *Alternative:* refuse any dragged value with more places (unworkable with a mouse).
- **DC-5** At save, only structure is checked: the GeoJSON type per element (Polygon for units, polygon objects, `BLOCK_AREA`, the boundary and footprints; LineString for doors, `ADD_PATH` and `REMOVE_PATH`), a closed ring, at least three distinct points, finite numbers. Self-intersection and every wall, reachability and boundary rule stay with publish (the Panel rule; P0-03 AC-12 to AC-18). *Alternative:* full geometric validity at save.
- **DC-6** A level loads whole in one response (as P0-03's drawing route, D16). *Alternative:* load by viewport tiles.
- **DC-7** Doors snap to their unit's outline, and the server does not check that a door lies on it. *Alternative:* the server refuses a door off its unit's outline.
- **DC-8** `IsWalkable` defaults from the IMDF category through one map in the constants file (the seeds use walkway, parking and footbridge as walkable), and the admin can change it. *Alternative:* always chosen by hand.
- **DC-9** The walk-through mark is offered on non-walkable units only (a walkable unit is already walked through). *Alternative:* allowed on any unit and ignored by publish.
- **DC-10** `RiseM` is 0 or more, prefilled with the difference of the two levels' `ElevationM` (as the seeds do), and editable. *Alternative:* left blank until typed.
- **DC-11** Confirming keeps `DraftConfidence` (the package never carries it, D11). *Alternative:* set it to NULL on confirm.
- **DC-12** The editor's Publish saves first, then opens FF-3's screen (the Batched Save rule names Publish as a save point). *Alternative:* Publish is disabled while changes are unsaved.
- **DC-13** FF-3's problem rows gain "Open in editor" (built in FF-10 as P0-03 r3's FF-10 part, §L). *Alternative:* the admin finds the element from its level and name.
- **DC-14** A searchable element list per level, with a "needs review" filter, beside the canvas: the accessible way to select an element. *Alternative:* canvas selection only, with a separate review page.
- **DC-15** Mouse, trackpad and keyboard in a desktop browser first (PRD §3: Carla and Jun use a desktop browser); touch drawing is not a target. *Alternative:* full touch support.
- **DC-16** Underlay files go through P0-03's storage interface to the local git-ignored folder (D2), `StoragePath` a storage key, never a disk path; the move to Cloud Storage is P0-03's ledger row. *Alternative:* the Firebase Storage emulator.
- **DC-17** Unsaved changes live in the page only; leaving asks first. *Alternative:* keep a draft in the browser's storage across a closed tab.
- **DC-18** The boundary and footprints are shown on every level's canvas and edited from any of them (one frame per venue, E10). *Alternative:* a separate site view.
- **DC-19** An incomplete connector can be saved; publish refuses it (P0-03 AC-15). *Alternative:* refuse an incomplete connector at save, so work on a connector must finish in one go.
- **DC-20** A lift's From end is kept equal to its stop on the lowest-ordinal level by the server (the seeds put it on the first stop); the admin edits stops only. *Alternative:* From edited separately from the stops.
- **DC-21** Saving a building footprint or the venue boundary from the editor leaves the building's or venue's `UpdatedAt` unchanged, so FF-1's open forms are not made stale (P0-01 AC-34 does the same for the derived boundary; recorded in P0-01 r3, §L); the editor's own clash check for these two shapes uses a separate token the plan names. *Alternative:* they share the record's `UpdatedAt`, and an open FF-1 form gets a 409 after a footprint edit.

## B9. r2's questions and their rulings (history; §10.3 says what became of each ruling)

Each is tagged [spec-writer], with the recommended option first. Q1 to Q18 were ruled on 2026-10-12 (L165; `plan/FF-5-11-decisions.md`); their options are kept for the record. Q19 to Q21, new in r2, were ruled on 2026-10-12 (`plan/FF-5-11-residual.md`, APPROVED, R13 to R15).

**Q1 [spec-writer] How does a Save behave when two admins work on one venue?** **Ruled 2026-10-12 (G1): (a).** Applied in AC-27 and AC-28.
- (a) *Recommended:* one Save is one transaction, all or nothing. Each changed element carries the `UpdatedAt` it loaded (P0-01 B5's rule); if any changed since, the whole save is refused with 409 naming them, and the admin keeps every unsaved change. Leaving with unsaved changes asks first. Simple and predictable; the same rule as FF-1.
- (b) Each element is saved on its own within the batch; the ones that clash are reported and the rest are kept. Fewer redos, but a level can end up half-changed.
- (c) One admin per level at a time: opening a level for editing takes a lock with an expiry. No clashes, but a forgotten tab blocks others.

**Q2 [spec-writer] Undo in the editor?** **Ruled 2026-10-12 (G2): (a).** Applied in AC-30.
- (a) *Recommended:* Undo and Redo through the unsaved changes, plus "Discard changes". Drawing without undo is slow to correct, and the unsaved batch is already held in the page.
- (b) "Discard changes" only; undo later.

**Q3 [spec-writer] How does the admin see the derived walkable area and the walkways while correcting?** **Ruled 2026-10-12 (G3): (a), built by engine-coder (A25) as P0-03 r3's FF-10 part.** Applied in AC-21 to AC-23.
- (a) *Recommended:* a read-only server route per level returns the derived walkable area and, on request, a preview of the walkways generated by the publish engine's own code for the saved draft, with nothing stored. One derivation, no Dart copy (One Router's spirit).
- (b) The walkable area from a server route; walkways only from the last published version (P0-03's drawing route with `versionNo`).
- (c) Both only after a publish.

**Q4 [spec-writer] Once the admin draws the venue boundary, does a level change still replace it?** **Ruled 2026-10-12 (G4): (a); schema 0.15 and P0-01 r3.** Applied in AC-24; the seeded venues' starting value is Q19 (ruled R13: TRUE).

- (b) No migration: the service stops deriving when the stored boundary differs from the rectangle it would derive. Fragile: a drawn rectangle that happens to match is overwritten.
