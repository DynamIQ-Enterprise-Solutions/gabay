## 1. What this spec covers

1. **The position source** (`lib/core/positioning/`): one `PositionSource` per open venue (A8). It gives the shopper's position and its confidence state, and it is the only origin for routes and for "nearest". It replaces P0-04's internal "Start here" tool (ruling A1 of round 1). It decides between a hand-set position and a later live fix (L106, as ruled by A8), and it exposes the state that P0-14's hedging reads (L99, L113).
2. **"Where are you?"** (`lib/features/shopper/locate/`): the sheet that opens when the shopper enters a venue, from the set-location (pin) button, and from Go with no position (C2). In it the shopper can:
   - search for a shop, entrance, lift or landmark;
   - describe where they are, typed or spoken (P0-08 owns the description rules on top of P0-05's search service, A9);
   - pick a floor, which gives an approximate dot that a tap refines.
3. **The hand-offs:**
   - a new position works out an active route again (P0-06);
   - a place picked from the sheet gives P0-13 a calibration sample (L107, DC18, C3);
   - a new hand-set position asks P0-13 to re-seed its estimate there (A8);
   - the sheet can be opened with a reason, for callers that open it because the shopper is not where the app expected (P0-06 r4 off-route; P0-14 and P0-15 "No, I'm somewhere else"; P0-13's grey offer; P0-09's outside card).

**On the Demo Malls test maps (§G1, L160)** this is the main way a route gets a start. Those venues have no beacons, so the source there only ever reports `none`, `approximate` or `handSet`. On real venues (the penthouse, MEZZ office) the live dot (P0-13, FF-9) joins the same source.

**P0-06 r4** is built in FF-6 beside this spec (§9). Its parts are not this spec's acceptance criteria.

## 2. Definitions

- **Position:** a point (x, y) in the venue's one planar frame (E10), a level, and the package version it was set on. It is not snapped. P0-06 snaps it by RG3 when it uses it as an origin (P0-06 AC-8, AC-9).
- **Confidence state (A8):** one value of a closed, code-owned set of six, held in the one constants file that FF-5 creates (A26: a JSON file read by the API and, through a generated Dart file, by the app), with its authority comment (Blueprint §4.3):
  - `none`: no position;
  - `approximate`: from a floor pick (PRD §6.8);
  - `handSet`: from a picked place, a picked door or a refining tap; later also from P0-14's "Yes" at a ride's foot or to the floor question (FF-7, D4) and P0-15's "Stop guiding" (FF-8, E11);
  - `liveConfident` and `liveUnsure`: from P0-13 (FF-9). Grey is `liveUnsure` with P0-13's grey flag (A8, DC-13);
  - `guided`: from P0-15's guided walk (FF-8, L118).

  In FF-6 only `none`, `approximate` and `handSet` are produced by real code. The others are defined now so that P0-13, P0-14 and P0-15 add producers and readers, not values.
- **Boundary status:** P0-09's separate value (unknown, inside, outside; P0-09 AC-8), published beside the confidence state. It is **not** a seventh confidence state (A8). P0-09 builds it in FF-8; in FF-6 the source reads it through an interface that tests fake.
- **Route origin (A8):** every state except `none` and grey. `liveUnsure` without the grey flag is an origin; grey is not.
- **Hand-set:** a position the shopper gave: a picked place, a picked door, a refining tap, or (later) the producers named above.
- **Place:** anything the sheet can list. The package (`spec/P0-03.md` §3.7, with r3's additions built in FF-5, A10) holds:
  - active occupants, including nested sections;
  - amenities;
  - transit points;
  - anchors (landmarks). They are listed here, though P0-05's destination search leaves them out (B6);
  - venue entrances (`Opening.IsVenueEntrance`), named by `Opening.Name`, else "Entrance, ⟨level⟩" (A10);
  - connector stops and ends: a lift's stop on each level it serves, and an escalator's, stairs' or ramp's end on each of its two levels, named like "Lift A · Level 2" (A10).

  Until P3-02, evacuation-only connectors and the refuge and assembly amenity types are left out of the search index (P0-03 r3 as ruled, R28, R29), so the sheet does not list them.
- **Door node:** the graph node where a place joins the walkway. For a store this is one of its doors (a store with several doors: AC-32). For a point place (an amenity, transit point or anchor) it is its attachment node. For a venue entrance it is the entrance node. For a connector it is the node of its stop or end on that level (P0-03 AC-25; P0-06 §3 item 4).
- **Name match:** a query whose text finds places through the FTS5 index (P0-05's search service over the package, A9). Accents are ignored both ways: "nino" finds "Niño" and "Niño" finds "Nino" (A10, P0-03 r3).
- **Description:** a query that finds no place by name. Its words are matched one by one: a word that names a place, a category, a facility or a connector counts; words that only say where something is ("near", "beside", "malapit", "tabi") are ignored; a word naming a floor narrows the list to that floor (PRD §6.8; the demo's `_described`). The word lists are ARB strings, and every shipped language's lists are read whatever the app's language (A12, R4; AC-13).
- **This floor:** the level named in the query; else the level of the current position; else the level shown on the map (DC-11).
- **Calibration pick:** the record handed to P0-13 when the shopper picks a place from the sheet (AC-26).
- **Re-seed request:** the record handed to P0-13 when a hand-set position is set (AC-34).

## 3. Settled context

- **E-20 (L153):** no admin route and no API call. Everything here runs on the phone, from the held package. Items 3, 4 and 9 of §5: see §10.
- **No QR (L107):** no scanner, no codes, no camera permission. A known spot comes only from search, a description, a tap or a floor pick (PRD §6.8). `mobile_scanner` and E-11 stay withdrawn.
- **Takeover (L106, as ruled by A8 and R6):** a live-confident fix takes over a hand-set position only if it is inside the boundary and comes after P0-13 has re-seeded its estimate at the hand-set spot. An approximate position (a floor pick) needs no re-seed: the first live-confident fix inside the boundary takes over (R6). A held hand-set position beats a live-unsure one. During a guided walk a live fix is offered, never taken (FF-8, E16). The internal "Test position" tool ("Walk the route", "Put me here") is the position source while it is switched on, and the takeover rule does not apply to it (R9).
- **Hedging (L99, amended by L113):** P0-14 reads the state:
  - places and surroundings are always worded suggestively, whatever the state;
  - the pause, foot-of-ride and arrival checks run only when the state is `handSet`, `approximate`, `liveUnsure` or `guided`;
  - every ride ends with the floor question, whatever the state.
- **Calibration (L107; PRD §6.9; Blueprint §4.3, DC18; C3):** every "I'm near here" pick in the sheet calibrates the phone, by name or description, typed or spoken. The pick is weighted by the place's size, and a place wider than `calibration.maxPlaceM` (6 m) does not count. P0-13 computes and applies the offset. This spec only hands over the pick.
- **Privacy and foreground (invariants 4 and 5; G3):** no position, query, calibration value or re-seed request leaves the phone. Nothing runs in the background.
- **Permissions (PRD §6.8, §6.23, §6.4; Apple 5.1.1(iv)):** everything here works with Bluetooth, location and the microphone denied.
- **The route split (A2 of round 1; A14):** P0-04 owns the sheet container, the place sheet with Go, the map drawing and the level chips; its r3 lists the set-location button on the rail and the dot's fallback looks this spec defines (§L). P0-06 owns the route section and its ViewModel, and r4 draws the direction card and "I've arrived". This spec adds the position source, the "Where are you?" sheet, the door choice, the set-location button and the dot's two fallback looks.
- **"Start here" (A1 of round 1):** P0-08 removes it. The build-time internal-tools flag stays, because the role picker, Test tools (FF-SK) and the later "Test position" tool (A16) use it.
- **Limits (A6):** the near-connector distance (15 m), the most rows (8) and the approximate ring (25 m) stay named constants.

## 4. Acceptance criteria

### 4.1 The position source

AC-1: One `PositionSource` per open venue exposes the current position (or none) and its confidence state (§2) as a stream. Every new value reaches every reader in order: the route ViewModel, the map, "nearest" (P0-05) and, later, P0-09, P0-14 and P0-15. Verify: unit.

AC-2: In FF-6 the source starts at `none` when a venue opens. It becomes `approximate` on a floor pick (AC-15) and `handSet` on a picked place (AC-14), a picked door (AC-32) or a refining tap (AC-16). No other value is produced by FF-6's real code; the other states come only from fakes in tests. Verify: unit.

AC-3: The route origin and the "nearest" origin come only from the `PositionSource`. P0-04's "Start here" long-press and its handler are removed from every build. The internal-tools flag stays, with its other tools, and is still listed in invariant 16's registry (A1 of round 1; P0-04 AC-50, AC-55). FF-8's "Put me here" (A16) will be a producer feeding this source behind the same flag; like "Walk the route", it is the position source while switched on, and AC-4's takeover rule does not apply to it (R9). Its plan names the change to this criterion's test (C1). Verify: widget (flag on: a long press sets no origin in FF-6); review.

AC-4: **Takeover (L106, as ruled by A8).**
- From `none`, the first live value is taken, `liveConfident` or `liveUnsure` (grey included; grey is a position but not a route origin).
- While the state is `handSet`, a `liveConfident` value replaces the position only when (a) P0-09's boundary status for it is `inside` (unknown and outside do not count) and (b) it follows the latest re-seed request (AC-34): it carries that request's sequence number or a later one (DC-17). The state becomes `liveConfident`.
- While the state is `approximate`, the first `liveConfident` value whose boundary status is `inside` replaces the position. No re-seed is needed: an approximate position emits no re-seed request (AC-34), and the value's re-seed number is not checked (R6).
- A `liveUnsure` value, grey or not, never replaces a `handSet` or `approximate` position.
- A new `handSet` or `approximate` position set by the shopper replaces any live state.
- While the state is `guided`, a live fix is never taken: it is handed to P0-15's offer (FF-8, E16).
- While the internal "Test position" tool is switched on ("Walk the route" from FF-7, "Put me here" from FF-8), it is the position source: the bullets above do not apply to its values, and live values are not taken while it runs (R9; P0-13 AC-56).

In FF-6 the live source and the boundary status are fakes (P0-13 supplies the real live source in FF-9, P0-09 the real status in FF-8). Verify: unit (a fake live source and a fake boundary status).

AC-5: A position belongs to one venue and one package version. Opening another venue clears it to `none` (P0-04 EC-35). A position is never saved across a restart, so after a restart the state is `none` and the sheet opens (AC-7). Verify: unit (a fake preferences store sees no position key); widget.

AC-6: No position, query, transcript, calibration pick or re-seed request is sent anywhere or written to disk by this feature (invariant 4, G3). Verify: unit (a failing HTTP client is never called; a fake preferences store records no write); the `position-privacy` lint; the review privacy pass.

### 4.3 Search and description

AC-11: The search field is the shared `DebouncedSearchField` (rule 7; no bare `TextField`), with the hint "Type a shop, or describe where you are". Verify: widget; the `no-bare-textfield` lint.

AC-12: A name match lists places from P0-05's FTS5 search service over the open package (A9). In Aurora:
- "cr" and "comfort room" each list restrooms (P0-03 AC-43);
- a store's name lists that store;
- a nested section lists the section (PRD §6.5);
- an entrance lists by its name, else as "Entrance, ⟨level⟩" (A10);
- "lift" or a lift's name lists its stops, one row per level ("Lift A · Level 2"; A10);
- a landmark lists by its name (B6).

Ranking (DC-4, accepted by A7):
1. the name equals the query, then starts with it, then contains it, then other FTS5 hits;
2. within each, this floor first;
3. then the shorter name.

P0-07's accessible-restrooms-first order (A11) is not applied here: A11 names P0-05's destination lists, and this sheet lists where the shopper is, not where to go. Verify: integration (the published Aurora package, once P0-03 r3 is in); unit (ranking on fixtures).

AC-13: When nothing matches by name, the query is read as a description (PRD §6.8; the demo's `_described`; P0-08 owns these rules, A9):
- each word that names a place, a category, a facility or a connector counts. Place words come from each type's label and its `SearchSynonyms` in the package, through the same index (A12);
- filler words are ignored. A word naming a floor ("2nd", "ground", "ikalawa", "level 2", a level's short name) sets this floor. Level words are matched in the app (A10);
- a place by a named lift, escalator or stairs counts: its door node lies within the near-connector distance (DC-9) of that connector's stop or end on the same level, and it is listed as "near ⟨connector name⟩" (L99). A connector is named by its own name or by a connector word ("escalator", "hagdan");
- results are ordered by the number of words matched, then this floor first, then (when a position exists) the nearest by straight-line distance from it (DC-4).

The filler, floor and connector word lists are ARB strings, one key per list, per language (A12). A query is read against every shipped language's lists, whatever the app's language, so Taglish works (R4). The Filipino lists are drafted in FF-6 and reviewed with FF-7's Tagalog; only the lines the product owner approves merge (R4; §M item 3), so in FF-6 the mechanism is proven with fixture lists. Verify: unit, with at least these queries on fixtures:
- "near the ATM beside the escalator";
- "malapit sa CR" (with a Filipino filler list, "malapit" and "sa" are ignored and restrooms are listed, whatever the app's language; FF-6 with a fixture list, FF-7 with the approved `app_tl.arb` lists);
- "2nd floor ATM";
- "jollibee" (a name match, so it is not treated as a description);
- "near the" (filler only, so nothing).

AC-14: Each result row shows:
- its number on screen (1, 2, 3 …; for spoken ordinals, AC-33);
- the place's category icon and name;
- its level, and its building when the venue has more than one;
- "near ⟨connector⟩" where AC-13 applies;
- the action "I'm near here".

At most 8 rows are shown (the demo's limit; DC-5, a named constant by A6). Tapping "I'm near here" on a row whose place has one door node on its level:
- sets a `handSet` position at that door node;
- switches the map to that level and moves the camera there;
- closes the sheet.

A place with several door nodes goes to the door choice (AC-32). Verify: widget; unit (the position set).

AC-32: **Which door (C1).** Tapping "I'm near here" on a place with more than one door node on its level:
1. closes the sheet, switches the map to that level and frames the place's doors;
2. marks each door, named by its `Opening.Name` when set (in the allow-list from P0-03 r3, A10), else "Door ⟨n⟩" in the package's order;
3. shows a banner "Which door are you near?" with Cancel.

A tap on a door's mark sets a `handSet` position at that door's node, emits the calibration pick with that door (AC-26) and ends the choice; a pending route then starts (AC-31). Until then the position is unchanged. Cancel reopens the sheet with the query and its results kept. A tap anywhere else on the map does nothing, and pan, pinch and rotate still work (DC-15). Verify: widget; unit (the door used).

AC-15: **Pick your floor.** Under the results, "Or pick your floor" shows one chip per level of the venue, grouped by building when there is more than one, and the outdoor ground included. The chip of this floor is marked. Picking a chip:
1. sets an `approximate` position at the walkway point nearest the centre of that level's walkways (DC-2);
2. shows that level;
3. closes the sheet;
4. starts refine mode, with the banner "Approximate · tap the map where you are" and a Done button (the demo's banner).

Verify: widget; unit (the point chosen).

AC-16: **Refine.** In refine mode, a tap on the shown level sets a `handSet` position at the tapped point, through the exact inverse projection (P0-04 AC-38, the tilted-tap trap). The tap goes to the position, not to a pin under it (DC-8). The camera does not move, and refine mode ends. Done ends refine mode and keeps the approximate position. Pan, pinch and rotate still work in refine mode. A tap beyond the venue boundary: EC-15 (A24). Verify: widget; unit (a tap at a known screen point gives the expected venue point).

AC-17: The sheet has four states:
1. **idle:** an empty query, so only the floor chips and the mic are shown;
2. **results;**
3. **nothing found:** "Nothing found. Try another name, or pick your floor." (the demo's line);
4. **search unavailable:** the package's index cannot be read. It shows "Search isn't working on this map. Pick your floor instead." and the floor chips stay usable.

Verify: widget (each state).

AC-18: The query is bound as a parameter to the FTS5 `MATCH`, after FTS5's own syntax characters and operators (quotes, `*`, `-`, `^`, parentheses, `AND`, `OR`, `NOT`, `NEAR`) are neutralised. It is never interpolated into SQL (the phone-side form of rule 3). A query made only of such characters gives "nothing found", never an error. Verify: unit (a table of hostile queries). The FTS5 syntax list is RECALLED (§8).

AC-19: **Spoken.** A "Say where you are" button uses P0-05's voice input as FF-5 builds it (A9):
- recognition on the phone first, and the L116 question before audio leaves the phone, with P0-05's remembered answer per recognition language (B5);
- one phrase, English or Filipino;
- the microphone listens only after the tap.

The transcript fills the field, and the results follow as for typing. Spoken ordinals pick a row (AC-33). The spoken read-back of the results comes with P0-14's voice in FF-7 (A13). Without a recogniser, or with the microphone denied, the button explains why and typing still works (PRD §6.23). Verify: widget (a fake recogniser: a transcript, denied, unavailable).

AC-33: **Ordinals (A13).** After spoken results, P0-05's ordinals ("the first one", "the second one", "the third one", "una" and the rest, as FF-5 builds them) pick that numbered row, as a tap on its "I'm near here" would (AC-14, AC-32), calibration pick included (AC-26). An ordinal with no earlier spoken results, or beyond the rows shown, is read as an ordinary phrase (P0-05's rule). Verify: unit (a fake recogniser).

### 4.4 The dot and the map

AC-20: The position is drawn above the scene (P0-04 AC-39):
- `handSet`: the dot with a dashed ring (PRD §6.9; P0-04 AC-55's look);
- `approximate`: a large dashed ring around the dot. Its radius is a named constant, the demo's 25 m (DC-3, A6).

Colours come from `gabay_tokens.dart` in light and dark (rule 6). The dot is drawn only on its own level in FF-6. P0-13 adds the faded dot on other levels for every state. P0-04 r3 records these looks in its drawing (§L). Verify: widget (screenshots light and dark); the `colour-literals` lint.

AC-21: Once a position exists, Recentre is shown and returns the camera to it (P0-04 AC-40, E8). The level chip of the position's level is marked, and the screen reader says "you are here" (PRD §6.4, §6.23). Verify: widget.

### 4.5 Routes and "nearest"

AC-22: With a route origin (§2: any state but `none` and grey; A8), Go on a routable place asks P0-06 for a route from it (P0-04 AC-45; P0-06 AC-35). With no route origin, Go follows AC-31. An origin that cannot be snapped gives P0-06's "can't start from here" (P0-06 EC-10, EC-11). Verify: widget (a fake router receives the position; a fake grey value opens the sheet).

AC-23: **A new hand-set or approximate position works out an active route again** (PRD §6.8):
- the route goes to the same destination, from the new position;
- the trip stays active and the sheet stays open;
- the other way is chosen again;
- only the newest result is shown (P0-06 EC-16).

This replaces P0-06 DC-12's Start-here case. A new position at the destination's door gives P0-06's "already here" result (P0-06 EC-8). A live takeover does not work the route out again (P0-13 DC-9, accepted by A7), and nothing re-routes while the dot is grey (P0-06 r4, §L). Verify: unit (the route ViewModel); widget.

### 4.6 Hand-offs to P0-13 (L107, DC18, A8)

AC-26: **Calibration pick (C3).** Every pick of a place in the sheet emits one calibration pick to a calibration sink: an "I'm near here" tap on a one-door place (AC-14), a door tap in the door choice (AC-32), or a spoken ordinal (AC-33), whether the place came from a name match or a description, typed or spoken. For a several-door place the pick is emitted at the door tap, not at the row tap. The pick holds:
- the package version, the place's id and kind, and its level;
- the door point used;
- the place's size in metres (DC-10);
- a monotonic time stamp.

A floor pick, a refining tap or a cancelled door choice emits none. In FF-6 the sink has no consumer, and P0-13 (FF-9) consumes it. The weighting, the 6 m cut-off (`calibration.maxPlaceM`) and the offset are P0-13's (P0-13 r2 widens its AC-38 to every pick, per C3). Verify: unit (a fake sink: one pick per place or door pick, none per chip, refining tap or Cancel).

AC-27: A calibration pick or a re-seed request is never sent, logged with its values or written to disk by this feature (invariant 4). Verify: unit (as AC-6).

AC-34: **Re-seed request (A8).** Every new `handSet` value, whoever produces it (this sheet now; P0-14's "Yes", D4, and P0-15's "Stop guiding", E11, later), emits one re-seed request to a re-seed sink. The request holds the spot, its level, the package version and a sequence number that rises with each request (DC-17). In FF-6 the sink has no consumer; P0-13 (FF-9) consumes it and defines the re-seed. An `approximate` value emits none (R6). Verify: unit (a fake sink: one request per hand-set value, with rising numbers; none for a floor pick).

## 7. Design choices (not requirements; each with an alternative)

DC-1 to DC-14 were accepted by the product owner on 2026-10-12 (L165, A7). DC-15 to DC-17, new in r2, were accepted on 2026-10-12 (residual sheet R8).

- **DC-1 One `PositionSource`, provided by Riverpod, that decides between producers** (fallback now; live in FF-9; guided in FF-8). *Alternative:* a separate provider per producer, with a selector in each reader. That would be better if the producers never competed, but L106 and L118 make them compete, so one place should decide. (A8 confirms one source.)
- **DC-2 The approximate point** is the walkway point nearest the centre of the bounding box of that level's walk edges (the demo uses the level's centre). A level with no walk edges gets no point (EC-5). *Alternatives:*
  - the walkway point under the camera's centre, better if shoppers pan to where they think they are before picking;
  - the level's most central venue entrance.
- **DC-3 The approximate ring's radius** is a named constant, 25 m (the demo's; A6). *Alternative:* a `GlobalSetting` sent in the public mall list. That is better if malls of very different sizes need different rings.
- **DC-4 Ranking** (AC-12, AC-13): name-match quality, then this floor, then the shorter name; for descriptions, words matched, then this floor, then straight-line distance from the current position. Straight line is used here because it orders candidates and is not shown. L103's "every distance shown" rule is kept. *Alternative:* P0-05's cached walking distance. That is more faithful to L103, but it needs a position, and the sheet is often opened without one.
- **DC-5 At most 8 rows** (the demo's; a named constant, A6). *Alternative:* a scrolling list of every match. That is better if shoppers often fail to find their place in the top 8.
- **DC-6 A position is not saved across restarts** (PRD §6.4's list of saved state does not include it; an active route is not restored). *Alternative:* save the last hand-set spot per venue. That is better if shoppers often reopen the app on the same spot.
- **DC-7 A package swap keeps the point if its level still exists** (EC-3). *Alternative:* always clear the position on a swap. That is simpler, but swaps happen only between trips, and asking again after every republish adds friction.
- **DC-8 In refine mode, a tap sets the position, on the shown level, even over a pin** (the demo's precedence). *Alternative:* a pin tap opens its sheet and only taps on open floor refine. That is better if shoppers often refine to a shop's door, which "I'm near here" already covers.
- **DC-9 Places "near" a named connector are those within 15 m** of its stop or end on the same level (the demo's `seeM`), as a named constant (C8; A6). *Alternative:* a `GlobalSetting`.
- **DC-10 A place's size for calibration** is the longer side of its outline's minimum bounding box. A store uses its unit's outline. An amenity, transit point or anchor uses its unit's outline when it has a `UnitId`, else 0 m (a point). An entrance or connector uses 0 m. *Alternative:* the outline's area converted to an equivalent width. That is better if odd-shaped stores (an L-shape) skew the longer side. P0-13 may restate this when it consumes the pick.
- **DC-11 "This floor" falls back to the level shown** when there is no position. *Alternative:* no floor preference without a position. That is simpler, but the shopper usually opens the floor they are on.
- **DC-12 A new position keeps a trip's "Find another way" avoidance** (EC-25), by analogy with PRD §6.6's off-route refresh. *Alternative:* clear the avoidance on a hand-set position, on the view that the shopper restarted. That is better if a new position usually means a new plan.
- **DC-13 The grey dot is `liveUnsure` with a grey flag** that P0-13 sets, not a seventh state (confirmed by A8). *Alternative:* a separate `liveGrey` state, better if P0-14's wording ever differs between unsure and grey.
- **DC-14 The query is cut at 200 characters** (the longest place name the schema allows, `VARCHAR(200)`). *Alternative:* 400, the `SearchKeywords` length.
- **DC-15 (new in r2; Accepted, R8) The door choice's details** (AC-32): the position is unchanged until a door is tapped; Cancel reopens the sheet with the query kept; a tap off a door mark does nothing; doors without a name are numbered in the package's order. C1 rules what the choice asks, not these details. *Alternative:* a list of the doors inside the sheet ("Door 1 · near ⟨nearest other place⟩"), with the map only as a preview. That is better if door marks on a far-zoomed map prove hard to tap.
- **DC-16 (new in r2; Accepted, R8) A pending destination from Go is dropped when the sheet closes without a position** (AC-31, EC-46). C2 says the route starts "once a position is set" but not for how long Go's place is held. *Alternative:* hold it until the next position from any source (a later pin-button pick, a live fix) and start the route then. That is better if shoppers often close the sheet and set the spot a moment later, but a route starting long after Go would surprise them.
- **DC-17 (new in r2; Accepted, R8) Each re-seed request carries a rising sequence number, and each live value carries the number of the latest request P0-13 has applied** (AC-4, AC-34). The source takes over a hand-set position only with a value at or above its latest number; an approximate position needs no re-seed, so the number is not checked there (R6). A8 rules that the takeover waits for the re-seed, not how the source knows. *Alternative:* P0-13 sends a separate "re-seeded" signal and the source ignores live values between a hand-set and that signal. That is simpler for the source but loses the link between a value and its re-seed if two hand-sets come quickly. P0-13 may restate this when it consumes the request.

## 8. RECALLED claims (each checked against its docs before it is load-bearing in the plan)

- The FTS5 query syntax: which characters and barewords (`AND`, `OR`, `NOT`, `NEAR`, `*`, `^`, `-`, quotes and parentheses) are operators, and that wrapping each token in double quotes, with internal quotes doubled, makes it a literal string (sqlite.org/fts5.html).

- `speech_to_text` with `onDevice` fails on a phone that cannot recognise on the device (Blueprint OQ11 cites pub.dev). This is P0-05's to check; this spec only reuses it.

- ARB (`intl`/`gen-l10n`) carries a word list as one string per key, which the app splits; the separator and its escaping are the plan's to check against the `gen-l10n` docs (AC-13, A12).
- The app can read another locale's ARB strings at run time, so every shipped language's lists are read whatever the app's language (R4; the same claim as P0-05 §9).
