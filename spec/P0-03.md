## 1. What this delivers

*(r4: read the next paragraph through the r4 note above. Where it says the server "refuses and lists every problem", r4 refuses only the four blocking conditions of Q2 and lists everything else as warnings with a published result. The graph is generated from the document, and the package is built behind OA-2's builder port.)*

A mall admin presses **Publish** on a venue in the admin page. The server checks the venue and does one of two things:
- It refuses, and lists every problem in plain words, each one shown on a flat map of its level.
- It generates the walkway graph, costs the connectors, joins the walk-through stores and marks passages, and writes one immutable package file with its SHA-256 as a new `VenueVersion`.

Shoppers' apps download that package later (P0-04). Nothing here runs on a phone.

## 3. Acceptance criteria

Terms used below (r3's; **§3.14.0 gives r4's reading of them**):
- **Place:** an active `Occupant` (through its unit's doors), an `Amenity`, a `TransitPoint` or an `Anchor`. All four must be reachable (ruled D5). *[r3 · FF-5]* Until P3-02, an amenity of one of the two evacuation types is not a place for the reachability check (AC-88; R29).
- **Element:** any row of `Unit`, `Opening`, `FloorObject`, `Amenity`, `TransitPoint`, `Anchor`, `NavConnector`, `NavConnectorStop`, `Beacon` or `NavCorrection` of the venue.
- **Wall (ruled D4):** each edge of a non-walkable unit's outline is a wall, except where one of that unit's `Opening`s sits on it. The outline of a floor object with `BlocksWalk` also counts as a wall for the crossing check.
- **Problem:** a reason publish refuses. **Warning:** a reason it reports without refusing.

### 3.1 Running a publish

- AC-1: **[Withdrawn in r4; replaced by AC-119, with OA-2 AC-24 to AC-27 for the steps and the state machine.]** A publish request for a venue of the request's tenant runs these steps in order: validation, graph generation, connector costing, walk-through stores and passages, then the package. It ends one of two ways: **published** (a new `VenueVersion` with `Status = 'PUBLISHED'`) or **refused** (the full problem list). The request waits until the publish ends, with no background job (ruled D3). Verify: integration (API against the seeded database).
- AC-2: **[Withdrawn in r4; replaced by AC-119. The rule "a refusal leaves no row and no file" is kept there, but a refusal now lists only Q2's blocking findings.]** A refused publish leaves no `VenueVersion` row of any status and no package file (ruled D3). Its problems exist only in the response. The response lists every problem found in that run, none dropped (DC-1). Each problem carries a kind, a plain-language message, its level, and the element it concerns and/or a location in level metres. `FAILED` is used only for build errors after validation (AC-9, AC-10). Verify: API.
- AC-3: **[Withdrawn in r4; replaced by OA-2 AC-26 (the row's fields, written by OA-2) and AC-118 (what the engine hands back).]** A published version's row has:
  - `VersionNo` = the venue's highest existing `VersionNo` + 1 (DC-8);
  - `PackageFileId` pointing at a `StoredFile` row with `Purpose = 'PACKAGE'` and the request's tenant;
  - `PackageSha256` as 64 lowercase hex characters;
  - `PackageFormatVersion` = the format constant (1 for the first format);
  - `NodeCount` and `EdgeCount` equal to the package's graph;
  - `PublishedAt` in UTC;
  - `PublishedBy` and `CreatedBy` = the stub's actor user id.

  Verify: integration.
- AC-4: `PackageSha256` equals `StoredFile.Sha256`. Both equal the SHA-256 of exactly the bytes the storage holds, and the test recomputes it on its own from those bytes. Nothing is hashed before or after any other step: not before a compression step, and not as re-encoded for HTTP. This agrees with P0-04 AC-6, where the served bytes' SHA-256 equals `PackageSha256`. Only whether the stored bytes are gzipped is [S2: provisional] (§2). Verify: integration.
- AC-5: Publishing never updates or deletes a `PUBLISHED` row. A correction is always a new version (invariant 3; the frozen-row trap). A test publishes the same venue twice and checks that version 1's row is unchanged. A direct `UPDATE` of it still raises `TR_VenueVersion_Frozen`'s error. Verify: integration.
- AC-6: A new publish leaves every earlier version's package file byte-identical and readable (PRD §6.3: a shopper keeps the old version until the new one is verified). Verify: integration (hash before and after).
- AC-7: **[Withdrawn in r4; replaced by OA-2 AC-24, which keeps the 409 and its message.]** While a publish of a venue is `BUILDING`, a second publish of the same venue is refused with HTTP 409 and the message "A publish is already running for this venue". The refused request creates no row and no file. Publishes of two different venues do not block each other. Verify: API (two concurrent requests).
- AC-8: **[Withdrawn in r4; replaced by OA-2 AC-26 and AC-28 (the layout is captured under the venue lock) and AC-117 (the stores and beacons are read in one snapshot).]** The package reflects the venue's draft at one moment (DC-2). An edit committed while a build is running is not in that version; it is in the next one. Verify: integration (an edit injected mid-build through a test hook).
- AC-9: **[Withdrawn in r4; replaced by OA-2 AC-27 (the FAILED row, no partial file, the 500) and AC-118.]** A failure after validation passes (for example, the file cannot be written) has these outcomes:
  - the row ends `FAILED`;
  - no partial package file is left;
  - the response is a 500 in the standard error shape with the request id and no raw exception text;
  - the venue's latest `PUBLISHED` version is unchanged.

  Verify: integration (fault injected).
- AC-10: **[Withdrawn in r4; replaced by OA-2 AC-27 (stale recovery) and AC-138 (the limit's value).]** A process that dies can leave a `BUILDING` row behind. Once that row is older than a stale limit, the next publish of the venue sets it to `FAILED` and then goes ahead, so recovery is automatic (ruled D3). The limit is a setting (C8). Its value is provisional until it is sized from the time a full Aurora publish takes, which is measured in stage B. Verify: integration.

### 3.2 Validation: refusals (PRD §6.3; L92; L108)

- AC-11: **[Withdrawn in r4: reversed by L170 Q2 and Q3; replaced by AC-113, a warning.]** **Unreviewed drafts (L108).** Publish is refused while any `Unit`, `Opening`, `FloorObject` or `NavConnector` of the venue has `NeedsReview = TRUE`. Each one is listed with its kind, name (if any) and level, and shown on the map. Verify: integration (the MEZZ seed's `NeedsReview` doors are each listed).
- AC-12: **[Withdrawn in r4: reversed by L170 Q2; replaced by AC-97 (an ADD_PATH through a wall is a warning) and AC-94 (the wall list).]** **No walkway through a wall (L92; walls ruled D4).** Publish is refused if any generated walkway, or any `ADD_PATH` correction, crosses a wall as defined in §3: a non-walkable unit's outline away from its openings, or the outline of a `BlocksWalk` floor object. The crossing point is shown on the map. Verify: unit (geometry fixtures, including a walkway through a blocking floor object and one through a door gap, which is allowed) and integration.
- AC-13: **[Withdrawn in r4: reversed by L170 Q2 (the owner named AC-13); replaced by AC-110, a warning. The router now ends such a trip at the nearest reachable point, P0-06 AC-76.]** **Reachability (PRD §6.3 "every store reachable"; ruled D5).** Publish is refused if a place cannot be reached. Each unreachable place is named and shown at its door. A place counts as reachable only if all of these hold:
  - every active occupant is reached through at least one of its doors; amenities, transit points and anchors are reached at their own position;
  - it can be reached from at least one venue entrance, and a way leads back from it to one;
  - only everyday connectors are counted (evacuation-only connectors are not);
  - walk-through stores count as passages (AC-39). A place that can only be reached through a store the mall has not marked `PassThrough` is unreachable (L92, Risks);
  - publish runs no step-free check (PRD §6.7 has the app say "no step-free route");
  - a nested section (`ParentUnitId`) with no reachable door of its own is reached through its parent's doors;
  - *[r3 · FF-5]* until P3-02, amenities of the two evacuation types (refuge area and assembly area) are not checked (AC-88; Q20, ruled 2026-10-12, residual sheet R29).

  Verify: unit and integration.
- AC-14: **[Withdrawn in r4: reversed by L170 Q2; replaced by AC-111, a warning.]** **No orphan paths.** Publish is refused if any part of the walkway graph is not joined to the part that holds the venue's entrances. This includes an `ADD_PATH` whose ends do not join the graph (DC-6). Each orphan part is shown. Verify: unit.
- AC-15: **[Withdrawn in r4: (a) and (b) are now OA-1's validator (OA-1 AC-7: two distinct levels, one stop per level, an escalator with exactly two); (c) is AC-96 and AC-112, a warning (reversed by L170 Q2); (d) is gone, because the document has no `RiseM` and the rise is the levels' elevation difference (AC-101), with AC-112's `CONNECTOR_NO_RISE` for a zero rise.]** **Connectors paired.** Publish is refused, with the faulty end shown, if any of these hold:
  - (a) a stairs, escalator or ramp row lacks `ToLevelId`, `ToX` or `ToY`, or has both ends on the same level;
  - (b) a lift has fewer than two `NavConnectorStop` rows on different levels;
  - (c) any end or stop does not lie on the walkable area of its level and so cannot join the graph;
  - (d) a stairs, escalator or ramp row has no `RiseM` (the rise trap, Blueprint Part 1).

  A lift needs no `RiseM` (ruled D7). Its rise between two stops is the difference of their levels' `ElevationM` (AC-33). Verify: unit and integration.
- AC-16: **[Withdrawn in r4: reversed by L170 Q2; replaced by AC-112, a warning. The containment test itself, with "on the line is inside" (DC-12), is kept, and AC-82's boundary vectors still run it.]** **Inside the boundary (invariant 10).** Publish is refused if any element is outside `Venue.BoundaryGeoJson`, and each such element is shown. The elements are: units, openings, floor objects, amenities, transit points, anchors, connector ends and stops, beacons and corrections. A point or shape on the boundary line counts as inside (DC-12; L30 puts transit points "at its edge"). Verify: unit.
- AC-17: **[Withdrawn in r4; replaced by AC-109, which keeps both checks as blocking (L170 Q2).]** **No beacon identity collision (invariant 9).** Among active beacons:
  - no two share (`ProximityUuid`, `Major`, `Minor`) anywhere on the platform;
  - every beacon's `ProximityUuid` is its tenant's `BeaconProximityUuid`.

  If either fails, publish is refused and both beacons are shown. The database already enforces both (`UQ_Beacon_Identity`, `FK_Beacon_Namespace`), so this check is defence in depth and is tested on in-memory data. D9's "identifier range per floor" was not checked in r2 (ruled D9: not yet). r3 adds it as its own refusal, AC-87, built in FF-11 (A19). Verify: unit.
- AC-18: **[Withdrawn in r4: an unclosed ring, fewer than three points and a wrong type can no longer arrive, because OA-1's validator rejects them (OA-1 AC-8, AC-16); a self-crossing outline is AC-112's warning (OA-1 DC-16; reversed by L170 Q2).]** **Unreadable shapes (DC-4).** An element whose geometry is not a readable polygon, line or point is listed as "This shape can't be read" with the element named, and publish is refused. Examples: an unclosed ring, fewer than three distinct points, a self-intersecting outline, or the wrong GeoJSON type. Verify: unit.

#### 3.14.1 [A1′a] The walkable area and the graph (AC-89 to AC-99)

- AC-89: **[A1′a] One analysis, three callers.** The engine's entry is one pure function, `analyseMap(snapshot)`. The snapshot is a plain object: the canonical layout, the venue's active stores and beacons, the lookup rows and the catalog, the tenant's beacon namespace, and the resolved settings (AC-117 lists them). It returns `{ findings, model }`: every finding (AC-107) and the package model (AC-116). It opens no database, reads no clock, no file and no environment value. Publish (AC-118), the checks route (AC-121) and the preview route (AC-124) all call this one function, so no check and no graph step has a second copy, in Node or in Dart. The same snapshot always gives the same findings and the same model in the same order (AC-31, kept). Verify: unit (the function run with the database, file system and clock stubbed to throw; two runs compared byte for byte); review (one exported analysis entry).
- AC-90: **[A1′a] The walkable area (L170 §1.2; office §11).** For each level the engine derives one walkable area in venue-frame metres. It is the level's rectangle (`origin`, `size`) minus the union of these blockers, each grown by the body margin (AC-91):
  - (a) every wall, as a rectangle of its thickness `t` along `a` to `b`;
  - (b) every unit whose `walkable` is false, a pass-through store included (its floor is crossed only by AC-104's edges);
  - (c) every item whose catalog type has `blocks` true, as its footprint: the box `w` × `d` turned by `rot`, or the circle of diameter `w` for a round type, a missing size read from the type's default;
  - (d) on the outdoor level only, the `footprint` of every building (DC-17).

  **A connector's footprint** (`x`, `z`, `w`, `len`, `rot`) **is not a blocker** (DC-40; this answers OA-3's X2). The editor and the 3D preview draw it, and the connector enters the graph only through its `stops` (AC-96). An item is the only drawn object that blocks, and only through its catalog type's `blocks`. A stop that OA-3 has snapped onto walkable floor may therefore lie inside its own connector's footprint without any effect on the graph. A stop that lies inside a non-walkable unit or another blocker is off the walkway (AC-96).

  Then the door channels of AC-92 are cut back in, and last every `BLOCK_AREA` correction is subtracted, exactly as drawn (DC-18). A node or a walk edge may lie only inside this area (AC-93). A window opening never cuts a gap. Verify: unit (V-GEO-1, V-GEO-3 and V-GEO-5, §3.14.6); property test (every generated node and edge inside the area).
- AC-91: **[A1′a] The body margin (office §11).** The blockers (a) to (d) of AC-90 are grown by `publish.bodyMarginM` (default 0.24 m; a `publish.*` setting, so it never enters the package, AC-46) before they are subtracted. The level rectangle's edge is not grown, and a `BLOCK_AREA` is not grown (DC-18). Vector V-GEO-1: two parallel walls 0.15 m thick whose inner faces are 3.000 m apart leave a walkable strip 2.520 m wide; a point 0.20 m from a wall face is not walkable, and a point 0.25 m from it is. With the margin set to 0 the strip is the full 3.000 m. Verify: unit.
- AC-92: **[A1′a] Door channels (office §11: "doors must cut a channel after blockers are marked").** After the blockers are grown, each opening of kind `door` cuts a channel back out of them: a rectangle as wide as the opening's `w` along its wall and as long as the wall's thickness plus the body margin on each side, centred on the opening. A `window` never cuts one. Without the channel the margin closes a narrow doorway, which is the trap this criterion guards. Vector V-GEO-2 holds both the channel and the trap. Verify: unit (V-GEO-2 run with channels and with channels switched off in the test).
- AC-93: **[A1′a] Nodes and walk edges (L32; L170 Q6).** Walk nodes lie on a square lattice of `publish.nodeSpacingM` (default 1.5 m; a setting, never a literal), anchored at the venue frame's origin (DC-19), at every lattice point inside a level's walkable area. Each node is joined to its 8 neighbours and its 8 knight's-move neighbours (16 in all; the named constant `GRAPH_NEIGHBOUR_MOVES`, DC-22, which a test can switch to the 8 neighbours so that AC-137 measures both; the owner rules on 8 or 16 after that measurement, A1's review round, Q4 "measure first") by a walk edge whenever the whole straight segment lies inside the walkable area. So no walk edge crosses a wall, a blocker or a store: L92's "no walkway through a wall" is now a property of the generated graph. Anchoring the lattice at the origin makes levels at the same `elevation` share node positions (AC-28, kept). Verify: unit (V-GEO-1 and V-GEO-2: a route through the channel, none through the closed wall); property test.
- AC-94: **[A1′a] Wall segments.** The engine builds one list of wall segments per level:

- AC-95: **[A1′a] Doors, entrances and places on the graph.** **Every `door` opening** becomes a **door node** on its level at the opening's midpoint (`a + at × (b − a)` along its wall), whether or not a unit lists it and whether or not it is an entrance (A1 made nodes only for place doors and entrances; a door that joins nothing now still gets its node, because AC-99 and AC-97 need it). A door node is joined, by walk edges that lie inside the walkable area (so through the channel), to the up to 4 nearest lattice nodes within 2 × `publish.nodeSpacingM` that it can see, on each side. Where one side is the inside of a non-walkable unit there is no walkway there, and the door node is that unit's place point. An amenity or anchor that names a `unit`, and one that lies inside a non-walkable unit, is reached through that unit's doors (A1's design choice 9, accepted); any other amenity, a transit point, and an anchor outside every unit, is a node at its own point, joined like a door node. ## 4. Edge cases

Each edge case below is covered by the criterion named, or has a one-line reason. **Read r3's edge cases through §4.1's table; r4's own are EC-69 onward, after it.**

**Offline or stale package**
- EC-1: A shopper's phone holds version N while N+1 is published. N's file and row are untouched (AC-6). How the app swaps is P0-04's job.
- EC-2: The admin page is offline or the API is down when Publish is pressed. The error state appears with a retry (AC-63) and nothing is created on the server.
- EC-3: A publish runs on settings and lookup costs as they are at that moment. Changing a cost or a `routing.*` value afterwards changes nothing until the next publish (AC-8, AC-33, AC-72). The old package keeps its values.

**Empty and maximum data**
- EC-4: A venue with no levels, or no walkable area, is refused (AC-20).
- EC-5: A venue with walkways but no places publishes, because nothing fails reachability. It still gets the "No beacons on this level" warnings if it has no beacons (AC-22).
- EC-6: A level with nothing on it adds no nodes and raises no problem. Its only possible warning is "No beacons on this level" (AC-22). The warning kinds are the stated ones (AC-22, AC-23, AC-75) and no others are invented.
- EC-7: The largest venue: about 100,000 m² and about 20,000 nodes (AC-69). Above that, a warning only (AC-75). About 400 places on five levels, as Aurora has (FEATURE_PIPELINE P0-02, L102), is covered by AC-66.
- EC-8: Very long text (`SearchKeywords` at 400 characters, names at 200) and non-ASCII names (ñ, Tagalog words) are stored and found by FTS5 (AC-43, with fixtures).
- EC-9: Hundreds of problems at once, for example a whole floor of unreviewed draft elements: all are returned (AC-2), and the list pages through the scaffold (AC-59).
- EC-37: A large level on the drawing route (Aurora has 2,320 units across the venue). The route answers for one level at a time (AC-73), so no response holds the whole venue.

**Tenant boundary**
- EC-10: A venue id from the other seeded tenant without the header gets 404 (AC-52). With a header naming a tenant the user lacks, it gets 403 (AC-53). The drawing route behaves the same (AC-74).
- EC-11: An element that points at another tenant's lookup row refuses the publish (AC-19).
- EC-12: Two tenants may each have a venue with the same `Code`. Packages and storage keys never collide, because the key holds the tenant id and the venue id (AC-50, D2) and the version row is per tenant (`UQ_VenueVersion`). No other venue's rows leak into a package (AC-49).
- EC-38: The dev command publishes another tenant's venues by design (AC-68, D13). It runs only where the stub runs, and it still binds each venue's own tenant in every query (rule 2).

**Each role, and permission denied**
- EC-13: MALL_ADMIN publishes (the stub acts as this role by default, L154). VENUE_EDITOR and VIEWER are refused with 403 from R2 (AC-54). Until then, the switcher can act as them and the server does not refuse. SUPERADMIN acting as a tenant is R1/R2. None of these is tested in FF-3 because of the E-20 waiver; each is on the ledger.
- EC-14: A missing venue grant (`UserVenueGrant`) is R1's tenant-and-venue check, which the stub does not do. It is on the ledger.

**Concurrent edits and publish-in-progress**
- EC-15: Two Publish presses on one venue: one runs, the other gets 409 (AC-7). The same applies to the dev command against a venue whose publish is running.
- EC-16: Two venues publishing at once: both proceed (AC-7). FF-3 runs on one machine with `maxInstances = 1` in mind (Blueprint Part 1).
- EC-17: The draft is edited while a build runs. The edit lands in the next version (AC-8).
- EC-18: The server dies mid-build and a `BUILDING` row is left behind. Once it passes the stale limit, the next publish sets it to `FAILED` and goes ahead (AC-10, D3).
- EC-19: The admin reloads the screen while a publish is running. The screen reads the `BUILDING` state (AC-62).
- EC-39: The draft is edited after version n, then the map asks for version n's walkways. The outlines are the draft's and the walkways are version n's (AC-73). They may disagree until the next publish. This is expected and is not a fault.

**Invalid input and bad data**
- EC-20: A non-integer, negative or oversized venue id gets 400 (AC-56). A venue id that does not exist gets 404. On the drawing route, the same applies to `levelId` and `versionNo` (AC-74).
- EC-21: An unreadable shape refuses the publish (AC-18).
- EC-22: Stairs, an escalator or a ramp without `RiseM` refuses the publish (AC-15d). A lift without `RiseM` publishes, with its rise taken from its stops' `ElevationM` (AC-15, AC-33, D7).
- EC-23: A connector end off the walkable area, a lift with one stop, or a two-ended connector with both ends on one level refuses the publish (AC-15).
- EC-24: An `ADD_PATH` through a wall or a blocking floor object refuses the publish (AC-12). An `ADD_PATH` whose ends join nothing refuses it as an orphan (AC-14). A `REMOVE_PATH` that cuts a place off refuses it as unreachable (AC-13).
- EC-25: A one-way escalator is the only way up to a floor, with no way back down. The places up there have no way back to an entrance, so they are unreachable and the publish is refused (AC-13, D5).
- EC-26: Evacuation-only stairs are the only way to a place. Evacuation-only connectors do not count, so that place is unreachable and the publish is refused (AC-13, D5).
- EC-27: A place that can be reached only through a marked walk-through store becomes a passage (AC-39). If either of two such stores would do, both become passages for it (AC-39, D10). If the only way is through an unmarked store, the place is unreachable (AC-40).
- EC-28: A door with no measured width raises a warning (AC-23). Its edge's clearance comes from the geometry (AC-30).
- EC-29: A nested section (`ParentUnitId`) with no reachable door of its own is reached through its parent's doors (AC-13, D5). If the parent itself is unreachable, so is the section.
- EC-30: Beacons:
  - a Demo Malls venue (no beacons) gets "No beacons on this level" warnings only (AC-22);
  - an inactive beacon is left out of the package and the checks (allow-list, D11);
  - a duplicate identity cannot reach the database (`UQ_Beacon_Identity`), so it is tested on in-memory data (AC-17);
  - two levels sharing a Major were not checked in r2 (D9). From FF-11 they refuse the publish (AC-87, A19), with the scope ruled by R30: active beacons across all the tenant's venues, and a level using two `Major`s refused too.
- EC-31: A deactivated lookup row still referenced by the venue is published with its values (AC-36).
- EC-32: The disk is full or the folder cannot be written. The row ends `FAILED` with no partial file and the latest published version is unchanged (AC-9).
- EC-33: The same draft is published twice. The graph is identical (AC-31) and a new version is written. Refusing a publish when nothing changed is not stated anywhere, so it is not done.
- EC-34: Coordinates arrive as `DECIMAL(9,3)` strings from `pg`. Geometry is computed from parsed numbers, never by string comparison. Covered by unit fixtures that use database-shaped rows.
- EC-40: The seed is run again after a publish. It stops with the `setup-db` line and changes nothing (AC-76, A8).
- EC-41: The dev command is given a tenant code or a venue code that does not exist. It names the unknown code in one line, publishes nothing, and exits non-zero, so a mistyped code cannot pass silently (AC-68; Q17 (a)).
- EC-42: The drawing route is asked for `versionNo` before any publish, or for a `FAILED` version. Either way it answers 404 (AC-74). Without `versionNo`, it returns the draft outlines (AC-73).

**Rule-specific**
- EC-35: Money (rule 1): the package carries no money, and beacon prices are not in the allow-list (D11). Nothing to test beyond AC-46's seal.
- EC-36: Option lists (rule 5): problem kinds and warning kinds are closed sets owned by code. They go in the one constants file with an authority comment (FEATURE_PIPELINE §5 item 14), not in a lookup. FF-3 creates that file in A26's shared shape: one JSON file read by the API, and by the app through a generated Dart file. FF-5 and later slices add their sets to it, and FF-3's plan is amended to cite A26 (Q23, ruled 2026-10-12, residual sheet R32).

## 7. Design choices in this spec (accepted, D15, 2026-10-09)

The product owner accepted DC-1 to DC-13 as written (D15). Each one names an alternative that would also satisfy what is stated.

- **DC-1** Validation reports every problem in one run. *Alternative:* stop at the first problem (faster, but the admin fixes one fault per round).
- **DC-2** The build reads the draft in one consistent snapshot (one database transaction). *Alternative:* lock the venue against edits for the length of the build.
- **DC-3** Graph generation is deterministic. *Alternative:* test only the graph's properties (AC-24 to AC-30) and allow ordering to vary.
- **DC-4** An unreadable shape is a refusal. *Alternative:* skip the element with a warning (risk: a store silently missing from the package).
- **DC-5** A venue with no walkable area is refused. *Alternative:* publish an empty package.
- **DC-6** How corrections apply (L32 names the three kinds but not their exact effect):
  - `BLOCK_AREA` is subtracted from the walkable area before generation;
  - `ADD_PATH` adds edges along its line, and each end joins the nearest node within a snapping distance (a setting), else it is an orphan;
  - `REMOVE_PATH` removes every generated edge its geometry crosses.

  *Alternative:* `REMOVE_PATH` removes edges within a set distance of its line.
- **DC-7** The package carries its own metadata table. *Alternative:* metadata only in the database row and HTTP headers.
- **DC-8** Version numbers keep a `FAILED` row's number, so published numbers may have gaps. *Alternative:* reuse the number of a `FAILED` row.
- **DC-9** Every published package file is kept while E-20 is open. R13 recreates everything anyway. *Alternative:* keep the last N versions per venue.
- **DC-10** Publish re-checks "same tenant or platform" for lookup references. *Alternative:* trust the write-side checks (Blueprint DC8), which FF-1's routes must then guarantee.
- **DC-11** Every problem carries an element reference and/or a location, so the screen can show it on the map. *Alternative:* problems as text only (this would not meet "shown on the map", PRD §6.3).
- **DC-12** A point on the boundary line counts as inside (L30's "at its edge"). *Alternative:* a small tolerance setting.
- **DC-13** One storage interface with a local implementation now. *Alternative:* write files directly now and refactor at the deploy call.

**Added in r3. Accepted (R33):** the product owner accepted DC-14 and DC-15 as written on 2026-10-12 (Q24, residual sheet R33). Each is a DESIGN CHOICE, not a requirement.

- **DC-14** The draft preview is its own route, `GET /api/venues/:venueId/levels/:levelId/preview`, with `?walkways=true` (AC-83). G3 says "a read-only route per level" but names no path. *Alternative:* a `?preview=` parameter on AC-73's drawing route. That means one route fewer, but one route would then answer from two sources (the draft and a version's package), with two sets of 404 rules. P0-11 r2 must cite the same path; if its plan picks the alternative, this spec changes first.
- **DC-15** In the preview, an element whose shape cannot be read is left out and listed (AC-18's wording), and the rest of the level is still drawn. *Alternative:* return no walkways at all while any shape on the level is unreadable. That is simpler, but the admin then cannot see the walkways while fixing a shape on that level.

**Added in r4.** Each is a DESIGN CHOICE, not a requirement, with an alternative that also meets what is stated. None changes what a shopper or an admin sees, except DC-38 and DC-39, which the L176 rulings left to this spec and which change nothing a shopper can see before P3-02. They are for the product owner's sign-off with the plan.

- **DC-16** The builder port carries **finding objects**, not strings (AC-118). It widens OA-2's port, and A2′ changes OA-2's tests that use a fake builder. OA-2 merged unchanged (decided 2026-10-14, C-3), so the widening is A2′'s. *Alternative:* encode each finding as a JSON string, which leaves OA-2's port as it is, and both sides parse text.
- **DC-17** The outdoor level leaves out the `footprint` of every building. The re-plan says "every building footprint at its elevation" (§1.2), which could mean only a building that has a level at the outdoor level's elevation. *Alternative:* that narrower reading. The sources never want a shopper to walk through a building from outside.
- **DC-18** A `BLOCK_AREA` is exact (it is not grown by the margin) and is applied after the door channels, so an admin can close a door with one. *Alternative:* grow it and apply it before the channels.
- **DC-19** The lattice is anchored at the venue frame's origin, so levels at one elevation share node positions. *Alternative:* each level's own origin.
- **DC-20** Wall segments include the outline edges of every non-walkable unit, split at its doors (AC-94). OA-1 §1 says such an outline only subtracts from the walkable area, but the origin snap (P0-06 AC-8) must not cross a store drawn without walls. *Alternative:* explicit walls only.
- **DC-21** Costs and real lengths are stored to 0.001 (seconds and metres), rounded with OA-1's helper. The owner's floor is "at least 0.001 s" (L176). *Alternative:* store more digits (a 32-bit float keeps about 7 significant digits), or compute the products in exact decimal arithmetic. The vectors avoid exact ties, because a binary float can flip one.
- **DC-22** `PREFERRED_CONNECTOR_FACTOR` (0.7) and `GRAPH_NEIGHBOUR_MOVES` (16) are named constants in one place, each with its source. *Alternative:* settings. Q4 of the re-plan makes only the base and the per-rise tunable, and the neighbour count changes the graph's structure.
- **DC-23** A connector edge's real length is the planar distance between its two stops (A1's choice 13). *Alternative:* the connector's `len`, or the 3-D length including the rise.
- **DC-24** `UNREVIEWED` is one finding per element. *Alternative:* one per level with the element list in `params`: shorter lists after an AI conversion, but a finding that names hundreds of elements.
- **DC-25** Kind spellings: a kind that survives from A1 keeps A1's spelling, and the finding keeps A1's shape plus `message`, `levelName` and `path`. *Alternative:* new, more descriptive names (`PLACE_UNREACHABLE`, `WALKWAY_ORPHAN`), which cost A1's tests a rename.
- **DC-26** With no entrance, reachability uses office §11's fallback, with a tie-break (least `elevation`, then `ordinal`, then document order) and a snap to the nearest walkway node on that level. The ruled text gives the fallback point but no tie-break. *Alternative:* skip the check and raise only `NO_ENTRANCE`.
- **DC-27** A store's place id is its unit key. With two active stores on one unit the lowest `OccupantId` is kept and the others are named and left out. *Alternative:* keep both and give the later ones a suffix, which breaks "one place per unit" (P0-11 G7).
- **DC-28** The stored package is the gzip of the SQLite file (`application/gzip`, extension `gz`), and P0-04 unzips it before opening. *Alternative:* store the raw file. r3's hash rule forbids re-encoding between the storage and the phone, so the download would be about 7 MB raw against PRD §7's 0.3 to 3 MB.
- **DC-29** The R*Tree stays over walk edges (r3 AC-44), because P0-06's origin snap projects onto an edge. Spike 2 found it the largest part of the file (about 5 MB of 7.2 MB raw). *Alternative:* index nodes and rebuild edges from adjacency, which saved about 3.3 MB raw in Spike 2. AC-137's size figures decide.
- **DC-30** The checks and the preview are two routes: the preview can be large, and the checks are small and called often. *Alternative:* one route with an `include` parameter.
- **DC-31** The engine runs on the request's event loop in FF-3′. *Alternative:* a worker thread, which keeps autosave responsive during a long publish but adds a build step and a message boundary. AC-137 measures the longest stretch.
- **DC-32** A1′ is split into A1′a (AC-89 to AC-99) and A1′b (AC-100 to AC-116). *Alternative:* one stage of 28 criteria, against the delivery-speed rule of about 20.
- **DC-33** The latest-version data is a new route (AC-125). *Alternative:* widen OA-2's `versions[]` with size, hash and counts.
- **DC-34** The snapshot reads the layout from the `BUILDING` row inside its own transaction (AC-117). *Alternative:* trust the layout the port passes, which is simpler but lets the layout and the rows come from two moments.
- **DC-35** `CONNECTOR_NO_RISE` warns for a connector between levels of equal elevation. OA-1 EC-30 leaves this check to FF-3′. *Alternative:* no check, so a near-free connector goes unnoticed.
- **DC-36** `ORPHAN` is reported only for a part that holds a lattice or an `ADD_PATH` node. *Alternative:* report every part, which would repeat each unreachable place's own finding.
- **DC-37** The checks route answers 200 with `INVALID_DOCUMENT` findings for a draft that fails today's validator. *Alternative:* 400, as a save would, which would make the Checks panel handle an error where it expects a report.
- **DC-38** (L176) `evacuationOnly` connectors stay in the graph, are costed by the same formulas, and carry the evacuation flag on each edge; they are excluded from the search index (R28) and from AC-110. *Alternatives:* leave them out of the package until P3-02 (a smaller graph, but a package change when evacuation arrives), or write a second graph for evacuation. No shopper-visible behaviour differs before P3-02, so this is not a product question.
- **DC-39** (L176) The other-way margin's key is `routing.otherWayMarginS`, default 0.417 (0.5 m ÷ 1.2 m/s, stored to 0.001 s), a static seeded default like `routing.stairsSaveS` and independent of the walking speed. *Alternative:* derive it at publish from the tenant's own walking speed, so "0.5 m of walking" stays true when a mall changes the speed.
- **DC-40** A connector's footprint is not a blocker (AC-90; OA-3's X2). *Alternative:* the footprint blocks walking except at its landings, which would make every snapped pin and converted connector need a landing offset.
- **DC-41** The package format number and its frame live in `functions/src/config/package-format.json` (A1's L5 proposal, not ruled), read by the builder as `formatVersion` and by the app's package reader through a generated Dart copy. *Alternative:* a named constant in the engine and a hand-kept Dart constant held equal by a test.
- **DC-42** The engine holds nodes and edges in typed arrays. *Alternative:* one object per edge, as A1's first cut did (about 470 MB of heap on Bayview Grand).

**Q18 [spec-writer] Lookup codes in the package (B2, B9; P0-04 r2 AC-36).** **Ruled 2026-10-12 (residual sheet R27): option (a)**, built in FF-5 with AC-79. B2's chip table is keyed by codes (Restroom → `CR`, `CR_PWD`; ATM → `ATM`; EV charging → `EV_CHARGING`; Food → `DINING`). B9 and P0-04 AC-36 put "the main building first" (`BuildingType` `MAIN`). But the allow-list (§3.7) carries the lookups' labels, not their `Code`s, so the phone cannot tell which rows a chip means or which building is the main one.
- (a) *Recommended:* add the `Code` of every lookup row the package carries to the allow-list (occupant category, amenity type, transit type, connector type, building type and store status), built in FF-5 with AC-79. The chip table and "main first" then read codes from the constants file (B2's pattern), never labels.
- (b) Codes for amenity types, occupant categories and building types only.
- (c) No codes. The chips match by label and the main building is the first one by id. This is fragile: a mall that renames "Restroom" breaks its chip.

**Q19 [spec-writer] Evacuation-only connectors in the index (A10; L87, L117).** **Ruled 2026-10-12 (residual sheet R28): option (a).** Applied in AC-43, AC-78 and EC-49. AC-78 indexes every connector's stops and ends. Routing uses evacuation-only connectors only in an evacuation (P3-02), and the emergency button is hidden until then (L117). So a shopper who searches "stairs" could be offered stairs no route will use.
- (a) *Recommended:* leave evacuation-only connectors out of the index until P3-02. They stay in the graph with their flag (AC-35).
- (b) Index them like every other connector, and let the app hide them.

**Q20 [spec-writer] Refuge areas and assembly areas (G9).** **Ruled 2026-10-12 (residual sheet R29): option (a).** Applied in AC-13 and new AC-88 (built in FF-5), EC-50, EC-67 and EC-68. G9 makes them amenity types that FF-10's editor can place. Under r2, every amenity is indexed (AC-43) and must be reachable over everyday connectors (AC-13, D5). So an assembly area outside, reachable only by evacuation-only stairs, would refuse the publish, and "assembly" would show in shopper search before evacuation exists.
- (a) *Recommended:* until P3-02, amenities whose type is an evacuation type are left out of the FTS5 index and out of AC-13's reachability check. They stay in the package with their position. The two evacuation types are a closed set in the constants file (codes `REFUGE_AREA`, `ASSEMBLY_AREA`; L87 as authority), read by the engine.
- (b) Treat them as ordinary amenities: indexed, and reachable over everyday connectors.
- (c) As (b), but their reachability also counts evacuation-only connectors.

**Q21 [spec-writer] The scope of AC-87's `Major` check (A19).** **Ruled 2026-10-12 (residual sheet R30): option (a).** Applied in AC-87, EC-30, EC-60 to EC-62, EC-65 and EC-66. A19 says "unique in the tenant's namespace" and "publish refuses two levels sharing a `Major`", but not which beacons count or whether one level may use two `Major`s.
- (a) *Recommended:* active beacons only (as AC-17 and the package), across every venue of the tenant (the namespace is the tenant's); a level whose active beacons use two or more `Major`s is also refused ("one `Major` per level"). Planned inactive rows are kept in line by P0-12's allocator (AC-31), not by publish.
- (b) Active beacons of the venue being published only, with no mixed-`Major` refusal.
- (c) As (a), with inactive rows counted too.

**Q22 [spec-writer] Do the FF-5 additions change `PackageFormatVersion` (AC-3, AC-81; P0-04 EC-9)?** **Ruled 2026-10-12 (residual sheet R31): option (a).** Applied in AC-81 and §5 item 12. FF-3 writes format 1. The FF-5 additions add columns and index rows. A phone that holds a format-1 package keeps it, and P0-04 EC-9 refuses only a newer format.
- (a) *Recommended:* keep format 1 while E-20 is open. The additions only add, a format-1 reader that names its columns is not misled, and every seeded venue is published again with `npm run publish:dev -- <TENANT_CODE> --all` once FF-5 merges (throwaway data, L153). The number is bumped only for a change an existing reader would misread.
- (b) Bump to format 2 in FF-5. The FF-5 app reads format 2 only, so held format-1 packages must be republished.

**Q23 [spec-writer] Which slice creates the one constants file (A26; EC-36)?** **Ruled 2026-10-12 (residual sheet R32): option (a).** Applied in EC-36 and §5 item 14. A26 says FF-5 creates it "in R11's shape" because "FF-5 is the first slice that adds sets". But FF-3 comes first and adds the problem and warning kinds (EC-36), and FF-3's plan has api-coder create a constants file in its stage A2 (`functions/src/config/constants.js`, JavaScript only; `plan/FF-3-publish-engine.md` §4.4, DC-P14). Neither is in code yet.
- (a) *Recommended:* FF-3 creates it in A26's shape (one JSON file read by the API, and by the app through a generated Dart file), and FF-5 adds its sets to it. FF-3's plan is amended to cite A26.
- (b) FF-3 creates its JavaScript-only file as planned, and FF-5 converts it to A26's shape. This costs some rework, and FF-3's sets move once.

**Q17 [spec-writer] The dev command (D13) is given a tenant code or venue code that does not exist. What does it do?** The plan's 0.9 §4.6 sets the exit code to "the number of venues refused or failed". That would make a mistyped code exit 0 with nothing published, which can hide the mistake in a script.
**Ruled 2026-10-09 (option a), by the product owner, as recommended:** the command names the unknown code, publishes nothing, and exits non-zero. Applied in AC-68 and EC-41.
- (a) Name the unknown code in one line, publish nothing, and exit non-zero. *Recommended; taken:* a mistyped code cannot pass silently, and nothing runs against the wrong venue.
- (b) Print "No venues matched", publish nothing, and exit 0. This follows the plan's exit rule as written.
- (c) Publish whatever does match and name the code that did not, with a non-zero exit.
