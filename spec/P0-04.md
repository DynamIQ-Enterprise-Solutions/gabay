## 1. What this spec covers

The shopper app's Map tab and what it needs, built on FF-SK's shell and run on an Android emulator or a phone connected to this machine (E-20, localhost only):

1. **The public package API** (api-coder): a GET-only, unauthenticated list of published malls, carrying each mall's shopper settings (A3), and a package download with an ETag check (`/api/public/*`, Blueprint Part 1).
2. **The mall picker and mall detection** (flutter-coder; the location channel by native-ble, E13): the picker opens at every launch (E2); manual pick; detection by location against each mall's boundary, on the phone. Detection is built in full and verified with fixtures; no seeded venue carries a georeference (§G ruling 1), so it is first seen on a device when a real venue does.
3. **Package delivery** (flutter-coder): download, SHA-256 verification, the ETag refresh check on launch, on detection or pick, and on a timer; a background download (while the app is open); verify-then-swap only between trips, with "Map updated" (L102); opened read-only and immutable (E-02).
4. **The map, a true 3D view from r4** (flutter-coder, `lib/core/map3d/`; L83's 2.5D standard amended for the shopper map by L188): extruded walls and store volumes, a perspective camera (orbit, tilt, zoom), simple shading, back-to-front drawing; levels, pinch, rotate with the compass, recentre, the flat toggle, the whole-site and all-levels views, wing shortcuts, labels that thin out. **[r4]** It is built in stage V's map view, after the picker and download (AC-80), and only after the spike of AC-78 to AC-79 passes.
5. **The Map tab on FF-SK's shell:** the Map tab replaces FF-SK's Map placeholder, and the module registry's Map entry is marked built (FF-SK §2); Me gains "Change mall" above FF-SK's Me placeholder; Places and Parking stay FF-SK's placeholders (E4).
6. **The hand-off to routing** (§6): the internal-build "Start here" origin and Go's disabled state otherwise (A1), the place sheet with Go, the route sheet's container with its three states and ✕, the trip-active state that holds a swap, and drawing what P0-06 returns (A2). The routing engine and the route section are P0-06.
7. **[r3] The parts §L of the 2026-10-12 sheet assigns here,** each built in the slice named:
   - **FF-5** (with P0-05): a trip also ends when the shopper confirms "End your route to ⟨place⟩?" to start another route (ruling B4; residual sheet R41; AC-46).
   - **FF-6** (with P0-08): "Start here" is withdrawn, because P0-08's `PositionSource` replaces it (AC-55, EC-34); Go with no position opens "Where are you?" (ruling C2; AC-56); the set-location button on the rail (AC-67); the map's position layer, drawing the looks each producer defines (AC-68).
   - **FF-7** (flutter-coder, with P0-14; ruling A15): the turning map, "Map faces the way I walk" (L111; AC-69 to AC-76); follow-me and level-follow (ruling F8; AC-77); the phone keeps the last shopper settings received per venue, so they apply offline (ruling A6; AC-66); the mall list's settings gain `voice.*` and `map.*` (AC-60).
   - **FF-8** and **FF-9:** the mall list's settings gain `guide.*` (FF-8) and `dot.*`, `floor.*`, `calibration.*`, `scan.*`, `rf.*` (FF-9) (AC-60); the live dot's start of follow-me is proven on a device in FF-9 (AC-77).

This revision covers the intent plus what the container needs (E4), and r3's parts. The rest of the FEATURE_PIPELINE P0-04 entry is listed in §10 with the entry that gives it behaviour; P0-04 stays `IN PROGRESS` and is marked `DONE` only when its last revision lands (E4) and FF-9 has proven the live-dot parts.

## 3. Acceptance criteria

### A. The public package API (api-coder)

- **AC-1:** A GET on the public mall list returns every venue that has at least one PUBLISHED version and whose venue and tenant are both active, from every tenant, paged with the standard's envelope and page-size cap; a venue with only BUILDING or FAILED versions, or none, and an inactive venue or a venue of an inactive tenant, is not listed (E6, r1 Q9 v). Verify: API (seeded rows inside a rolled-back transaction).
- **AC-2:** The list takes a search term: every word typed must appear in the venue's name, case-insensitive; "spire" finds Skyline Spire and "bay grand" finds Bayview Grand (the demo's split-on-"s" filter is not copied, L85). Verify: API.
- **AC-3:** Each list item carries only the allow-listed fields the plan names, which include the venue's id and name, its latest published version, that version's SHA-256 and size, building and level counts (AC-61), the boundary, the georeference (null where unset) and the shopper settings of AC-60; no draft data, no `TenantId`, no secret (invariant 8). Verify: API (asserts the exact key set).
- **AC-4:** A GET on a venue's package returns the bytes of its latest PUBLISHED version with an `ETag` and a way for the phone to tell which version the bytes belong to. Verify: API.
- **AC-5:** The same request with `If-None-Match` set to the current ETag returns 304 with no body. Verify: API.
- **AC-6:** After a newer version is published, the same conditional request returns 200 with the newer bytes and a new ETag; the bytes' SHA-256 equals that newer version's `PackageSha256`. Verify: API.
- **AC-7:** The public routes answer GET only; any other method is refused and changes nothing. Verify: API.
- **AC-8:** The public routes need no sign-in and ignore `Authorization` and `X-Tenant-Id`: an anonymous request and the same request carrying a token of each seeded role (SUPERADMIN, MALL_ADMIN, VENUE_EDITOR, VIEWER, and the shopper) or any tenant header get the same response; the development stub is not mounted on them. Verify: API.
- **AC-9:** An unknown venue id, a venue with no PUBLISHED version, an inactive venue or a venue of an inactive tenant (E6, r1 Q9 v), and a malformed id each get a 4xx in the standard error shape, never a 500 and never another venue's package. Verify: API.
- **AC-10:** The routes' cross-tenant queries carry the platform-query mark (`// tenant-scope: <reason>`) and pass `tenant-predicate`; no request value is interpolated into SQL (`sql-interpolation`). Verify: unit (the linters in `npm run verify`).

### B. The mall picker and detection (flutter-coder; the channel by native-ble)

- **AC-11:** The mall picker lists the malls of AC-1 through the shared paged list (`ModuleListScaffold`, `PagedListNotifier`) with all four states: loading, empty ("no malls yet"), error with Retry (`formatApiError`), and data with Load more. Verify: widget.
- **AC-12:** The picker's search uses the shared `DebouncedSearchField` (no bare `TextField`, rule 7) and the server-side search of AC-2. Verify: widget.
- **AC-13:** Picking a mall whose package is not held shows a downloading state, then opens that mall's map in the Map tab; picking a held mall opens its map at once and starts a refresh check (D). Verify: widget.
- **AC-14:** With location allowed and a fix whose accuracy circle lies inside exactly one mall's boundary (through that mall's georeference), that mall is shown at the top of the picker marked "You're here"; one tap opens it (E2, r1 Q3 (a)). Verify: unit (boundary test through the georeference, fixtures) and widget (fake location source). Not on a device until a real venue carries a georeference (§G ruling 1).
- **AC-15:** Detection runs on the phone against the boundaries already received; no request the app makes carries the phone's location (invariant 4). Verify: unit (request parameters), the `position-privacy` lint, and the review privacy pass.
- **AC-16:** With location denied, unavailable or without a fix, or with a fix outside every boundary, the picker works exactly as a manual picker and nothing blocks it (PRD §6.4, §6.8). Verify: widget.
- **AC-17:** A mall without a georeference is never detected, only picked; this includes every Demo Malls venue (§G ruling 1). Verify: unit.
- **AC-18:** Location is asked only as "while using the app"; no background or "Always" permission is declared (Foreground rule). Verify: the `foreground-manifest` lint, and review of the channel (AC-65).

### C. Download, verification and opening

- **AC-19:** A download is written to a staging file and checked against the SHA-256 of the version it belongs to before it can be opened; on a mismatch it is deleted and whatever was held stays in use. Verify: unit (a tampered byte).
- **AC-20:** A download cut short (connection lost, the app closed) never becomes the held package; the next trigger starts again. Verify: unit (a fake adapter that drops the stream).
- **AC-21:** A response that is not the API's (a captive portal's page, a redirect to a sign-in page, an HTML body, an unexpected status) is treated as offline: nothing is swapped, no error dialog is shown, and the held package stays in use (FEATURE_PIPELINE P0-04). Verify: unit (fake responses: 200 HTML, 302, 511).
- **AC-22:** The held package is opened read-only and immutable (`?mode=ro&immutable=1`, E-02); a write through the connection fails. Verify: integration (`sqlite3` on the test host).

### D. Refresh and swap (L102)

- **AC-23:** While online and in the foreground, the app sends one conditional request (`If-None-Match`) for the shown mall's package on launch, when the mall is detected or picked, and every `package.refreshCheckS` seconds, read from the mall list's settings (AC-60; default 300 until received, A3; from FF-7 the value kept for the venue, AC-66); a 304 changes nothing. Verify: unit (fake clock and adapter).
- **AC-24:** A newer version downloads while the shopper keeps using the map, is verified (AC-19), and replaces the held one only when no route is active. Verify: unit and widget.
- **AC-25:** A shopper mid-route finishes on the version they started with; when the route ends (✕, AC-46; from FF-6 also arrival, P0-06 r4 AC-68) the swap happens and the sheet says "Map updated" (PRD §6.4). Verify: widget (fake router and adapter).
- **AC-26:** Every swap shows "Map updated" once (L102's design choice) and tells the routing side to reopen the new file (§6). Verify: widget and unit.
- **AC-27:** Offline, or when a check fails, the shopper keeps the held version; no error dialog; the next trigger tries again (PRD §6.4). Verify: unit.
- **AC-28:** When the app leaves the foreground the timer stops and no request is made until it returns (invariant 5); nothing downloads while the app is closed (PRD §6.4, out of scope). Verify: unit (lifecycle fake).

### E. Offline (D2, G3)

- **AC-29:** With no connection, a mall whose package is held opens and its map works in full (levels, views, place sheet, Go); the picker lists the held malls. Verify: widget and manual (§5).
- **AC-30:** With no connection and no package held, the picker says that a connection is needed once to download a mall's map, with Retry. Verify: widget.

### F. The map: a true 3D view from r4 (L188; r3's 2.5D map, L83, L85, PRD §6.4)

AC-31, AC-32, AC-35, AC-37, AC-38, AC-39, AC-42 and AC-43 are rewritten in r4; AC-33, AC-34, AC-36, AC-40 and AC-41 are unchanged. The new 3D criteria are AC-78 to AC-92 (section K).

- **AC-31 [r4]:** The map draws the shown level from the held package as a 3D scene under the perspective camera of AC-83: the floor, the walkable areas as floor, walls extruded with their door gaps, the non-walkable units (store volumes among them) extruded from their outlines, and column and furniture blocks extruded (AC-81, AC-82); tilted by default, with a flat toggle on the rail (DC-11). (r3: store slabs, walls with door gaps and blocks drawn tilted 2.5D.) Verify: widget (screenshots, tilted and flat) and unit (the scene built from a fixture package).
- **AC-32 [r4]:** Pinch zooms (the camera moves in and out; there are no zoom buttons); a two-finger twist orbits (turns the camera round the map, the "rotation" of L111); a two-finger vertical drag tilts; one finger pans the camera's target (DC-12); every move stays inside AC-83's limits. A compass button appears while the camera's yaw is away from the building's "up" and turns the yaw back to it (`Building.MapUpDeg`, else `Venue.MapUpDeg`; the venue's for the whole site and the outdoor ground; DC24); it keeps the tilt, the zoom and the target (DC-16). From FF-7, during a route with the turning map on, the compass button also switches the turning off for that route (AC-73). (r3: pinch, a two-finger twist and the compass on a fixed-tilt 2.5D map.) Verify: widget (gestures) and unit (the angle chosen; each gesture's effect on yaw, tilt, dolly and target).
- **AC-33:** The compass needle shows north only where the venue has a georeference; no Demo Malls venue shows it (§G ruling 1). Verify: unit.
- **AC-34:** Level chips list the shown building's levels top to bottom, mark the shown one, scroll to keep it in view when they do not all fit, and mark the levels a route uses ("on your route" for the screen reader). Verify: widget.
- **AC-35 [r4]:** The whole-site view shows every building as a volume and the outdoor ground, and tapping a building opens it; the all-levels view stacks every level of the shown building in 3D, and tapping a level opens it. How each is built from the package (a building's height, the stack's spacing) is AC-88's. Taps are resolved by AC-86. (r3: the same views on the 2.5D map.) Verify: widget.
- **AC-36:** Wing shortcuts: one per building, labelled with the building's name, in published order with the main building first; each moves the camera to its building (E5, r1 Q8 (a)). Verify: widget.
- **AC-37 [r4]:** Labels thin out as the camera moves away (zooming out, or a lower view), at thresholds scaled to the venue's size, so a small venue and a mall-sized one both read cleanly (the demo's fixed thresholds are a known bug, L85). - **AC-84 [r4]:** **Simple shading, colours from the tokens only.** Each face of a volume is filled with one flat colour: a token colour (a wall token, a store token, an item token, a floor token, a ground token, each in `gabay_tokens.dart`, in light and dark) made lighter or darker by a fixed amount that depends on how the face is turned to one fixed light, plus an ambient share; roofs read lightest, and two faces turned the same way read the same. The light is fixed in the venue's frame (DC-13), so orbiting turns the faces' shades with the building. The shade factors are named constants in one file (C8) and are not colours; no colour literal appears (rule 6). No textures and no gradients are used. Verify: the `colour-literals` lint; unit (a face's colour from its normal and the token: same normal, same colour; roof lightest) and screenshots in light and dark.
- **AC-85 [r4]:** **Drawn back to front.** The scene's faces or volumes are drawn farthest first from the camera, the order is worked out again whenever the camera moves, and the sort key and its tie-break are fixed in the plan. On the fixture scenes, at every yaw from 0° to 359° (a step the plan names) and at both pitch limits, nothing farther is drawn over anything nearer: a store behind a wall, a column in front of a store, two stores side by side, a wall beside a store, a concave store. Any case that per-object ordering cannot get right (volumes that cross each other, a very long wall beside a store) is listed in the spike's report with its screenshot and either fixed by the plan or put to the owner, never left unmentioned (EC-74). Nothing behind the camera is drawn (EC-70). Verify: unit (the order from each of the fixture camera angles against a reference painter's order) and widget (screenshots at fixed cameras).
- **AC-86 [r4]:** **Taps in 3D.** A tap is resolved nearest first: (1) a pin, inside its target of at least 48 dp (AC-38); (2) in the whole-site view a building's volume, and in the all-levels view a level's slab; otherwise (3) nothing. A pin is hit even when a taller volume stands between it and the camera (the pin is drawn above the scene, AC-39). Where two pins' targets overlap, the pin whose anchor is nearer the camera wins. A long press maps to the floor plane (AC-38). A store volume's wall or roof opens nothing in r4 (the place sheet opens from the pin, AC-44; the Suggestions list a tap on the volume). Verify: unit (hit order on fixtures, including two overlapping pins and a pin behind a volume) and widget (tap a pin, a building, a level).
- **AC-87 [r4]:** **The route, the dot and the pins in 3D.** The main route and the other way (dotted amber, PRD §6.6), the position layer (every look its producer defines, AC-68) and the pins and labels are placed in venue metres on their level at that level's elevation and projected through the same camera as the scene, so the route lies on the floor in perspective, the dot's halo, dashed ring and cone lie on the floor (a circle reads as an ellipse when tilted), and pins and labels face the screen at their anchor (DC-15). They are painted after the scene (AC-39). In the all-levels view each leg of a route is drawn on its own level of the stack. The colours, states and fades each look needs are its producer's (P0-08, P0-13, P0-15); P0-04 owns the placement, the projection and the paint order. Verify: unit (a known point projects to the expected screen point at two cameras; the dot's anchor and the route's vertices share one projection) and widget (screenshots with a fake router and a fake position source in each state).
- **AC-88 [r4]:** **Levels and views.** In the single-level view the shown level is the one level whose geometry is drawn, standing at its `elevation` (a basement at a negative elevation draws as any other), and a level change moves the camera to the new level's default view. **Only the shown level's geometry is drawn: no other level shows, faded or otherwise (ruled 2026-10-15, Q20 option 1);** the shopper's other floor is marked by the faded dot alone (P0-13 AC-32). The whole-site view draws each building as a volume of its footprint raised to the top of its highest level (that level's `elevation` plus `height`) with the outdoor ground, with no interior. The all-levels view stacks the shown building's levels in ordinal order at their package elevations plus the display gap of DC-17, so each lower level stays readable, and its detail may be reduced only as the spike's figures require (DC-17). Levels of different buildings never share a stack. The faded dot on another level is P0-13 AC-32's, drawn by the position layer. Verify: unit (the stack's levels and spacing from a fixture; a basement; two buildings at equal elevations) and widget (level chips change the level; the three views).
- **AC-89 [r4]:** **Screen-reader nodes for stores and the dot.** The map gives a screen reader one node for each store of the shown level (its name, its level and its mall-set status, for example "closed"; activating it opens the place sheet, as the pin does, AC-44) and one node for the position (its state and, where the producer defines one, its label; "You should be near ⟨place⟩" is P0-13's wording), in an order that does not change when the camera moves (DC-18's alphabetical order), and a store hidden behind a volume still has its node. Each node's frame follows the pin's projected target, at least 48 dp. The node count is the level's store count (up to the schema's 300 units per level, §8). Verify: widget (the semantics tree on a fixture: a node per store; the same order at two yaws; a hidden store present; activating a node opens its sheet) and review (the node source is the scene's store list, not the painted pixels).
- **AC-90 [r4]:** **Offline from the same package (D6).** Every input of the 3D scene is read from the held package (AC-22). Drawing, the camera, picking and the semantics make no network request, and load no tile, texture, font or model from the network; nothing new is downloaded after install for the map. A held mall draws exactly as it does online (AC-29). Verify: widget (offline, a fake adapter that records zero requests across an orbit, a tilt, a zoom and a tap) and review (no network call in `lib/core/map3d/`).
- **AC-91 [r4]:** **No new package, structurally.** The map adds nothing to the app's `pubspec.yaml` or `pubspec.lock`, and nothing is added to `EXCEPTIONS.md` for it; the camera's matrices come from what the Flutter SDK already provides (a direct import of `package:vector_math` would need a pubspec entry and is therefore not used unless it is already a declared dependency; RECALLED, §12); the shopper app holds no WebView, no JavaScript and no three.js (E-25 stays admin-only). Verify: review (the `pubspec.yaml` and `pubspec.lock` diffs of the stage; `flutter analyze` with its undeclared-import check, RECALLED) and unit or lint (no `webview` or `three` import under `app/lib`).
- **AC-92 [r4]:** **The tablet layout and L111's turning map are kept on the 3D camera.** (a) AC-51 stands: a screen whose shortest side is at least 600 dp keeps the wide layout and landscape, and turning the device keeps the camera (yaw, tilt, zoom, target) and the shown level, with the projection's aspect recomputed and no stretch (EC-78). (b) AC-69 to AC-77 stand with "the map's rotation" read as the camera's yaw: the route segment's heading, off by default, the rail button and tip, a glide only at real turns timed by the clock (`map.turnMinDeg`, `map.glideMs`), touch pausing the turning and follow-me until Recentre, and the compass switch; the turning and its glide change the yaw only, never the tilt, the zoom or the level. (c) Follow-me keeps the dot inside the visible part of the map (the map pane, not under the sheet) in perspective at any tilt (EC-84). Verify: widget (360×800, 800×1280 and 1280×800 logical px, tilted and flat) and unit (the yaw from a fake progress stream; the glide leaves tilt and zoom unchanged).

**Q18 [spec-writer] How tall the walls and the store volumes are drawn.** L188 asks for "extruded walls and stores" and gives no heights. **Q19 [spec-writer] The spike's pass threshold and memory ceiling.** PRD §7 states no frame-time target and no map memory figure; A6 deliberately set none for the map (AC-64 records provisional figures); L188 says "measure frame time and memory and paste them" and "if the spike fails", without a number. The figures below are **candidates for the owner to choose, not taken from any document**; none was measured. (AC-79; §8.)
1. *(Recommended)* **p95 frame time at most 33.3 ms (30 fps), and peak total app memory at most 300 MB,** on the phone at hand, on the scripted run; the share of frames over 16.7 ms is reported with no pass or fail. Reason: a CPU-sorted, CustomPainter 3D scene on a phone of unknown class (RECALLED, not measured) is more likely to hold 30 fps than 60, and a shopper app that is walked with is not a game.
2. **p95 frame time at most 16.7 ms (60 fps), and peak memory at most 200 MB.** The smoothest result; the likeliest to fail on a budget phone, which would stop the 3D map and bring options back to the owner.
3. **A frame-time threshold now (33.3 ms or 16.7 ms, the owner's pick) and the memory ceiling after the first pasted run.** Memory is then recorded, and its verdict waits for the owner to see a real figure; the risk is that a ceiling set after a measurement is bent to fit it.

**Ruled 2026-10-15 (L188 sitting): option 1.** The spike passes at a p95 frame time of at most 33.3 ms (30 fps) and a peak app memory of at most 300 MB; the share of frames over 16.7 ms is reported, with no pass or fail. Not taken: 60 fps with 200 MB; a memory ceiling set after the first run. → AC-79, §8.

2. **The level directly below, faded,** as a ghost floor plate and wall outlines under the shown level, to give depth. More to draw; the spike would need to measure it.

**Q22 [spec-writer] How tall an item is drawn when it has no height anywhere.** An item's `h` comes from the document or, when absent, from its object type's `DefaultHeightM`; the column is nullable (`db/schema.sql`), and the document's `h` is optional (OA-1, G13 requires only `w` and `d` for a type with no default size). 1. *(Recommended)* **Draw it at the same display height as a wall** (the `map.volumeHeightFraction` of its level's height), so a missing height never makes an item vanish or crash the scene. No new setting.
2. **Draw it flat**, as a footprint on the floor with no extrusion. Honest about missing data, but a pillar or kiosk then looks like paint.
3. **Require a default height on every object type** (a catalog and seed rule for OA-1 and the seeds), so the case cannot arise. Cleanest in the map, but a change to the catalog's rules outside this spec.

**Ruled 2026-10-15: option 1.** An item with no `h` is drawn at the same display height as a wall, `map.volumeHeightFraction` of its level. Not taken: flat footprint; a required default height on every object type. → AC-82, EC-89.

## 13. Design choices added in r3 (not requirements; each with an alternative)

- **DC-1 The kept settings are built in FF-7,** the first slice whose keys (`voice.*`, `map.*`) a mall would tune; FF-4's one key already has a safe default. *Alternative:* build them in FF-6; earlier, with nothing yet to keep but `package.refreshCheckS`.
- **DC-2 A newly received value that fails its key's validity rule (AC-60, R22) uses the default, not the last valid value,** as A3's rule is written. *Alternative:* keep the last valid value; kinder when an admin mistypes, but it can hide the mistake.
- **DC-3 Follow-me is built in FF-7 with the turning map,** because L111 ruling 6 pauses and resumes them together and P0-15 (FF-8) needs it; F8's live-dot start is proven in FF-9. *Alternative:* build all of follow-me in FF-9; the turning map's "pauses follow-me" would then do nothing until FF-9, and FF-8 would need its own follow.
- **DC-4 A level pick pauses follow-me and level-follow (F8) but not the turning,** since L111 ruling 6 names pan, pinch and twist only. *Alternative:* a level pick pauses the turning too; one rule for every touch.
- **DC-5 The kept settings are one record per venue in `shared_preferences`** (already pinned), replaced whole at each list read. *Alternative:* one record for every venue; simpler, but one bad write loses all.
- **DC-6 The "face my way" tip shows on the first trip on which no other one-time tip shows.** In FF-7 that is the first trip; from FF-8 the guided-walk tip takes the first trip, as ruling E18 says. *Alternative:* hold the "face my way" tip until FF-8 builds the guided-walk tip; FF-7 would then ship the button with no tip.
- **DC-7 The kept settings of a venue no longer in the list stay in use,** as the venue's package does (EC-8). *Alternative:* drop them with the venue's listing; the defaults would then apply to a map still in use.
- **DC-8 The turning map holds its angle when a route ends,** and the map stays where it was until the shopper turns it or taps the compass. *Alternative:* glide back to the building's "up" at the end of every route.
- **DC-9 A Go with no position is forgotten if "Where are you?" closes without one.** *Alternative:* keep the pending destination until another place is picked, so a later pin-button position starts the route; that could start a route the shopper had given up on.

### Design choices added in r4 (not requirements; each with an alternative; listed at sign-off, L174)

- **DC-10 The camera's bounds and the shade factors are named constants in one file, not `GlobalSetting` rows; the volume height fraction is a setting.** L188 allows "named settings or constants". Constants add no API, seed or validity rule, and a camera limit is not something a mall tunes; the height fraction is a setting because the owner ruled it so (Q18). *Alternative:* `map.*` settings for the camera's bounds too, like `map.turnMinDeg`, tunable per mall and per tenant and kept per venue (AC-66); L117 starts spike-measured numbers as provisional settings, which would favour this if the spike's numbers need field tuning.
- **DC-11 The flat toggle is kept as a camera preset:** it moves the tilt to the top-down limit and back to the last tilt (PRD §6.4 lists the toggle). *Alternative:* drop the toggle, since the tilt gesture reaches the top-down view; PRD §6.4 would then need the owner's amendment.
- **DC-12 Gestures:** one finger pans the target, a pinch zooms, a two-finger twist orbits, a two-finger vertical drag tilts. It keeps r3's pan, pinch and twist (L111 ruling 6 names exactly these) and adds tilt. *Alternative:* a tilt control on the rail (a button or a slider) and no tilt gesture, which avoids two-finger gestures fighting, at the cost of an extra control to find.
- **DC-13 The light is fixed in the venue's frame,** so each face's colour is worked out once and orbiting turns the shades with the building. *Alternative:* a light fixed to the camera, so the same screen side is always lit; shading never "moves" but every face's colour is recomputed on every camera move.
- **DC-14 The route, the dot and the pins are always painted above the scene,** as PRD §6.4 and r3's AC-39 say, even where a volume stands between them and the camera. *Alternative:* hide or ghost the part of the route behind a volume; truer to a 3D view, but it can hide the route the shopper is following.
- **DC-15 A pin and its label are anchored at the roof centre of the store's volume** (the top of the volume, facing the screen). *Alternative:* anchor at the floor, which sits inside the volume and reads as offset when tilted.
- **DC-16 The compass button returns the yaw only,** keeping the tilt, zoom and target (L111 speaks of "up", an angle). *Alternative:* return all four, which also undoes a tilt the shopper chose.
- **DC-17 The all-levels stack is spaced at each level's package elevation plus a display gap (a named constant, provisional, L117), and its detail may be reduced** (for example items left out; walls and stores stay) **only as far as the spike's figures require.** Real elevations alone put one level's walls against the next level's floor, so the lower levels would not read. *Alternative:* the real elevations with no gap and full detail, which is exact but hides the lower levels.
- **DC-18 The screen-reader order of the stores is alphabetical by name,** the same at every camera angle. *Alternative:* nearest to the dot, or to the camera target first, which is more useful on a big level but reshuffles as the camera or the dot moves.
- **DC-19 The spike's level is the Demo Malls level with the most elements (walls, units and items together)**, its counts stated beside the document's caps (AC-78), so a pass is not won on a small level. *Alternative:* a representative level of Aurora, the mall-scale proof (L102), which reads more like a real shopper's view but is lighter than the heaviest.
- **DC-20 Every wall kind (solid, glass, partition) is drawn as the same box in r4;** the kind is carried by the package (P0-03 AC-140) so a later look can use it. Q18 settled heights, not looks. *Alternative:* draw glass and partition walls lower or paler; more faithful, more to decide and to draw, and no ruling asks for it.
