## 1. What this spec covers

The shopper app's Map tab and what it needs, built on FF-SK's shell and run on an Android emulator or a phone connected to this machine (E-20, localhost only):

1. **The public package API** (api-coder): a GET-only, unauthenticated list of published malls, carrying each mall's shopper settings (A3), and a package download with an ETag check (`/api/public/*`, Blueprint Part 1).
2. **The mall picker and mall detection** (flutter-coder; the location channel by native-ble, E13): the picker opens at every launch (E2); manual pick; detection by location against each mall's boundary, on the phone. Detection is built in full and verified with fixtures; no seeded venue carries a georeference (§G ruling 1), so it is first seen on a device when a real venue does.
3. **Package delivery** (flutter-coder): download, SHA-256 verification, the ETag refresh check on launch, on detection or pick, and on a timer; a background download (while the app is open); verify-then-swap only between trips, with "Map updated" (L102); opened read-only and immutable (E-02).
4. **The 2.5D map** (flutter-coder, `lib/core/map3d/`, L83): levels, pinch, rotate with the compass, recentre, the flat toggle, the whole-site and all-levels views, wing shortcuts, labels that thin out.
5. **The Map tab on FF-SK's shell:** the Map tab replaces FF-SK's Map placeholder, and the module registry's Map entry is marked built (FF-SK §2); Me gains "Change mall" above FF-SK's Me placeholder; Places and Parking stay FF-SK's placeholders (E4).
6. **The hand-off to routing** (§6): the internal-build "Start here" origin and Go's disabled state otherwise (A1), the place sheet with Go, the route sheet's container with its three states and ✕, the trip-active state that holds a swap, and drawing what P0-06 returns (A2). The routing engine and the route section are P0-06.
7. **[r3] The parts §L of the 2026-10-12 sheet assigns here,** each built in the slice named:
   - **FF-5** (with P0-05): a trip also ends when the shopper confirms "End your route to ⟨place⟩?" to start another route (ruling B4; residual sheet R41; AC-46).
   - **FF-6** (with P0-08): "Start here" is withdrawn, because P0-08's `PositionSource` replaces it (AC-55, EC-34); Go with no position opens "Where are you?" (ruling C2; AC-56); the set-location button on the rail (AC-67); the map's position layer, drawing the looks each producer defines (AC-68).
   - **FF-7** (flutter-coder, with P0-14; ruling A15): the turning map, "Map faces the way I walk" (L111; AC-69 to AC-76); follow-me and level-follow (ruling F8; AC-77); the phone keeps the last shopper settings received per venue, so they apply offline (ruling A6; AC-66); the mall list's settings gain `voice.*` and `map.*` (AC-60).
   - **FF-8** and **FF-9:** the mall list's settings gain `guide.*` (FF-8) and `dot.*`, `floor.*`, `calibration.*`, `scan.*`, `rf.*` (FF-9) (AC-60); the live dot's start of follow-me is proven on a device in FF-9 (AC-77).

This revision covers the intent plus what the container needs (E4), and r3's parts. The rest of the FEATURE_PIPELINE P0-04 entry is listed in §10 with the entry that gives it behaviour; P0-04 stays `IN PROGRESS` and is marked `DONE` only when its last revision lands (E4) and FF-9 has proven the live-dot parts.

## 2. Settled context

- **E-20 (L153):** localhost only, no deploy, throwaway test data, nothing live until R13. Admin routes sit behind the development stub (L154). This spec's routes are public by design and are **not** behind the stub.
- **The shell (FF-SK, P0-16; L85, L117):** FF-SK builds the shopper shell with four tabs, Places, Map, Parking and Me, each a shared placeholder page ("Under development", the module's name, pipeline ID and slice; no data, no API call) drawn from the module registry `app/lib/core/modules/module_registry.dart`. A slice that delivers a module flips its "built" flag and supplies its route (FF-SK §2, §3, §6). FF-SK does not cover orientation or the wide layout; they stay in this spec (r1 AC-51, approved). The emergency button is hidden until P3-02 ships for that mall. The role picker, Test tools and the demo panel exist only in internal builds (build-time flags, Blueprint invariant 16; FF-SK §2).
- **The fallback on the Demo Malls test maps (§G ruling 1, L119):** the Demo Malls venues (Aurora, Bayview Grand, Meridian Twin Malls, Skyline Spire) have no beacons and get no georeference. On them the app runs on the fallback: pick the mall, a hand-set start, "Where are you?" (P0-08) and the guided walk (P0-15). In FF-4 and FF-5 the hand-set start is the internal-build "Start here" (A1); from FF-6 it is P0-08's "Where are you?". Real venues keep BLE positioning (P0-13) and detection by location, unchanged.
- **Delivery (L102; Blueprint §4.4):** every map comes from the database through publish; the app ships no venue. Check on launch, on detection or pick, and every `package.refreshCheckS` seconds (default 300, a `GlobalSetting`) while online and in the foreground. Download to staging, verify against the version's SHA-256, swap only when no route or evacuation is active, then "Map updated". Offline shoppers keep what they have. Only status and closures travel without a republish (P1-01, not here).
- **Settings to the phone (A3), split by key:** `routing.*` travels only inside the package, fixed at publish and working offline (P0-03, P0-06). Every other shopper setting travels in the public mall list, resolved per venue tenant (the tenant's override, else the platform value). Until received, the Blueprint default applies; a value that fails its key's validity rule is ignored and the default used. r1 Q2 (a) worded that rule as "not a positive number"; the residual sheet's R22 (2026-10-12) narrows it: each key gets the rule its own spec states, so radio values can be stored as the real, negative dBm of the beacon datasheets (AC-60). **[r3 · FF-7] Ruling A6 (2026-10-12):** the phone keeps the last values received per venue, so a mall's own values apply offline (AC-66). The keys grow slice by slice (AC-60).
- **The package (D6, E-02):** a prebuilt SQLite file (FTS5, R*Tree, the CSR graph), opened `?mode=ro&immutable=1` through `sqlite3` (Dart FFI) 3.x. Its tables are defined by P0-03; this spec reads only what P0-03 publishes. One planar frame per venue (E10).
- **Device packages (E1):** `crypto` for SHA-256 and `path_provider` for the package folder, each pinned in Blueprint Part 1 from a pub.dev check, with EXCEPTIONS entries E-21 and E-22. Location comes through Gabay's own platform channel, written by native-ble (E13); no location package. `integration_test` joins the Blueprint's SDK pin row, with no EXCEPTIONS entry; device runs are by hand, output pasted (E14). Timed figures on the realme (AC-64) come instead from a self-contained APK sideloaded from Google Drive, whose results file the product owner shares (residual sheet R42).
- **The map (L83, L85, PRD §6.4):** the app's own 2.5D renderer (CustomPainter, no map package); tilted by default with a flat toggle; pinch zoom, no zoom buttons; two-finger rotate; a compass that returns to the building's "up" (`Building.MapUpDeg`, else `Venue.MapUpDeg`; L111, DC24), its needle showing north where the venue is georeferenced; level chips; the whole-site and all-levels views; wing shortcuts; labels thinned by zoom; dot, route and pins on top; pin tap targets of at least 48 dp; taps through the exact inverse projection (the tilted-tap trap).
- **[r3] The turning map (L111; Blueprint §4.4; ruling A15):** "Map faces the way I walk" turns the map to the heading of the route segment at the shopper's progress point, during a route only, never to the compass. It is off by default; the switch is P0-14's Me setting (P0-14 AC-53), and its behaviour is this spec's. It is built in FF-7 so that P0-14's switch ships visible and FF-8's guided walk and Preview find it in place.
- **Devices (L103):** Android 7.0+ (`minSdk 24`), iOS 15+. Phones portrait; a screen whose shortest side is at least 600 dp gets the wide layout (map and sheet side by side) and may turn to landscape (DC11).
- **Saved on the phone (PRD §6.4, L88):** the last venue and the camera, across restarts, never sent; a broken or foreign saved value falls back to the default; an active route is not restored. From r3, also each venue's last received shopper settings (A6) and the "face my way" tip flag (AC-74).
- **Privacy and foreground (invariants 4 and 5):** the phone's location never leaves the phone; nothing runs in the background.
- **Wording (A4):** every new phrase in English (`app_en.arb`) now; the Tagalog part of G2 is waived to P0-14 (FF-7), recorded in FF-4's slice row; screen-reader names and ×1.4 are met now. r3's FF-6 phrases carry the same waiver (ruling A1 of 2026-10-12); its FF-7 phrases go through FF-7's Tagalog review (P0-14; ruling D1, §M item 3); from FF-8, each slice's phrases go through its own review (ruling A2).
- **Spike Venues in the admin page (A10):** settled by FF-SK ruling 3 (the development switcher picks the tenant). Nothing in this spec depends on it: the public routes ignore the tenant (AC-8).
- **Demo bugs not copied (L85)** that touch this spec: the venue search that splits words on the letter "s" (the demo's picker filter); the label zoom levels not scaled per venue; the Me subtitle that always names Aurora Mall; the turning map moved a fixed share per frame, so faster on a 120 Hz screen (L111); the compass button that silently saved the turning setting as off (L111).

## 3. Acceptance criteria

### A. The public package API (api-coder)

- **AC-1:** A GET on the public mall list returns every venue that has at least one PUBLISHED version and whose venue and tenant are both active, from every tenant, paged with the standard's envelope and page-size cap; a venue with only BUILDING or FAILED versions, or none, and an inactive venue or a venue of an inactive tenant, is not listed (E6, r1 Q9 v). Verify: API (seeded rows inside a rolled-back transaction).
- **AC-2:** The list takes a search term: every word typed must appear in the venue's name, case-insensitive; "spire" finds Skyline Spire and "bay grand" finds Bayview Grand (the demo's split-on-"s" filter is not copied, L85). Verify: API.
- **AC-3:** Each list item carries only the allow-listed fields the plan names, which include the venue's id and name, its latest published version, that version's SHA-256 and size, building and level counts (AC-61), the boundary, the georeference (null where unset) and the shopper settings of AC-60; no draft data, no `TenantId`, no secret (invariant 8). Verify: API (asserts the exact key set).
- **AC-4:** A GET on a venue's package returns the bytes of its latest PUBLISHED version with an `ETag` and a way for the phone to tell which version the bytes belong to. Verify: API.
- **AC-5:** The same request with `If-None-Match` set to the current ETag returns 304 with no body. Verify: API.
- **AC-6:** After a newer version is published, the same conditional request returns 200 with the newer bytes and a new ETag; the bytes' SHA-256 equals that newer version's `PackageSha256`. Verify: API.
- **AC-7:** The public routes answer GET only; any other method is refused and changes nothing. Verify: API.
- **AC-8:** The public routes need no sign-in and ignore `Authorization` and `X-Tenant-Id`: an anonymous request and the same request carrying a token of each seeded role (SUPERADMIN, MALL_ADMIN, VENUE_EDITOR, VIEWER, and the shopper) or any tenant header get the same response; the development stub is not mounted on them. Verify: API.
- **AC-9:** An unknown venue id, a venue with no PUBLISHED version, an inactive venue or a venue of an inactive tenant (E6, r1 Q9 v), and a malformed id each get a 4xx in the standard error shape, never a 500 and never another venue's package. Verify: API.
- **AC-10:** The routes' cross-tenant queries carry the platform-query mark (`// tenant-scope: <reason>`) and pass `tenant-predicate`; no request value is interpolated into SQL (`sql-interpolation`). Verify: unit (the linters in `npm run verify`).

### B. The mall picker and detection (flutter-coder; the channel by native-ble)

- **AC-11:** The mall picker lists the malls of AC-1 through the shared paged list (`ModuleListScaffold`, `PagedListNotifier`) with all four states: loading, empty ("no malls yet"), error with Retry (`formatApiError`), and data with Load more. Verify: widget.
- **AC-12:** The picker's search uses the shared `DebouncedSearchField` (no bare `TextField`, rule 7) and the server-side search of AC-2. Verify: widget.
- **AC-13:** Picking a mall whose package is not held shows a downloading state, then opens that mall's map in the Map tab; picking a held mall opens its map at once and starts a refresh check (D). Verify: widget.
- **AC-14:** With location allowed and a fix whose accuracy circle lies inside exactly one mall's boundary (through that mall's georeference), that mall is shown at the top of the picker marked "You're here"; one tap opens it (E2, r1 Q3 (a)). Verify: unit (boundary test through the georeference, fixtures) and widget (fake location source). Not on a device until a real venue carries a georeference (§G ruling 1).
- **AC-15:** Detection runs on the phone against the boundaries already received; no request the app makes carries the phone's location (invariant 4). Verify: unit (request parameters), the `position-privacy` lint, and the review privacy pass.
- **AC-16:** With location denied, unavailable or without a fix, or with a fix outside every boundary, the picker works exactly as a manual picker and nothing blocks it (PRD §6.4, §6.8). Verify: widget.
- **AC-17:** A mall without a georeference is never detected, only picked; this includes every Demo Malls venue (§G ruling 1). Verify: unit.
- **AC-18:** Location is asked only as "while using the app"; no background or "Always" permission is declared (Foreground rule). Verify: the `foreground-manifest` lint, and review of the channel (AC-65).

### C. Download, verification and opening

- **AC-19:** A download is written to a staging file and checked against the SHA-256 of the version it belongs to before it can be opened; on a mismatch it is deleted and whatever was held stays in use. Verify: unit (a tampered byte).
- **AC-20:** A download cut short (connection lost, the app closed) never becomes the held package; the next trigger starts again. Verify: unit (a fake adapter that drops the stream).
- **AC-21:** A response that is not the API's (a captive portal's page, a redirect to a sign-in page, an HTML body, an unexpected status) is treated as offline: nothing is swapped, no error dialog is shown, and the held package stays in use (FEATURE_PIPELINE P0-04). Verify: unit (fake responses: 200 HTML, 302, 511).
- **AC-22:** The held package is opened read-only and immutable (`?mode=ro&immutable=1`, E-02); a write through the connection fails. Verify: integration (`sqlite3` on the test host).

### D. Refresh and swap (L102)

- **AC-23:** While online and in the foreground, the app sends one conditional request (`If-None-Match`) for the shown mall's package on launch, when the mall is detected or picked, and every `package.refreshCheckS` seconds, read from the mall list's settings (AC-60; default 300 until received, A3; from FF-7 the value kept for the venue, AC-66); a 304 changes nothing. Verify: unit (fake clock and adapter).
- **AC-24:** A newer version downloads while the shopper keeps using the map, is verified (AC-19), and replaces the held one only when no route is active. Verify: unit and widget.
- **AC-25:** A shopper mid-route finishes on the version they started with; when the route ends (✕, AC-46; from FF-6 also arrival, P0-06 r4 AC-68) the swap happens and the sheet says "Map updated" (PRD §6.4). Verify: widget (fake router and adapter).
- **AC-26:** Every swap shows "Map updated" once (L102's design choice) and tells the routing side to reopen the new file (§6). Verify: widget and unit.
- **AC-27:** Offline, or when a check fails, the shopper keeps the held version; no error dialog; the next trigger tries again (PRD §6.4). Verify: unit.
- **AC-28:** When the app leaves the foreground the timer stops and no request is made until it returns (invariant 5); nothing downloads while the app is closed (PRD §6.4, out of scope). Verify: unit (lifecycle fake).

### E. Offline (D2, G3)

- **AC-29:** With no connection, a mall whose package is held opens and its map works in full (levels, views, place sheet, Go); the picker lists the held malls. Verify: widget and manual (§5).
- **AC-30:** With no connection and no package held, the picker says that a connection is needed once to download a mall's map, with Retry. Verify: widget.

### F. The 2.5D map (L83, L85, PRD §6.4)

- **AC-31:** The map draws the shown level from the held package: store slabs, walls with door gaps, and column and furniture blocks; tilted 2.5D by default, with a flat toggle on the rail. Verify: widget (screenshots) and unit (the scene built from a fixture package).
- **AC-32:** Pinch zooms and there are no zoom buttons; a two-finger twist rotates; a compass button appears while the map is rotated and turns it back to the building's "up" (`Building.MapUpDeg`, else `Venue.MapUpDeg`; the venue's for the whole site and the outdoor ground; DC24). From FF-7, during a route with the turning map on, the compass button also switches the turning off for that route (AC-73). Verify: widget (gestures) and unit (the angle chosen).
- **AC-33:** The compass needle shows north only where the venue has a georeference; no Demo Malls venue shows it (§G ruling 1). Verify: unit.
- **AC-34:** Level chips list the shown building's levels top to bottom, mark the shown one, scroll to keep it in view when they do not all fit, and mark the levels a route uses ("on your route" for the screen reader). Verify: widget.
- **AC-35:** The whole-site view shows every building and the outdoor ground, and tapping a building opens it; the all-levels view stacks every level of the shown building, and tapping a level opens it. Verify: widget.
- **AC-36:** Wing shortcuts: one per building, labelled with the building's name, in published order with the main building first; each moves the camera to its building (E5, r1 Q8 (a)). Verify: widget.
- **AC-37:** Labels thin out as the shopper zooms out, at thresholds scaled to the venue's size, so a small venue and a mall-sized one both read cleanly (the demo's fixed thresholds are a known bug, L85). Verify: unit (two fixture venues of different sizes).
- **AC-38:** A tap anywhere on the tilted, rotated, zoomed map maps back to venue metres through the exact inverse of the draw projection (the tilted-tap trap), and a pin is hit anywhere inside a target of at least 48 dp. Verify: unit (round trips at several tilts, rotations and zooms; the tolerance is set in the plan) and widget (tap at a pin's edge).
- **AC-39:** The route and pins (and the dot, once a position exists) are always drawn above the scene. Verify: unit (paint order).
- **AC-40:** Recentre is hidden until a position exists (E8, r1 Q13 (a)). In FF-4 and FF-5 the only position is the "Start here" origin of AC-55, and once it is set, Recentre returns the camera to it. *[r3]* From FF-6 the position is the `PositionSource`'s (P0-08 AC-21; from FF-9 the live dot, P0-13 AC-45), and Recentre is hidden again while the shopper is outside the venue (P0-09 AC-13, FF-8). From FF-7, Recentre also resumes follow-me, level-follow and the turning map (AC-72, AC-77). Verify: widget.
- **AC-41:** Every map and shell colour comes from `gabay_tokens.dart` through the theme, in light and dark (rule 6). Verify: the `colour-literals` lint and screenshots in light and dark.
- **AC-42:** With the phone's animations off (Android `MediaQueryData.disableAnimations`; iOS `AccessibilityFeatures.reduceMotion`, checked per Blueprint §4.4, L117), camera moves such as the compass reset happen in one step. From FF-7 this includes the turning map (AC-70). Verify: widget.
- **AC-43:** The map describes itself to a screen reader (mall, shown level, view mode), and every control on the map and rail has a screen-reader name (G2, PRD §6.23). Verify: widget (semantics).

### I. Added in r2 (from the 2026-10-09 rulings)

- **AC-55:** *[Built in FF-4; withdrawn in r3 from FF-6.]* In an internal build, a long press on the shown level sets the route's origin there (x, y, level); it is drawn as a hand-set dot with the dashed ring, and P0-06 snaps it to the walkway (RG3). ## 13. Design choices added in r3 (not requirements; each with an alternative)

- **DC-1 The kept settings are built in FF-7,** the first slice whose keys (`voice.*`, `map.*`) a mall would tune; FF-4's one key already has a safe default. *Alternative:* build them in FF-6; earlier, with nothing yet to keep but `package.refreshCheckS`.
- **DC-2 A newly received value that fails its key's validity rule (AC-60, R22) uses the default, not the last valid value,** as A3's rule is written. *Alternative:* keep the last valid value; kinder when an admin mistypes, but it can hide the mistake.
- **DC-3 Follow-me is built in FF-7 with the turning map,** because L111 ruling 6 pauses and resumes them together and P0-15 (FF-8) needs it; F8's live-dot start is proven in FF-9. *Alternative:* build all of follow-me in FF-9; the turning map's "pauses follow-me" would then do nothing until FF-9, and FF-8 would need its own follow.
- **DC-4 A level pick pauses follow-me and level-follow (F8) but not the turning,** since L111 ruling 6 names pan, pinch and twist only. *Alternative:* a level pick pauses the turning too; one rule for every touch.
- **DC-5 The kept settings are one record per venue in `shared_preferences`** (already pinned), replaced whole at each list read. *Alternative:* one record for every venue; simpler, but one bad write loses all.
- **DC-6 The "face my way" tip shows on the first trip on which no other one-time tip shows.** In FF-7 that is the first trip; from FF-8 the guided-walk tip takes the first trip, as ruling E18 says. *Alternative:* hold the "face my way" tip until FF-8 builds the guided-walk tip; FF-7 would then ship the button with no tip.
- **DC-7 The kept settings of a venue no longer in the list stay in use,** as the venue's package does (EC-8). *Alternative:* drop them with the venue's listing; the defaults would then apply to a map still in use.
- **DC-8 The turning map holds its angle when a route ends,** and the map stays where it was until the shopper turns it or taps the compass. *Alternative:* glide back to the building's "up" at the end of every route.
