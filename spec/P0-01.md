## 1. What this delivers

On localhost, in the admin page, behind FF-0's development stub and inside FF-SK's admin shell:

- Create, list, search, open and edit a **venue**: the whole property, as a record with its Code, its Name and an Active switch (B4). Venues are never deleted (B4).
- A venue's map is not part of this record. Its buildings, levels, outdoor ground level, boundary, georeference and map "up" angle are in the venue map document (`spec/OA-1.md` r1 §2.1–§2.4). OA-2 stores the document and serves it (`spec/OA-2.md` r1), OA-3 converts the seeds into documents, and the editor (OA-4, P0-11 r3) edits it. **B4 for the map** (re-plan Q12 (a)): a venue's map is never deleted. Only its draft can be cleared, and its published versions are never deleted (OA-2 AC-35).
- The venue form is a `FieldSpec` projection on S9's machinery (rule 7). The venue list uses `ModuleListScaffold` with search, "Load more", the four states and refresh on return (B3).
- In the client, the write controls are hidden from roles that may not write, from the module registry's read-only marker (B14). The server does not check roles until R2.
- The trimmed client keeps FF-1's shared machinery, which other slices reuse (re-plan §3.1; OA-2 plan §12 step 4): `ColKind.decimal` with its input rules, the paged list, refresh on return, `RoutedFormScaffold` with its delete confirmation, and the `field_spec` changes. No r4 venue field uses a decimal and no r4 screen deletes anything; their criteria stay as the machinery's own (DC-r4-1).

*r3's §1, withdrawn in r4 (L170, OA-2 DC-1): now in the venue map document (spec/OA-1.md r1).* r3 also delivered: the venue's map "up" angle and its derived boundary (B2, G4); buildings with a type from `BuildingType` and an optional map "up" angle, deleted only when empty; indoor levels and one outdoor ground level, with ordinal, real dimensions, elevation, ceiling height, grid cell size and spoken name (B6, B7), deleted only when unused (B4); `ColKind.decimal` for their seven `DECIMAL` columns (B1).

## 2. Acceptance criteria

The request's tenant is always `req.tenantCompanyID`, which the stub fills (rule 2; FF-0 §2). Without an `X-Tenant-Id` header that is Demo Malls. In the admin page, FF-SK's development switcher picks the account and, for an account holding two tenants, the tenant, and sends `X-Dev-Act-As` and `X-Tenant-Id` (A10; FF-SK 1.0 §5, ruling 3). FF-1 has no tenant code of its own: the stub still fills `req.tenantCompanyID`. "Refused" means an HTTP 4xx with the standard body `{ error: "<message for a person>" }`, no row written or changed, and never a 500 from a constraint the service could have checked first (standard §3.8). Each criterion that a 2026-10-09 ruling settled names it (for example "B4").

### Venues

- **AC-1:** An admin creates a venue with:
  - Code: required, up to 40 characters;
  - Name: required, up to 200 characters;
  - map "up" angle: *withdrawn in r4 (L170, OA-2 DC-1): now in the venue map document (spec/OA-1.md r1)*, as `site.mapUp` (OA-1 §2.2). r3 text: "0 to under 360, two decimal places; blank saves the column default, 0";
  - Active: a switch, on by default (B4).

  The form has no boundary field and no map "up" field (r4). The venue API neither reads nor answers `mapUpDeg` or `boundary` (OA-2 AC-43). Until OA-3's migration 0002 drops those columns (OA-2 H-1), the server stores `venueBoundary.js`'s `ZERO_BOUNDARY` and the `MapUpDeg` column default itself, because both columns are NOT NULL (OA-2 AC-43). The venue is stored under the request's tenant. `CreatedBy` is the acting user (actor context) and `CreatedAt` is set. It appears in the venue list without a manual reload (AC-21). Verify: API test (`venues.test.js` as OA-2 changes it), plus a widget test of the form.
- **AC-2:** An admin opens a venue, changes any of AC-1's fields still in force (Code, Name, Active) and saves. The changed values are stored, `UpdatedBy` is the acting user and `UpdatedAt` is set. Reopening the venue shows the saved values. Verify: API test, plus a widget test.
- **AC-3:** The venue list shows the tenant's venues only, a page at a time with "Load more", and a search box (350 ms debounce, S9). The search matches Code and Name. The list is sorted by Name (B11). An inactive venue stays listed, marked inactive (B4). It shows all four states: loading, empty (with a way to create the first venue), error (with Retry) and data. Verify: widget test (the four states, search, "Load more", the inactive marker); API test (the search columns, the order, the paging envelope `{ items, totalCount, page, pageSize }`, and a requested `pageSize` above 200 is capped at 200, `MAX_PAGE_SIZE`).
- **AC-4:** A second venue with the same Code in the same tenant is refused with 409 and a message that names the code field. The same Code in another tenant is accepted, because `UQ_Venue_Tenant_Code` is per tenant. Code is stored as typed, trimmed, and uniqueness is exact, as the index is: "aurora" and "AURORA" are two different codes (B11). Verify: API test.
